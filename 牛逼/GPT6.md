## 2. 面试官：章节正文为什么分表？为什么选择 chapter_id？

**参考答案：**

正文主要通过章节 ID 查询单章内容，因此选择 `chapter_id` 作为分片键，可以让阅读场景精准路由。

当前配置是**单库十表**，按照：

```
chapter_id % 10
```

路由到 `book_content0`～`book_content9`。例如章节 ID 为 12345，就访问 `book_content5`。

按章节分片能够把一本超长小说的不同章节分散到不同表，但整本书批量查询正文可能涉及多张表。分片后仍需要 `chapter_id` 索引：分片解决查哪张表，索引解决表内怎么查。

**被追问“提升数十倍”时：**

不能从拆成十张表直接推导查询快十倍。数据均匀时，只能说单表记录量约降为原来的十分之一。性能需要同环境、同数据、同并发的对照压测，比较 P95/P99、吞吐和 IO；没有数据就不报倍数。

## 3. 面试官：你做的是 Caffeine + Redis 二级缓存吗？一致性怎么保证？

**参考答案：**

严格说，当前是**两个 CacheManager 按业务域分工**，不是同一个 key 自动执行“Caffeine → Redis → 数据库”。

例如：

- 小说详情使用 Caffeine，访问快，但实例间不共享。
- 章节正文使用 Redis，便于多个实例共享。
- 不同缓存域设置不同 TTL，详情是 18 小时，正文是 12 小时。

写操作后通过缓存失效方法删除相关缓存，但不能因此宣称强一致。尤其是数据库事务提交前就删除本地缓存，其他请求可能读到旧数据并回填。

多实例下，还要处理其他节点的 Caffeine 失效。后续可以采用**事务提交后发布失效事件、可靠重试和 TTL 兜底**，更高一致性要求则需要版本控制或绕过缓存。

## 4. 面试官：MySQL 更新后如何同步 ES？afterCommit 能保证消息不丢吗？

**参考答案：**

小说变更后发送 `bookId`。如果当前有事务，就注册 Spring 事务同步回调，在 `afterCommit()` 中发送 RabbitMQ 消息；消费者收到消息后回查 MySQL，再按书籍 ID 更新 ES。

这样可以避免数据库事务回滚，但 ES 已经更新的问题。

不过，**afterCommit 只保证发送时机，不保证可靠投递**。数据库提交后进程崩溃，或者 MQ 发送失败，仍可能丢失事件。

更可靠的方案是业务数据和 outbox 事件在同一个本地事务中落库，再由任务或 CDC 投递，配合发送确认、重试、幂等消费和对账。这是改进方向，不能说当前已经全部实现。

## 5. 面试官：AI 书童具体做了什么？是不是只是调用聊天接口？

**参考答案：**

不只是聊天。项目给 `ChatClient` 注册了四类业务工具：

1. 语义找书。
2. 查询排行榜。
3. 加入书架。
4. 根据阅读偏好推荐。

模型负责识别意图和生成工具参数，真正的业务操作由后端函数执行。例如加入书架时，模型只提供 `bookId`，用户身份由后端获取，并校验登录状态和书籍是否存在。

语义找书则把书籍信息和用户描述分别转成向量，通过 ES 的 `dense_vector` 和近似 kNN 查询相近书籍。

**关键边界：**

模型参数是不可信输入，权限、参数校验和写操作幂等必须由后端保证。提示词不能代替鉴权，这也不是在训练一个大模型。

## 6. 面试官：你用 Flux 实现的是真流式吗？Emoji 为什么会乱码？

**参考答案：**

严格说，当前不是模型边生成边返回，而是先通过：

```
chatClient.prompt().user(message).call().content()
```

获得完整回答，然后按码点拆分，通过 SSE 输出。因此这是**完整响应后的分块输出**，不能说已经降低了模型首 token 等待时间。

Java 的 `String` 使用 UTF-16，部分字符需要两个 `char` 组成代理对。按 `char` 下标截断可能拆开代理对；使用 `codePoints()` 分块，可以避免这种情况。

但一个可见 Emoji 还可能由多个码点组成，所以**码点安全不等于所有组合 Emoji 都完整**。如果要实现真正的生成流，需要使用模型的 streaming API，并处理取消、超时、调度线程和用户上下文。

# 二、商城项目深挖

## 7. 面试官：介绍一下下单流程，Seata 解决了什么问题？

**参考答案：**

交易服务编排下单流程：

```
查询商品
→ 根据服务端价格计算金额
→ 保存订单和订单明细
→ 清理购物车
→ 扣减库存
```

当前下单入口标注了 `@GlobalTransactional`，目标是协调跨服务数据修改。

普通 `@Transactional` 通常只管理当前服务的数据源事务，不会自动覆盖 Feign 对端。以 Seata AT 模式为例，通过全局事务协调器、分支事务、XID 和 undo_log，协调提交或补偿回滚。

但不能认为加了注解就一定有效，还必须验证数据源代理、XID 传播、分支注册和配置。**下单有全局事务，也不代表支付链路自动拥有同样的事务保障。**

## 8. 面试官：你用数据库原子更新扣库存，能防超卖吗？

**参考答案：**

原子更新能避免应用层“先查库存，再写回库存”导致的丢失更新，但**原子性不等于库存不能为负**。

当前 SQL 主要是：

```
UPDATE item
SET stock = stock - #{num}
WHERE id = #{itemId};
```

不能仅凭它就宣称防超卖，还要结合数据库约束和执行结果判断。

更明确的改进方式是：

```
UPDATE item
SET stock = stock - #{num}
WHERE id = #{itemId}
  AND stock >= #{num};
```

同时校验购买数量大于零，并检查影响行数。影响行数为零就拒绝下单；批量扣减要核验每项结果，不能把批处理返回成功当成每个商品都扣减成功。

另外，重复请求可能重复扣库存，所以还需要业务幂等。

## 9. 面试官：用户身份如何经过网关、业务服务和 Feign 传递？

**参考答案：**

完整链路是：

```
网关验证 JWT
→ 将用户 ID 写入 user-info 请求头
→ 下游 MVC 拦截器读取请求头
→ 写入 ThreadLocal
→ Feign 拦截器取出用户 ID
→ 再写入下游请求头
```

请求结束后，在 `afterCompletion()` 中调用 `remove()`，避免线程复用导致身份串请求和数据滞留。

**两个重要边界：**

- ThreadLocal 不会自动跨线程、跨服务；跨服务靠的是 HTTP 请求头。
- `user-info` 不是天然可信的。应清理外部伪造的同名头、由网关统一重建，并限制业务服务被公网绕过访问。

异步线程池或 Reactor 场景还需要显式上下文传递，不能直接照搬同步 ThreadLocal 方案。

## 10. 面试官：Nacos 动态路由怎么实现？

**参考答案：**

网关启动时拉取 `gateway-routes.json`，并注册 Nacos 配置监听器。配置解析成 `RouteDefinition` 后，通过 `RouteDefinitionWriter` 更新路由；后续监听到变更，再重新加载。

当前实现会删除旧路由并写入新路由，因此具备不重启加载配置的机制。

不过，不能直接宣称零中断热更新。当前逐条删除和保存，还需要考虑配置校验、更新失败、上一版本保留，以及实际路由刷新是否生效。

## 11. 面试官：支付状态用了乐观锁，为什么仍可能重复扣款？

**参考答案：**

因为当前顺序是：

```
查询支付单未支付
→ 远程调用用户服务扣余额
→ 条件更新支付单为成功
```

两个并发请求可能都先读到未支付，也都完成了远程扣款，最后只有一个支付状态更新成功。

失败请求抛异常时，**支付服务的本地事务不能自动撤销用户服务已经执行的扣款**。

因此，状态条件更新只保护了支付状态迁移，没有覆盖完整支付链路。

改进需要让扣款接口按支付业务号幂等，使用唯一资金流水，并设计处理中状态、未知结果查询和补偿；必要时采用覆盖所有参与分支的分布式事务。不能只依靠最后一步更新状态。

## 12. 面试官：支付成功后 MQ 发送失败，只记录日志可以吗？

**参考答案：**

记录日志可以避免同步发送异常直接打断流程，但不能保证订单最终更新。

当前发送还发生在本地事务方法内部，可能出现：

- 消息发出，但数据库随后提交失败。
- 支付状态提交成功，但消息发送失败，没有自动重放。

更可靠的方案是：

```
支付状态与事件记录同事务提交
→ 可靠任务投递 MQ
→ 失败重试并告警
→ 消费者幂等更新订单
→ 对账修复长期不一致
```

发送确认、持久化和消费确认都重要，但任何单独一个配置都不等于“消息绝不丢”。

## 13. 面试官：支付消息已经消费，订单为什么还没变成已支付？

**结合你当前源码的答案：**

先检查消费者是否进入、是否提前返回、更新 SQL 是否执行。

你当前的支付监听器存在一个明确的条件错误：

```
if (order != null || order.getStatus() != 1) {
    return;

```

它的实际效果是：

- 订单存在：直接返回，永远不更新。
- 订单不存在：继续调用 `getStatus()`，发生空指针。

原意应该是：

```
if (order == null || order.getStatus() != 1) {
    return;
}
```

但只改判断还不够，后续更新也应该带上：

```
WHERE id = ? AND status = 1
```

避免检查后订单被关闭，却又被无条件改成已支付。

# 三、基础题快速答案

下面这些也很容易从你的简历继续追问。

### 14. HashMap 为什么不线程安全？

并发修改可能发生竞争，数据结构和复合操作没有必要的同步保障。现代 JDK 常见实现是数组、链表和红黑树；需要并发访问时可考虑 ConcurrentHashMap，但“先查再写”仍应使用 `putIfAbsent` 等原子操作。

### 15. volatile 能保证线程安全吗？

它提供可见性和一定的有序性，不保证复合操作原子。例如 `i++` 包含读、修改、写，仍需要锁或原子类。

### 16. CAS 和 AQS 有什么区别？

CAS 是比较并交换的原子操作机制；AQS 是构建锁和同步器的框架，通过同步状态和等待队列协调线程。CAS 可能用于 AQS 内部，但二者不是同一层概念。

### 17. 线程池什么时候扩到最大线程数？

通常先创建核心线程，然后任务进入队列；**队列满后**才尝试增加线程到最大值，仍无法接收则拒绝。无界队列可能导致任务持续积压，使最大线程数难以发挥作用。

### 18. `@Transactional` 为什么可能不生效？

常见原因是对象不受 Spring 管理、内部自调用绕过代理、异常被吞掉、回滚规则不匹配、使用了错误的事务管理器，或者业务进入了新线程。它也不会自动管理远程 HTTP 调用的事务。

### 19. 你项目里的策略模式和模板方法在哪里？

- **策略模式：** novel 的 `AuthInterceptor` 根据业务端选择不同 `AuthStrategy`。
- **模板方法：** `AbstractMessageSender` 固定获取模板、解析、发送的步骤，子类提供具体变化。
