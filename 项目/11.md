### 一、用户看小说的业务起点（两种情况完全一致的代码）

当读者在前端打开小说第 **`1025`** 章进行阅读时：

   `GET /api/front/book/content/1025`
2. **Controller 层接收**（[`BookController.java:102`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/controller/front/BookController.java#L102)）：

3. **Service 层业务处理**（[`BookServiceImpl.java:617`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/service/impl/BookServiceImpl.java#L617)）：
   ```java
   // 调用缓存管理器获取正文大文本
   String content = bookContentCacheManager.getBookContent(chapterId);
   ```
4. **Cache 缓存层防击穿/查询**（[`BookContentCacheManager.java:30`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/manager/cache/BookContentCacheManager.java#L30)）：
   ```java
   @Cacheable(cacheManager = CacheConsts.REDIS_CACHE_MANAGER, value = "bookContentCache")
   public String getBookContent(Long chapterId) {
       QueryWrapper<BookContent> contentQueryWrapper = new QueryWrapper<>();
       contentQueryWrapper.eq("chapter_id", chapterId).last("limit 1");
       // 触发 MyBatis-Plus 查数据库
       BookContent bookContent = bookContentMapper.selectOne(contentQueryWrapper);
       return bookContent != null ? bookContent.getContent() : null;
   }
   ```

**关键点来了**：如果 Redis 中没有这章的缓存（第一次阅读或缓存失效），MyBatis-Plus 就会生成一条标准的逻辑 SQL：
```sql
SELECT id, chapter_id, content FROM book_content WHERE chapter_id = 1025 LIMIT 1;
```
**从这条 SQL 离开 MyBatis-Plus 开始，两种情况走向了完全不同的道路！**

### 二、不使用 ShardingSphere-JDBC 时：一条路走到黑的“单表直连”

这是你项目目前**默认未开启开关**时的运行状态。

```
[MyBatis-Plus] 
       ↓ 
[原生 HikariDataSource] (只认默认数据源)
       ↓ (原封不动发送 SQL)
[MySQL 物理服务器]
       ↓
[单表 book_content] (包含千万/数亿行大文本)
```

#### 1. 底层怎么走？
- Spring Boot 容器注入的是最普通的 `HikariDataSource`。
- 驱动拿到 SQL 后，**不做任何修改**，原样发送给 MySQL：
  `SELECT id, chapter_id, content FROM book_content WHERE chapter_id = 1025 LIMIT 1`
- MySQL 存储引擎（InnoDB）直接扫描单张物理大表 `book_content`。

#### 2. 在海量小说场景下，会出现什么严重后果？
- **单表体积爆炸**：
  小说正文字段是 `mediumtext`，一章大约 3000~8000 字（包含中文排版大约 10KB~30KB）。假设平台有 100 万本小说，每本平均 500 章，总共就是 **5 亿章**。
  单表的数据文件（`.ibd`）大小将达到：
  $$500,000,000 \times 20\text{KB} \approx 10\text{TB}$$
- **B+ 树维护成本高，InnoDB 缓冲池被击穿**：
  - 单表 10TB，InnoDB 的 `innodb_buffer_pool`（通常服务器只有几十到上百 GB）**根本装不下**这张表的索引和数据页。
  - B+ 树层级随着数据暴增升高到 4 层甚至 5 层。
  - 读者每次读冷门章节，都会发生严重的 **物理磁盘随机 I/O 缺页中断**，查一条大文本耗时从几十毫秒恶化到数秒。
- **DDL 噩梦与锁表风险**：
  后期如果想给 `book_content` 表加个字段或修改索引，MySQL 会因为整表太大直接执行几十个小时甚至把数据库跑死。

### 三、使用 ShardingSphere-JDBC 时：智能“降维打击”的路由分流

这是你在简历上描述的架构（在 `application-dev.yml` 中配置 `novel.shardingsphere.enabled: true` 后生效）。

```
[MyBatis-Plus] 
       ↓ 发出逻辑 SQL: SELECT ... FROM book_content WHERE chapter_id = 1025
[ShardingSphereDataSource] (伪装成标准 DataSource 拦截 SQL)
       ↓
  【1. SQL 解析】提取出 表名=book_content, chapter_id=1025
       ↓
  【2. 路由算法】计算: 1025 % 10 = 5  ──→  目标真实表是 book_content5
       ↓
  【3. SQL 改写】将表名替换: book_content ──→ book_content5
       ↓
  【4. 执行引擎】借用底层的 HikariCP 物理连接发往 MySQL
       ↓
[MySQL 物理服务器]
       ↓ 
[物理分表 book_content5] (只需在 1/10 体量的小表中做精准点查)
```

#### 1. 底层怎么走？（以查 1025 章为例）

1. **欺骗上层**：
   MyBatis-Plus 以为自己面对的还是一张叫 `book_content` 的大表，吐出同样的 SQL：
   `SELECT ... FROM book_content WHERE chapter_id = 1025 LIMIT 1;`
2. **拦截与解析（SQL Parsing）**：
   `ShardingSphereDataSource` 拦截到了这条 SQL，内部解析引擎将 SQL 拆解成语法树，发现：
   - 要查的表是：`book_content`（命中分片规则）
   - 条件携带的分片键：`chapter_id = 1025`
3. **哈希路由计算（SQL Routing）**：
   找到 [`shardingsphere-jdbc.yml`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/resources/shardingsphere-jdbc.yml#L49) 里的行表达式：
   `book_content${chapter_id % 10}`
   立即在客户端本地 CPU 进行取模计算：
   $$1025 \pmod{10} = 5$$
   **决策**：这条数据绝对在物理表 **`book_content5`** 里面！
4. **透明改写（SQL Rewriting）**：
   改写引擎在内存中瞬间把表名给替换了，改写后的真实 SQL 变成：
   ```sql
   SELECT id, chapter_id, content FROM book_content5 WHERE chapter_id = 1025 LIMIT 1;
   ```
5. **物理执行与响应**：
   ShardingSphere 拿着改写后的 SQL 发给 MySQL，MySQL 打开 **`book_content5`** 表，通过唯一索引 `uk_chapterId` 瞬间拿到正文大文本，包装后原路返回。

#### 2. 为什么说使用它后，性能与容量提升了数十倍？

1. **单表瘦身 10 倍（热点分散）**：
   - 物理上变成了 10 张表：`book_content0` 到 `book_content9`；
   - 同样是 5 亿章节，原来单表 10TB，现在每张分表只有 1TB、5000 万行；
   - 根据章节 ID 取模，所有读写流量被**极其均匀地分流到 10 张小表**中。
2. **B+ 树矮化，缓存命中率暴涨**：
   - 每张表的索引体积急剧缩小，可以轻易全部缓存在 MySQL 的 Buffer Pool 内存中；
   - 点查时只需 2~3 次内存比较即可定位到行数据，磁盘随机读几乎绝迹。
3. **业务代码完全无感**：
   - 你项目中的 `BookServiceImpl`、`BookContentCacheManager`、`BookContentMapper.xml` **不需要改哪怕一行代码**，表名依然写 `book_content`，所有的路由、替换全由客户端 Jar 包在内存完成。

### 四、核心对比总结表（面试标准回答框架）

| 维度                       | 不使用 ShardingSphere-JDBC（现状默认）                          | 使用 ShardingSphere-JDBC（分表优化后）                                 |
| :----------------------- | :----------------------------------------------------- | :------------------------------------------------------------ |
| **生效的数据源**               | 原生 `HikariDataSource`                                  | `ShardingSphereDataSource`（装饰器包装）                             |
| **物理表结构**                | 只有单张 `book_content` 巨无霸大表                              | 物理存在 10 张小表（`book_content0` ~ `book_content9`）                |
| **发送给 MySQL 的 SQL**      | `SELECT ... FROM book_content WHERE chapter_id = 1025` | `SELECT ... FROM book_content5 WHERE chapter_id = 1025`（自动改写） |
| **B+ 树维护成本**             | 随着千万/亿级大文本膨胀，树高变大，节点频繁页分裂                              | 单表数据量降为 $1/10$，B+ 树维持在健康低层级，节点紧凑                              |
| **MySQL Buffer Pool 状态** | 索引和数据过大，内存装不下，冷数据读取产生大量磁盘 I/O 抖动                       | 单表索引小，全表热点索引常驻内存，点查逼近内存级速度                                    |
| **业务层体验**                | 面对单表 `book_content` 编写 CRUD                            | **完全相同！** 业务代码依然写逻辑表名 `book_content`                          |
