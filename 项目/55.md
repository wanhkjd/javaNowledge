<a id="第一轮统一网关鉴权与动态路由"></a>
# 第一轮：统一网关鉴权与动态路由

### ❓面试官提问 1.1：为什么要把鉴权放在网关层？Spring Cloud Gateway 的底层架构是怎样的？

#### 【基础知识剖析】
- **网关鉴权的价值**：在单体应用时代，权限校验通常由 Spring Security、Shiro 或自定义 Filter/Interceptor 完成。但在微服务架构下，如果每个微服务都各自校验 Token，会产生三大痛点：
  1. **代码重复冗余**：每个业务团队都要引入 JWT 依赖与验签逻辑；
  2. **维护成本极高**：若加密算法升级或密钥轮换，需要全量重启所有业务微服务；
  3. **安全边界模糊**：内网服务直接暴露在外，没有统一流量防御屏障。因此网关作为**边缘服务（Edge Service）**，统一承接流量入口，负责“白名单过滤 -> 鉴权验签 -> 身份透传 -> 限流监控 -> 路由转发”。
- **Gateway 底层架构原理**：
  - Spring Cloud Gateway 是基于 **Spring 5.0、Spring Boot 2.0 和 Project Reactor（WebFlux 响应式非阻塞体系）** 构建的，底层服务器是 **Netty**，而非传统的 Servlet 容器（如 Tomcat）。
  - **核心三要素**：
    - **Route（路由）**：网关的基本构建模块，由 ID、目标 URI、断言集合（Predicates）和过滤器集合（Filters）组成。
    - **Predicate（断言）**：基于 Java 8 Predicate 函数，匹配 HTTP 请求的任何内容（路径、Host、请求头、Cookie、Query 参数等）。
    - **Filter（过滤器）**：使用责任链模式，对请求在路由前后进行修改，分为 `GatewayFilter`（路由级别）和 `GlobalFilter`（全局级别）。
  - 核心处理流程：`NettyWebServer` 收到请求 -> `DispatcherHandler` 路由分发 -> `RoutePredicateHandlerMapping` 匹配目标路由 -> `FilteringWebHandler` 构建 Filter 链执行前置（Pre）逻辑 -> 路由转发下游 -> 捕获下游响应执行后置（Post）逻辑 -> 响应客户端。

#### 【结合项目代码回答】
在我们的 `hmall` 项目中，网关模块是 `hm-gateway`。我们定义了一个实现了 `GlobalFilter, Ordered` 接口的全局过滤器 [`AuthGlobalFilter`](file:///c:/Users/35998/Desktop/job/project/hmall/hm-gateway/src/main/java/com/hmall/gateway/filters/AuthGlobalFilter.java)。

```java
// AuthGlobalFilter 核心流程
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    ServerHttpRequest request = exchange.getRequest();
    // 1. 白名单放行判断
    if (!isExclude(request.getPath().toString())) {
        // 2. 提取 authorization 请求头
        List<String> headers = request.getHeaders().get("authorization");
        // 3. jwtTool.parseToken(token) 验签并解析出 userId
        // 4. exchange.mutate() 向下游请求注入 user-info 请求头
        ServerWebExchange swe = exchange.mutate().request(b -> b.header("user-info", userInfo)).build();
        return chain.filter(swe);
    }
    return chain.filter(exchange);
}
```

#### 【连环追问 & 坑点挖掘】
- **面试官追问**：代码中为什么修改请求头必须用 `exchange.mutate().request(...)`，而不是直接 `request.getHeaders().add(...)`？
  - **回答**：因为在 Spring WebFlux 响应式体系中，`ServerHttpRequest` 是**只读、不可变（Immutable）**的，`getHeaders()` 返回的是一个只读的 `HttpHeaders`。Gateway 采用了装饰器模式（Decorator Pattern），必须通过 `exchange.mutate()` 创建一个构建者（Builder），对底层 Request 包装后再生成新的 `ServerWebExchange` 继续向下传递。
- **面试官追问**：如果外部恶意用户直接伪造一个 `user-info: 1` 请求头打到网关，会不会导致越权？
  - **回答**：这是一个经典安全漏洞。网关在放行或向下游转发前，应当先从原始请求中**剥离（Remove）**外部传入的敏感 Header（如 `user-info`），只有网关验签成功后自己生成的 `user-info` 才能向下游透传；同时内网各微服务应当通过网络安全组（VPC）、K8s Service Mesh 或防火墙隔离，禁止公网直接调用内网微服务端口。

### ❓面试官提问 1.2：你们网关的动态路由是如何实现的？Nacos 监听配置的底层原理是什么？

#### 【基础知识剖析】
- **为什么需要动态路由**：Gateway 默认静态路由定义在 `application.yaml` 中，新增或修改路由规则必须重启网关，在高可用微服务集群中是不可接受的。
- **动态路由实现机制**：Spring Cloud Gateway 提供了 `RouteDefinitionWriter` 接口，内置基于内存的实现 `InMemoryRouteDefinitionRepository`。只要调用其 `save(Mono.just(routeDefinition))` 和 `delete(Mono.just(routeId))`，就能动态增删内部的路由表。
- **Nacos 监听原理**：
  - **Nacos 1.x**：采用基于 HTTP 的**长轮询（Long Polling）**机制。客户端向服务端发起轮询，服务端挂起请求 29.5 秒；若在这期间配置发生变化，立即返回最新 MD5；若超时未变化则返回 304，客户端紧接着发起下一次长轮询。
  - **Nacos 2.x**：升级为 **gRPC 双向长连接流**。服务端配置变更后，通过 gRPC 连接主动 Push 给客户端，同时辅以定期连接健康检测，实时性从原来的秒级降低到了毫秒级。

#### 【结合项目代码回答】
在我们的 [`DynamicRoutLoader`](file:///c:/Users/35998/Desktop/job/project/hmall/hm-gateway/src/main/java/com/hmall/gateway/routers/DynamicRoutLoader.java) 中：
1. 项目启动时，在 `@PostConstruct` 方法中通过 `NacosConfigManager.getConfigService()` 注册监听器：
   ```java
   String configInfo = nacosConfigManager.getConfigService()
       .getConfigAndSignListener(dataId, group, 5000, new Listener() {
           @Override
           public Executor getExecutor() { return null; }
           @Override
           public void receiveConfigInfo(String configInfo) {
               updateConfigInfo(configInfo); // 监听到变更刷新路由
           }
       });
   updateConfigInfo(configInfo); // 首次启动拉取
   ```
2. 当监听到 Nacos 上的 `gateway-routes.json` 发生变更时，调用 `updateConfigInfo`：
   - 先遍历本地维护的 `routeIds` 集合，调用 `writer.delete(Mono.just(routeId)).subscribe()` 移除旧路由；
   - 解析新的 JSON 配置为 `List<RouteDefinition>`，遍历调用 `writer.save(Mono.just(routeDefinition)).subscribe()` 写入新路由；
   - 更新本地 `routeIds` 记录。整个过程完全无需重启网关进程。

#### 【连环追问 & 坑点挖掘】
- **面试官追问**：你的代码中先 delete 清空旧路由，再遍历 save 新路由，而且都是非阻塞异步的 `subscribe()`，在高并发下会不会出现短暂的“路由找不到（404）”的毛刺？
  - **回答**：会存在短暂的并发窗口期！更优雅的做法是：
    1. **差量计算**：对比新旧配置，仅更新变更的路由，删除废弃的路由，保持不变的路由不动；
    2. **事件发布机制**：使用 Spring 的事件驱动机制，发布 `RefreshRoutesEvent`（由 `ApplicationEventPublisher` 发布），底层会触发 `RouteRefreshListener`，原子性地刷新内部路由缓存，避免了手动全量清空造成的流量真空。

# 第二轮：服务间调用与上下文透传

### ❓面试官提问 2.1：微服务之间通过 OpenFeign 调用时，用户信息为什么会丢失？你们是怎么解决这个问题的？

#### 【基础知识剖析】
- **ThreadLocal 与请求生命周期**：在基于 Spring MVC 的微服务中，每个客户端请求到达 Tomcat 时，都会从线程池中分配一个工作线程处理。我们通常使用 `ThreadLocal`（如项目中的 `UserContext`）保存当前登录用户上下文，在整个请求处理链条中随时获取，请求结束时再清理。
- **跨服务调用上下文丢失的本质**：
  - 当 A 服务（如 `trade-service`）通过 OpenFeign 调用 B 服务（如 `cart-service`）时，**Feign 本质上是一个独立的 HTTP 客户端（默认 HttpURLConnection，或 HttpClient/OkHttp）**。
  - Feign 在向下游发起全新的 HTTP 请求时，其底层 Request 并不会自动带上原请求的 Header，此时两个请求处于不同的物理网络请求中，导致原有的 `user-info` 请求头丢失，下游服务解析到的上下文即为 `null`。

#### 【结合项目代码回答】
在我们的项目中，这一整套链路是这样闭环解决的：
1. **网关层打标**：[`AuthGlobalFilter`](file:///c:/Users/35998/Desktop/job/project/hmall/hm-gateway/src/main/java/com/hmall/gateway/filters/AuthGlobalFilter.java) 验签后，通过 `request.header("user-info", userId)` 将用户 ID 放入 Header。
2. **当前服务拦截存入 ThreadLocal**：各微服务通过 Spring MVC 拦截器 [`UserInfoInterceptor`](file:///c:/Users/35998/Desktop/job/project/hmall/hm-common/src/main/java/com/hmall/common/interceptor/UserInfoInterceptor.java) 在 `preHandle` 阶段获取 `user-info` 请求头，并执行 [`UserContext.setUser(Long.valueOf(userInfo))`](file:///c:/Users/35998/Desktop/job/project/hmall/hm-common/src/main/java/com/hmall/common/utils/UserContext.java)。在 `afterCompletion` 阶段执行 `UserContext.removeUser()` 防止内存泄漏。
3. **Feign 请求拦截器链路透传**：在公共模块 [`DefaultFeignConfig`](file:///c:/Users/35998/Desktop/job/project/hmall/hmall-api/src/main/java/com/hmall/api/config/DefaultFeignConfig.java) 中注册 Feign 的 `RequestInterceptor`：
   ```java
   @Bean
   public RequestInterceptor userInfoRequestInterceptor(){
       return new RequestInterceptor() {
           @Override
           public void apply(RequestTemplate template) {
               Long userId = UserContext.getUser(); // 从当前线程获取
               if (userId != null){
                   template.header("user-info", userId.toString()); // 塞入 Feign 出站请求头
               }
           }
       };
   }
   ```
4. **下游服务再次接力**：下游服务（如 `cart-service`）收到 Feign 发来的请求，其自身的 `UserInfoInterceptor` 同样拦截到 `user-info` 放入下游的 `UserContext`。例如在 [`CartServiceImpl.removeByItemIds`](file:///c:/Users/35998/Desktop/job/project/hmall/cart-service/src/main/java/com/hmall/cart/service/impl/CartServiceImpl.java#L119) 中，直接使用 `UserContext.getUser()` 就能拿到当前用户的购物车并安全清理。

```
[前端请求] (携带 authorization)
     ↓
[Gateway: AuthGlobalFilter] 验签并添加 header("user-info", 1)
     ↓
[Trade-Service]
  ├─ UserInfoInterceptor.preHandle() -> UserContext.setUser(1)
  ├─ 业务逻辑 (下单)
  ├─ Feign 调用 CartClient
  │     ↓ [DefaultFeignConfig: RequestInterceptor]
  │     ↓ 读取 UserContext.getUser()=1 -> template.header("user-info", 1)
  ↓
[Cart-Service]
  ├─ UserInfoInterceptor.preHandle() -> UserContext.setUser(1)
  └─ CartServiceImpl.removeByItemIds() 安全获取当前用户并清空购物车
```

#### 【连环追问 & 坑点挖掘】
- **面试官追问**：如果在 `trade-service` 中，我用 `CompletableFuture.runAsync()` 启了子线程去调 Feign，你的 `UserContext.getUser()` 还能拿到吗？
  - **回答**：拿不到了！因为普通的 `ThreadLocal` 是线程私有的，子线程无法获取父线程的副本。
    - 哪怕使用 JDK 的 `InheritableThreadLocal`，也只能在**新创建线程**（`new Thread()`）时拷贝；在实际生产中，异步任务都是使用**线程池（池化复用线程）**，线程不会销毁重建，导致无法动态传递甚至发生上下文污染。
    - **终极解决方案**：采用阿里的开源组件 **TransmittableThreadLocal (TTL)**。配合 TTL 的 `TtlExecutors.getTtlExecutorService(threadPool)` 对线程池进行装饰，或者通过 Java Agent 字节码增强，在每次提交 Runnable/Callable 任务时快照父线程上下文，执行完毕再恢复，实现池化线程的透明透传。
- **面试官追问**：`UserInfoInterceptor` 的 `afterCompletion` 中为什么要调 `UserContext.removeUser()`？不调会有什么后果？
  - **回答**：两个严重后果：
    1. **内存泄漏（OOM）**：Tomcat 线程池中的线程是长久存活的。`Thread` 对象内部维护了 `ThreadLocalMap`，其 Entry 的 Key 虽然是弱引用（`WeakReference<ThreadLocal<?>>`），但 Value（这里的 `Long` 用户ID）是强引用。只要线程不销毁，Value 就无法被垃圾回收。
    2. **脏数据/身份错乱**：线程被下一个 HTTP 请求复用时，如果下一个请求是一个未登录或异常请求，可能直接读到上一个用户残留的 `userId`，造成灾难性的跨租户数据越权！

### ❓面试官提问 2.2：OpenFeign 的降级逻辑怎么写？你们在项目中是如何做容错处理的？

#### 【结合项目代码回答】
在我们的项目 [`hmall-api`](file:///c:/Users/35998/Desktop/job/project/hmall/hmall-api/src/main/java/com/hmall/api/fallback/ItemClientFallbackFacotry.java) 中，我们采用了 `FallbackFactory` 来实现降级：

```java
@Slf4j
public class ItemClientFallbackFacotry implements FallbackFactory<ItemClient> {
    @Override
    public ItemClient create(Throwable cause) {
        return new ItemClient() {
            @Override
            public List<ItemDTO> queryItemByIds(Collection<Long> ids) {
                log.error("查询商品失败", cause);
                return CollUtils.emptyList(); // 查询类接口：降级返回空集合兜底
            }

            @Override
            public void deductStock(List<OrderDetailDTO> items) {
                log.error("扣减商品库存失败", cause);
                throw new RuntimeException(); // 写操作接口：绝不能静默吞掉，必须向上抛异常触发事务回滚！
            }
        };
    }
}
```

- **核心设计考量**：
  1. **为什么用 `FallbackFactory` 而不用 `fallback = ItemClientFallback.class`？** 因为 `FallbackFactory` 能够在 `create(Throwable cause)` 中捕获到底层的具体失败原因（是网络超时 `SocketTimeoutException`、熔断开启 `DegradeException` 还是服务 500 异常），便于排查问题和分级降级。
  2. **读写分离的降级策略**：
     - **读接口（Query）**：容忍度高，可以降级返回空列表、走本地缓存或友好提示；
     - **写接口（Update/Deduct）**：**绝对禁止伪降级**。如果扣减库存服务超时，若 Fallback 返回 success，下单服务会误以为扣款/扣库存成功而继续创建订单，造成严重的数据不一致与超卖资损！因此必须抛出 RuntimeException，通知上层的分布式事务框架（Seata）进行全局回滚。

# 第三轮：下单主链路与分布式事务

### ❓面试官提问 3.1：请详细梳理一下你们商城“创建订单”的主链路，Seata AT 模式在这里扮演了什么角色？

#### 【结合项目代码回答】
在我们 [`OrderServiceImpl.createOrder`](file:///c:/Users/35998/Desktop/job/project/hmall/trade-service/src/main/java/com/hmall/trade/service/impl/OrderServiceImpl.java#L47) 方法上打上了 `@GlobalTransactional` 注解，整体流程如下：

```
[Trade-Service: createOrder] (@GlobalTransactional 开启全局事务)
   │
   ├─ 1. 查询商品：ItemClient.queryItemByIds(itemIds)  (校验存在性)
   ├─ 2. 算价校验：遍历计算 totalFee
   ├─ 3. 订单落库：orderMapper.insert(order) (状态为待支付 status=1)
   ├─ 4. 明细落库：detailService.saveBatch(details)
   ├─ 5. 清理购物车：CartClient.deleteCartItemByIds(itemIds) [分支事务 1]
   └─ 6. 扣减库存：ItemClient.deductStock(apidetailDTOS)      [分支事务 2]
```

如果第 6 步扣减库存因库存不足抛出异常，整个分布式调用栈抛出 `RuntimeException`，Seata 捕获异常后通知 TC（事务协调器）发起全局回滚，前序落库的订单、明细、已清理的购物车全部恢复！

#### 【基础知识剖析：Seata AT 模式两阶段原理】
Seata 是阿里开源的高性能分布式事务解决方案，由三大核心组件构成：
- **TC (Transaction Coordinator)**：事务协调者，维护全局和分支事务的状态，驱动全局提交或回滚。
- **TM (Transaction Manager)**：事务管理器，定义全局事务的范围，即标注 `@GlobalTransactional` 的服务。
- **RM (Resource Manager)**：资源管理器，管理分支事务涉及的本地资源（DataSource）。

**AT 模式执行流程（无侵入二阶段提交）**：
1. **一阶段（本地执行 + 记录回滚日志）**：
   - RM 拦截业务 SQL；
   - 在更新前查询记录的原始状态，生成**前镜像（Before Image）**；
   - 执行业务更新 SQL；
   - 查询更新后的最新状态，生成**后镜像（After Image）**；
   - 将前/后镜像组装成 `undo_log` 插入数据库的 `undo_log` 表中；
   - 向 TC 注册分支事务并申请**全局锁（Global Lock）**，若获取锁成功，将业务变更与 `undo_log` 在**同一个本地事务中 Commit**。
2. **二阶段（全局提交或全局回滚）**：
   - **若所有分支成功**：TC 发送异步提交指令给各 RM，RM **异步批量删除 `undo_log` 表记录**，释放全局锁，性能极高。
   - **若任意分支失败**：TC 发送回滚指令给各 RM，RM 收到通知后：
     1. 根据 XID 和 BranchID 找到 `undo_log` 记录；
     2. 对比当前数据库记录与**后镜像**（校验是否被其他非 Seata 事务修改，防脏写）；
     3. 若一致，根据**前镜像**生成逆向补偿 SQL 并执行，还原数据；
     4. 删除 `undo_log`，向 TC 报告回滚成功，释放全局锁。

#### 【连环追问 & 深度考核】
- **面试官追问**：Seata AT 模式中，如果有人直接在数据库手工执行 `UPDATE` 改了这行数据，二阶段回滚会发生什么？
  - **回答**：会发生**脏写（Dirty Write）**校验失败！RM 在二阶段回滚时会对比数据库当前值与后镜像，发现当前值 $\neq$ 后镜像值，说明数据已经被外部脏写，无法自动逆向还原。此时 Seata 会停止自动回滚，打印错误报警日志，并通过钉钉/企业微信或人工干预平台报警，由运维或开发人工介入处理。这也是为什么重要业务库必须严格收口应用权限，禁止直连生产库手动修改数据。

### ❓面试官提问 3.2：在高并发下单场景下，库存扣减是如何防止超卖的？（数据库原子更新）

#### 【结合项目代码回答】
在我们的 [`ItemMapper.java`](file:///c:/Users/35998/Desktop/job/project/hmall/item-service/src/main/java/com/hmall/item/mapper/ItemMapper.java#L19) 中，库存扣减的 SQL 为：
```sql
UPDATE item SET stock = stock - #{num} WHERE id = #{itemId}
```
在 [`ItemServiceImpl.java`](file:///c:/Users/35998/Desktop/job/project/hmall/item-service/src/main/java/com/hmall/item/service/impl/ItemServiceImpl.java#L30) 中，采用 `executeBatch` 批量执行更新。

#### 【基础知识剖析】
- **为什么不能用 Java 代码判断库存**：
  - 错误写法：“`Item item = itemMapper.selectById(id); if(item.getStock() >= num) { item.setStock(item.getStock() - num); itemMapper.updateById(item); }`”。
  - 这种“先读再写”在并发下存在典型的 **Check-Then-Act（检查后行动）** 竞态条件：两个线程同时查到库存为 1，都判断满足条件，都扣减写入为 0，实际卖出 2 件，引发超卖。
- **数据库原子更新原理**：
  - MySQL InnoDB 存储引擎在执行 `UPDATE` 语句时，会自动对命中索引的行加上**行级排他锁（X锁，Record Lock）**。
  - 所有对该商品的扣减更新操作在行锁上强制**串行化**执行，利用数据库自身的原子性保证计算正确。

#### 【坑点深挖与面试亮点】
- **面试官挖坑**：我看你代码里的 SQL 只是 `WHERE id = #{itemId}`，并没有带 `AND stock >= #{num}`，万一库存只有 2 件，用户买了 3 件，数据库会不会扣成负数？
  - **回答**：
    1. **结合项目代码现状**：在当前项目中，MySQL 的 `stock` 字段设计为 `INT UNSIGNED`（无符号整数）。当扣减后结果小于 0 时，MySQL 引擎会抛出异常：`Data truncation: Out of range value for column 'stock'`。在 `ItemServiceImpl.deductStock` 中有 `try...catch (Exception e)` 捕获了该 DB 异常并包装抛出 `BizIllegalException("更新库存异常，可能是库存不足!")`，上层事务感知到异常从而回滚。
    2. **工程最佳实践优化**：依赖无符号异常并非最佳写法，更优雅、通用的做法是**在 SQL 显式增加库存防超卖条件**：
       ```sql
       UPDATE item SET stock = stock - #{num} 
       WHERE id = #{itemId} AND stock >= #{num}
       ```
       在 Service 层判断更新受影响行数 `rows`：若 `rows == 0`，说明行存在但库存不足，直接抛出 `BizIllegalException("库存不足")`，既语义明确，又避免了数据库抛出底层的截断异常。
- **面试官追问**：双十一大促秒杀几万 QPS 冲向同一个热门商品，全部打在 MySQL 同一行锁上排队，会导致什么后果？你们该如何优化？
  - **回答**：会引发**行锁严重竞争、线程池耗尽、数据库连接池排队打满**，拖垮整个商品库。
  - **进阶架构演进**：
    1. **Redis 预扣减 + Lua 脚本**：秒杀前将库存预热到 Redis。用户下单时，通过执行一段原子 Lua 脚本先校验并预扣 Redis 库存，拦截 99% 以上的超额无效流量。
    2. **MQ 异步削峰**：Redis 预扣成功后，投递消息到 RabbitMQ，后端以数据库可承受的恒定速率消费消息，异步批量扣减 MySQL 最终库存并落库订单。
    3. **库存分桶（Sub-Stock）**：若必须强依赖数据库，可将 1000 个库存拆分为 10 个子批次（如 10 个 slot，每个 slot 100 个），下单时根据用户 ID Hash 路由到不同 slot 扣减，将单点热点锁竞争分散为 10 倍并发。

# 第四轮：支付与异步解耦

### ❓面试官提问 4.1：用户点击支付时，支付服务的幂等性是如何保证的？

#### 【基础知识剖析】
- **什么是幂等性（Idempotence）**：一个操作无论执行一次还是多次，其产生的业务结果与状态都是相同的，不会因为重复请求导致重复扣款、生成多笔单据。
- **支付幂等场景**：
  1. 用户在前端连续快速点击“立即付款”；
  2. 网络抖动导致客户端重试；
  3. 用户申请了支付单但未付款，随后返回重新选择使用“微信”换成了“支付宝”。

#### 【结合项目代码回答】
在我们的 [`PayOrderServiceImpl.checkIdempotent`](file:///c:/Users/35998/Desktop/job/project/hmall/pay-service/src/main/java/com/hmall/pay/service/impl/PayOrderServiceImpl.java#L95) 中，基于业务订单号（`bizOrderNo`）实现了精细的状态机幂等校验：

```java
private PayOrder checkIdempotent(PayApplyDTO applyDTO) {
    // 1. 根据业务订单号查询已有支付单
    PayOrder oldOrder = queryByBizOrderNo(applyDTO.getBizOrderNo());
    // 2. 第一次申请：创建新单并设置 WAIT_BUYER_PAY 状态落库
    if (oldOrder == null) {
        PayOrder payOrder = buildPayOrder(applyDTO);
        payOrder.setPayOrderNo(IdWorker.getId());
        save(payOrder);
        return payOrder;
    }
    // 3. 已支付成功：抛出异常阻断
    if (PayStatus.TRADE_SUCCESS.equalsValue(oldOrder.getStatus())) {
        throw new BizIllegalException("订单已经支付！");
    }
    // 4. 已关闭：抛出异常阻断
    if (PayStatus.TRADE_CLOSED.equalsValue(oldOrder.getStatus())) {
        throw new BizIllegalException("订单已关闭");
    }
    // 5. 渠道变更（如微信换支付宝）：重置原支付单渠道信息，更新落库
    if (!StringUtils.equals(oldOrder.getPayChannelCode(), applyDTO.getPayChannelCode())) {
        PayOrder payOrder = buildPayOrder(applyDTO);
        payOrder.setId(oldOrder.getId());
        updateById(payOrder);
        return payOrder;
    }
    // 6. 同一渠道重复点击：直接返回旧单，复用已有支付流水
    return oldOrder;
}
```

### ❓面试官提问 4.2：余额支付成功后，你们代码里标注了“支付状态的乐观锁判断”，请问这个乐观锁是怎么设计的？为什么不用普通的 version 版本号？

#### 【结合项目代码回答】
在 [`PayOrderServiceImpl.markPayOrderSuccess`](file:///c:/Users/35998/Desktop/job/project/hmall/pay-service/src/main/java/com/hmall/pay/service/impl/PayOrderServiceImpl.java#L84) 中：

```java
public boolean markPayOrderSuccess(Long id, LocalDateTime successTime) {
    return lambdaUpdate()
        .set(PayOrder::getStatus, PayStatus.TRADE_SUCCESS.getValue())
        .set(PayOrder::getPaySuccessTime, successTime)
        .eq(PayOrder::getId, id)
        // 关键点：基于前置状态条件的乐观锁判断
        .in(PayOrder::getStatus, PayStatus.NOT_COMMIT.getValue(), PayStatus.WAIT_BUYER_PAY.getValue())
        .update();
}
```

#### 【基础知识剖析】
- **乐观锁思想与状态机条件更新**：
  - 传统的乐观锁是在表里加一个 `version` 列：`WHERE id=#{id} AND version=#{version}`。
  - 但在订单与支付系统中，**订单状态（Status）本身就是天然的、单向递增的状态机（Finite State Machine）**！
  - 合法的流转规则只有一条：`待支付 (WAIT_BUYER_PAY) -> 支付成功 (TRADE_SUCCESS)`。
- **解决的并发痛点**：
  - 在真实的支付场景中，**第三方回调（Webhook）**、**前端轮询查单**、**支付关单定时任务** 可能会在同一毫秒级并发到达；
  - 如果一个请求已经将状态置为 `TRADE_SUCCESS`，第二个并发请求执行该 Update 时，`status IN (1, 2)` 条件不成立，受影响行数为 0，返回 `false`；
  - `PayOrderServiceImpl` 检查 `if (!success) throw new BizIllegalException(...)`，优雅拦截并发更新，保证状态机绝不逆向流转，且不需要引入额外的 `version` 维护字段。

### ❓面试官提问 4.3：支付完成后为什么要用 RabbitMQ 异步通知交易服务？消息发送失败时为什么做日志降级而不是回滚？

#### 【结合项目代码回答】
在 [`PayOrderServiceImpl.tryPayOrderByBalance`](file:///c:/Users/35998/Desktop/job/project/hmall/pay-service/src/main/java/com/hmall/pay/service/impl/PayOrderServiceImpl.java#L75) 中：

```java
} catch (AmqpException e) {
    log.error("发送支付状态通知失败，订单：{}", po.getPayOrderNo(), e);
}
```

#### 【核心设计思想剖析】
1. **为什么要异步解耦，而不是用 OpenFeign 同步调用？**
   - **性能与用户体验**：支付是核心资金流链路，用户在前端付完款后，需要毫秒级得到“支付成功”的明确反馈。如果使用 Feign 同步调用交易服务改订单状态，交易服务可能还要去通知物流、赠送积分、发送短信……导致调用链路极长、延迟极高。
   - **容灾与可用性解耦**：如果交易服务刚好在发布重启、发生网络超时或者 GC 停顿，若采用同步调用，会导致支付事务失败回滚，出现致命体验：“明明扣了用户的钱，前端却提示支付失败”。通过 MQ 解耦，支付服务只管记录资金到账，后续的订单处理由 MQ 缓冲。
2. **为什么消息发送失败仅记录日志降级，而不抛异常回滚？**
   - **资金真实发生**：此时用户的真实余额已经扣减（`userClient.deductMoney`），支付单已经落库成功。若因为消息中间件闪断抛出异常导致支付事务回滚，钱扣了又退，或者发生本地事务回滚但远程扣钱未回滚，会引发极难平账的资金灾难。
   - **最终一致性保证机制**：
     - **第一层防御（日志报警）**：记录 ERROR 日志，可对接日志监控告警；
     - **第二层防御（本地消息表 / 定时任务对账）**：交易服务可设置一个对账定时任务，扫描创建超过 15 分钟仍为“待支付”的订单，主动向支付服务或微信/支付宝轮询查单，若已支付则主动补录订单状态；
     - **第三层防御（生产者可靠投递）**：在发送前将消息落地到 `local_message` 本地消息表，随支付事务一同提交，后台线程不断轮询未 ACK 消息重试投递。

# 第五轮：微服务综合架构与高并发拓展

### ❓面试官提问 5.1：生产环境下 RabbitMQ 如何保证消息“不丢失”且“不重复消费”？

#### 【基础知识剖析】
一笔消息从产生到消费，经历三个环节，每个环节都可能丢消息：
1. **生产者 -> Broker 丢失**：
   - **解决方案**：开启 RabbitMQ 的 **Publisher Confirm（发布确认机制）** 和 **Publisher Returns（退回机制）**。Broker 成功收到消息后向生产者发送 ACK；若路由不可达则触发 returnCallback。
2. **Broker 自身宕机丢失**：
   - **解决方案**：
     - 交换机持久化：`@Exchange(name = "pay.direct", durable = "true")`；
     - 队列持久化：`@Queue(name = "trade.pay.success.queue", durable = "true")`；
     - 消息投递模式设置为持久化（`MessageDeliveryMode.PERSISTENT`，Spring AMQP 默认设置）。
     - 集群采用 **Quorum 队列（Raft 协议强一致性副本）** 或镜像队列（Mirrored Queue）。
3. **Broker -> 消费者丢失**：
   - **解决方案**：将消费者应答模式改为**手动 ACK（`acknowledge-mode: manual`）**。消费者成功完成业务逻辑（订单修改）后才显式调用 `channel.basicAck()`；若发生异常则调用 `basicNack(requeue=false)` 进入死信队列（DLX），绝不能在收到消息的第一时间自动 ACK。
4. **消费端幂等性（防重复消费）**：
   - 消息重复是不可避免的（网络抖动重发、ACK 丢失等）。消费端保证幂等的两大利器：
     1. **业务状态机天然防重**：如 `UPDATE order SET status = 2 WHERE id = #{id} AND status = 1`，即使消费 100 次，只有第一次更新行数为 1，其余都为 0。
     2. **Redis 防重表 / 消息去重表**：利用全局唯一消息 ID（`messageId`），以 `SET messageId NX EX 86400` 存入 Redis，若存在则说明已消费直接 ACK 丢弃。

### ❓面试官提问 5.2：Nacos 注册中心和 Eureka、Zookeeper 有什么区别？Nacos 的 AP/CP 模式是如何切换的？

#### 【基础知识剖析】
- **CAP 定理回顾**：
  - **C (Consistency)**：强一致性；
  - **A (Availability)**：高可用性；
  - **P (Partition Tolerance)**：分区容错性。在分布式网络中，P 是必然存在的，因此系统只能在 AP 与 CP 之间二选一。
- **组件对比**：
  | 特性 | Nacos | Eureka (已停更) | Zookeeper |
  | :--- | :--- | :--- | :--- |
  | **CAP 模式** | **支持 AP 和 CP 动态切换** | 纯 AP | 纯 CP |
  | **健康检查** | 临时实例（心跳）+ 持久实例（服务端探测）| 客户端心跳 | TCP 长连接与临时节点会话 |
  | **负载均衡** | 支持权重、机房就近路由 | 不支持权重 | 不支持 |
  | **配置中心** | **集成一体化（支持动态刷新）** | 无（需搭配 Spring Cloud Config）| 无（仅作为协调存储） |
  | **长连接** | 2.x 基于 gRPC 长连接 | 基于 HTTP 短轮询 | 基于 TCP ZK 连接 |
- **Nacos 的 AP / CP 切换机制**：
  - 默认情况下，Nacos 针对**临时实例（ephemeral=true）**采用 **AP 模式（Distro 协议）**。各个 Nacos 节点之间平权无主，数据异步同步，哪怕网络分区，客户端依然能向可用节点注册或拉取服务列表，保证高可用。
  - 对于**持久化实例（ephemeral=false，如 MySQL、Redis 等有状态服务注册）**，Nacos 自动切换为 **CP 模式（JRaft 协议）**。如果半数以上节点不可达，拒绝写入，以保证强一致性。
  - 切换方式：在注册实例的元数据或配置文件中配置 `spring.cloud.nacos.discovery.ephemeral: false`，或者通过 Nacos OpenAPI 切换。

### ❓面试官提问 5.3：如果微服务集群某个下游服务（如商品服务）挂了，如何防止“微服务雪崩效应”？

#### 【基础知识剖析】
- **雪崩效应产生链条**：
  下游服务变慢/崩溃 -> 上游服务请求阻塞，等待超时 -> 上游线程池打满，无法响应其他正常接口 -> 级联导致整个调用拓扑链条上的所有微服务全部挂掉。
- **三道防线**：
  1. **超时控制（Timeout）**：为 OpenFeign 和 HTTP 客户端设置合理且激进的连接超时（`connectTimeout: 1000ms`）与读取超时（`readTimeout: 2000ms`），避免线程长时间挂起。
  2. **舱壁隔离（线程池隔离 / 信号量隔离）**：限制调用某一个远程服务所能占用的最大并发线程数（如 Sentinel 的线程并发数限制），就算商品服务拖死 10 个线程，也不会影响用户服务或购物车服务的使用。
  3. **熔断降级（Circuit Breaker）**：引入 **Sentinel** 或 **Resilience4j**。
     - **熔断器三态转换**：
       - **Closed（闭合）**：正常放行所有请求；
       - **Open（开启）**：当失败比例（如慢调用比例超过 50%，或异常比例超过 20%）达到阈值，熔断器打开，后续所有请求**立即被切断，直接执行 Fallback 降级**，给下游留出恢复时间；
       - **Half-Open（半开）**：经过一个熔断时间窗口（如 10 秒）后，允许少量探测请求通过，若成功则恢复为 Closed，若依然失败则重新回到 Open。
