### 一、 整体架构与缓存域划分策略

在你的项目中，不同的数据场景特征差异明显，因此通过枚举划分了不同的存储域：

```
                              ┌───────────────────────────────────────────────┐
                              │               客户端请求 (Web/App)             │
                              └───────────────────────┬───────────────────────┘
                                                      │
                                                      ▼
                                       Spring Cache 注解代理层
                     (@Cacheable / @CacheEvict 指定 cacheManager & value)
                                      ┌───────────────┴───────────────┐
                                      ▼                               ▼
                      【本地缓存 Caffeine】                 【分布式缓存 Redis】
                      caffeineCacheManager                  redisCacheManager
                   (零网络IO / 进程内微秒级访问)             (跨服务共享 / 容纳大文本)
                                      │                               │
        ┌─────────────────────────────┼───────────────┐               │
        │ 首页推荐 (homeBookCache)    │               │               │
        │ 小说详情 (bookInfoCache)    │ 榜单/分类等   │               │
        │ 章节元信息 (bookChapterCache)│               │               │
        └─────────────────────────────────────────────┘               │
                                              ┌───────────────────────┴───────────────┐
                                              │ 章节正文 (bookContentCache, 避免堆OOM)│
                                              │ 用户信息 (userInfoCache, 鉴权共享)    │
                                              │ 作家信息 (authorInfoCache)            │
                                              │ 点击榜 (bookVisitRankCache)           │
                                              └───────────────────────────────────────┘
```

#### 划分原则与依据：
1. **本地内存（Caffeine）**：
   - **特点**：单机直接内存读取（纳秒~微秒级），零序列化/反序列化开销，零网络往返延迟。
   - **适用域**：体积小、高频访问、对极短延迟敏感的元数据（如首页小说推荐、小说分类、小说基本详情、章节目录/元数据、更新榜）。
2. **分布式存储（Redis）**：
   - **特点**：独立内存空间、支持集群分布式共享、避免单机 JVM 堆内存膨胀。
   - **适用域**：
     - **大文本正文（小说内容）**：单章小说通常几千至几万字，若缓存在本地 JVM 堆中极易引起频繁 GC 乃至 OOM，因此推入 Redis；
     - **分布式跨节点共享数据**：用户鉴权信息（SSO 场景）、作家信息、全局点击榜单。

#### 2. 双 CacheManager 动态装配：[`CacheConfig.java`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/core/config/CacheConfig.java)
在 [`CacheConfig.java`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/core/config/CacheConfig.java) 中，Spring 容器初始化时分别注册了两个 `CacheManager`：

##### (1) Caffeine 本地缓存管理器（`caffeineCacheManager`）
- 加注 `@Primary`，作为默认 CacheManager；
- 遍历 `CacheEnum` 中 `c.isLocal()` 的枚举项；
- 通过 `Caffeine.newBuilder().recordStats().maximumSize(c.getMaxSize())` 限制堆内存大小，并动态配置 `.expireAfterWrite(Duration.ofSeconds(c.getTtl()))`；
- 包装为 `CaffeineCache` 并注入 `SimpleCacheManager`。

##### (2) Redis 分布式缓存管理器（`redisCacheManager`）
- 使用非阻塞无锁写入器：`RedisCacheWriter.nonLockingRedisCacheWriter(connectionFactory)`；
- 统一前缀与防穿透保护：`.disableCachingNullValues().prefixCacheNameWith("Cache::Novel::")`；
- 遍历 `CacheEnum` 中 `c.isRemote()` 的枚举项，为每个特定缓存域独立构建定制的 `RedisCacheConfiguration` 并注入 `entryTtl`；
- **开启事务感知**：`redisCacheManager.setTransactionAware(true)`，确保数据库事务提交后才真正对 Redis 缓存生效，避免事务回滚导致的脏数据；
- 执行 `redisCacheManager.initializeCaches()` 预热初始化。

在启动类 [`NovelApplication.java`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/NovelApplication.java#L20-L37) 添加了 `@EnableCaching`，并在容器启动后的 `commandLineRunner` 中遍历打印所有加载的 CacheManager 及各自管辖的 CacheNames。

### 四、 写操作后主动失效缓存保证一致性（Cache-Aside）

### 五、 项目落地的核心技术亮点与面试/总结话术

1. **按数据特征区分存储域（防 JVM 堆 OOM）**：
   - 没有把所有数据无脑放入 Caffeine，而是把占用内存极大的“小说正文”隔离在 Redis 中，本地 Caffeine 只保留极小体积的元数据和 ID 列表，极大减轻了 JVM 垃圾回收（GC）压力。
2. **差异化 TTL 布局（防缓存雪崩）**：
   - 首页 24 小时、更新榜 1 分钟、新书榜 30 分钟、章节 6 小时、正文 12 小时、小说信息 18 小时，各缓存域 TTL 天然离散，有效避免了大量热点 Key 在同一瞬间集体失效引发的缓存雪崩。
3. **容量边界控制（W-TinyLFU 防内存溢出）**：
   - Caffeine 本地缓存全部配置了基于 Window TinyLFU 算法的 `maximumSize`（例如章节最大 5000，书籍最大 500），保证即使被频繁遍历也不会导致本地内存撑爆。
4. **Spring 事务感知（保证一致性）**：
   - 在 [`CacheConfig.java`](file:///c:/Users/35998/Desktop/job/project/novel/src/main/java/novel/core/config/CacheConfig.java#L86) 中显式配置了 `redisCacheManager.setTransactionAware(true)`，结合业务方法上的 `@Transactional`，避免在数据库事务发生异常回滚时缓存已经执行了淘汰或变更，确保了数据库与缓存状态的一致。
