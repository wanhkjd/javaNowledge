### 1.2 90 秒项目介绍参考

> 这是一个用于微服务开发实践的商城项目，按商品、购物车、用户、交易、支付拆成五个业务服务，由 Gateway 统一入口。我的准备重点是下单和余额支付两条链路：下单时由交易服务查询商品价格、计算金额、保存订单与明细，再调用购物车和库存服务，使用 Seata 管理跨库事务，库存通过带条件的 SQL 原子扣减。
>
> 余额支付不是直接套同一个 Seata 事务，而是使用支付单行锁、业务订单唯一约束和用户侧扣款流水分别控制不同层次的重复请求。支付状态与通知记录在支付服务的同一个本地事务里提交，再通过 RabbitMQ 通知交易服务；对远程扣款成功、本地支付状态未更新的情况，通过流水对账补偿。
>
> 这个项目让我重点理解了：RPC 超时不等于业务失败，MQ 重投需要消费端幂等，而锁只能覆盖明确的事务边界。目前也有待完善的异常窗口，比如扣款结果未知时的关单协调，以及消息 return 与 confirm 的联合判断。

## 二、下单与分布式事务：必会的 8 道题

### Q1：从点击下单到返回订单 ID，完整流程是什么？

#### 面试时可以这样回答

> 当前项目由交易服务编排下单。首先接收商品 ID 和数量，把重复商品的数量合并；然后通过 Feign 批量查询商品，检查商品是否存在，使用服务端查询到的单价计算应付金额，而不是直接相信前端传来的总价。接着保存订单主表和订单明细，订单记录用户、金额与状态，明细保留商品名称、规格、单价等快照。
>
> 数据保存后，调用购物车服务清理对应商品，再调用商品服务扣库存。下单入口使用 Seata 的全局事务，库存不足或远程写调用失败时抛出异常，让符合接入条件的数据库分支回滚。最后发送延迟检查消息，后续检查订单是否支付，未支付则尝试关单。需要注意，延迟消息本身不属于 Seata AT 的数据库事务，我不会把它说成已经与订单原子提交。

#### 为什么这样设计

1. **服务端计价**防止客户端把高价商品改成低价；但服务端查询可能来自缓存，所以严格的价格版本一致性仍需要额外设计。
2. **订单明细快照**固定成交时的信息，不能在展示历史订单时完全依赖商品当前名称和价格。
3. **先创建待支付订单、再支付**把交易内容和资金动作分离，允许超时关闭、重新查询支付结果等后续流程。
4. **异常必须向上传播**，否则上层可能把库存失败误认为整个下单成功。

#### 追问与详细答案

**问：重复提交下单会不会重复生成订单？** 目前普通下单没有看到独立的请求幂等键，因此支付幂等不能避免创建两张不同订单。可以让客户端提交稳定的请求号，数据库对“用户 ID＋请求号”建立唯一约束，重复请求返回同一业务订单；还要核对重复请求的商品和金额等参数，防止同号不同请求被错误复用。

**问：负数数量、空明细和金额溢出在哪里处理？** 商品服务已有非正数校验，但交易入口仍应先校验集合非空、数量范围和商品 ID，再做数量合并及金额计算。当前用 Integer 累加/乘法可能溢出，改进可用 long 配合 Math.addExact / Math.multiplyExact 及业务金额上限。不能只依赖后面的库存服务兜底。

### Q2：为什么一个 @Transactional 不够？

#### 面试时可以这样回答

> @Transactional 通常只能控制当前服务、当前事务管理器对应的数据源。例如交易服务保存订单后，远程商品服务已经扣库存并提交，这时交易服务再抛异常，自己的本地回滚并不能撤销商品服务的提交。HTTP 或 Feign 请求本身不会把 JDBC 事务自动延伸到另一台服务。
>
> 因此当前下单入口用了 @GlobalTransactional，由 Seata 把交易、购物车、商品服务中的数据库操作作为全局事务分支进行协调。不过注解只是入口条件，真正生效还依赖数据源代理、XID 跨服务传播、TC 和事务分组配置，以及各分支数据库的 undo_log 等。项目源码有这些服务的依赖及共享配置引用，运行环境是否完整生效仍要通过实际回滚实验验证。

#### 本地事务与全局事务的关系

- **本地事务**负责一个分支内部的原子性。例如一次请求扣多个商品，第二个商品失败，前一个商品的扣减要在本地回滚。
- **全局事务**负责跨分支协调。例如商品扣减失败后，还需要撤销交易服务已经保存的订单和购物车服务已经执行的删除。
- 全局事务不等于各服务共用一个数据库 Connection，也不等于取消本地事务。

#### 追问与详细答案

**问：只给远程服务也加 @Transactional，可以吗？** 不行。那只会产生几个独立的本地事务，没有统一协调者知道哪些分支需要一起提交或撤销。

**问：只要加了 Seata，所有动作都能回滚吗？** 不能。AT 主要对接入代理的、受支持的数据库操作进行补偿；普通 MQ 发送、Redis 修改和外部支付动作不自动生成数据库 undo_log，需要独立保证一致性。

**问：怎样证明配置生效？** 让下单在库存环节稳定失败，检查订单、明细、购物车及库存最终状态；同时核对上下游 XID、分支注册及回滚日志。测试不仅看接口报错，还要看所有业务不变量是否恢复。

### Q3：Seata AT 模式的一阶段、二阶段分别做什么？

#### 面试时可以这样回答

> Seata AT 可以理解为在数据库本地事务基础上加入全局协调和自动补偿。TM 是事务发起和结束方，TC 负责全局事务状态及分支协调，RM 负责实际数据库分支。下单进入全局事务后，各服务通过代理数据源执行 SQL。
>
> 一阶段会记录数据修改前后的镜像，生成 undo_log，并把业务数据与 undo_log 一起在本地事务中提交，同时完成相应的分支注册和全局锁管理。全局成功时，二阶段主要清理 undo_log 等资源；全局失败时，RM 根据 undo_log 检查并恢复数据。它的特点是分支的一阶段本地事务可以已经提交，不是所有数据库都一直等到最后才提交。

#### 用库存例子理解

假设库存原来 10，订单 A 扣 2，一阶段数据库变为 8，并保留相应回滚信息。如果后续分支失败，Seata 根据回滚信息尝试恢复为 10。恢复前需要检查当前数据是否符合预期；如果有不受协调的外部修改，不能盲目覆盖，否则可能把其它合法修改抹掉。

#### 追问与详细答案

**问：本地锁和全局锁分别干什么？** 数据库本地锁负责本地事务中的并发控制；一阶段提交后本地锁可以释放。Seata 全局锁用于协调参与全局事务的写操作，避免前一个全局事务尚未结束时，另一个参与者随意修改同一资源。它们处于不同层次，不能把全局锁等同于 Redis 锁。

**问：有全局锁，普通查询是不是就看不到中间状态？** 不一定。普通查询并不会自动因为 Seata 的全局锁而等待全局事务结束。AT 的读隔离有使用条件，不能宣称所有普通 SELECT 都获得跨服务串行化隔离。

**问：有什么成本？** 增加镜像查询、undo_log 写入、协调通信以及全局锁竞争；慢 RPC 会拉长全局事务。并且异常回滚可能需要重试和人工处理，所以我会控制事务范围，而不是把非核心操作无限塞进全局事务。

### Q4：XID 怎么跨 Feign 传递？与 user-info 有什么不同？

#### 面试时可以这样回答

> XID 是 Seata 用于标识同一个全局事务的 ID。交易服务发起全局事务后，调用商品、购物车服务时，需要通过 Seata 与 Feign 的集成把这个 XID 放到调用上下文中传到下游。下游接收后绑定全局事务上下文，数据库分支才能向 TC 注册到同一个事务中；请求结束时也要清理上下文，避免线程复用导致串事务。
>
> user-info 则是另一条链路：它是项目自定义的用户身份头，由自己的 Feign RequestInterceptor 从 UserContext 读取并写入。XID 回答“这次数据库操作属于哪个事务”，user-info 回答“当前业务操作对应哪个用户”。用户身份传到了下游，并不代表全局事务也已经传过去。

#### 追问与详细答案

**问：如果下游没有接收到 XID，会发生什么？** 即使下游本地事务执行成功，它也可能没有作为预期的全局分支加入事务。上游失败后，不能指望这次独立本地提交自动被全局回滚。因此要排查传播和数据源代理，而不是只看下游接口是否成功。

**问：如何排查传播问题？** 在真实请求中比较交易服务与下游 RootContext 中的 XID，结合 TC 分支日志，确认一次业务调用对应同一个全局事务。记录时注意日志关联，不应随意把所有请求头或敏感数据打出来。

**问：换成异步线程后会自动传递吗？** 不能默认会。线程上下文与远程请求上下文都需要对应的传播机制，而且异步任务还可能晚于原全局事务结束。不能简单复制一个 XID 就认为延后执行的任务能安全加入已结束事务，应重新设计事务边界。

### Q5：原子扣库存为什么能防止超卖？

#### 面试时可以这样回答

> 项目不是先读库存再在 Java 里减，而是通过一条带条件的 UPDATE 把“库存够不够”和“扣库存”合并成数据库原子操作。SQL 同时要求商品上架、库存大于等于本次购买数量，执行后检查影响行数；不是 1 就抛异常。前提是购买数量必须为正数，项目在商品服务进行了校验。
>
> 例如库存为 1，两个请求都想购买 1 件，同一库存行的并发 UPDATE 会经过数据库锁协调。一个请求成功扣为 0 后，另一个请求不能再以旧库存为依据成功扣减，而会因为条件不满足更新 0 行。因此不会把库存扣成负数。

~~~sql
-- 示意 SQL，实际 Mapper 使用 MyBatis 参数绑定
UPDATE item
SET stock = stock - :num
WHERE id = :itemId AND status = 1 AND stock >= :num;
~~~

#### 追问与详细答案

**问：先查后扣有什么问题？** 两个请求可能都查到库存 1，再各自认为有货。即使最终覆盖写后库存仍是 0，也可能生成两笔有效销售，因此超卖不一定表现为库存出现负数。

**问：这是不是无锁 CAS？** 可以把条件更新理解为类似 compare-and-set 的业务判定，但底层仍然依赖 InnoDB 的并发控制和行锁，不是没有锁开销。也不能把它和 Java CPU 层面的 CAS 混为一谈。

**问：为什么判断影响行数？** 语句执行没有抛数据库异常，不代表业务扣减成功；库存不足、商品下架、商品不存在都会使 WHERE 不匹配。必须用影响行数把这些情况转成业务失败。

**问：负数为什么危险？** stock - (-2) 等于加 2。只写 stock >= num 无法挡住负数，因此数量校验是这条 SQL 正确性的必要前提。

### Q6：一次买多个商品，扣了一半失败怎么办？会不会死锁？

#### 面试时可以这样回答

> 商品服务的 deductStock 方法有本地事务，它遍历订单商品，逐个执行条件扣减，任何一条影响行数不符合预期就抛运行时异常。比如 A 商品扣减成功，但 B 库存不足，本地事务会撤销 A 的扣减；异常继续传给交易服务，触发 Seata 对其它已参与分支的回滚。
>
> 多商品也可能出现死锁。比如订单一按 A、B 更新，订单二按 B、A 更新，双方各持有一行锁后等待另一行，就可能形成循环等待。数据库会检测某些死锁并回滚选中的事务，应用必须正确处理失败。

#### 追问与详细答案

**问：怎样减少死锁？** 先把重复商品合并，再按商品 ID 的固定顺序扣减，减少不同请求锁顺序不一致；控制单笔商品数量、缩短事务内操作时间，并确保查询更新走合理索引。固定顺序能减少这类死锁，不保证消除所有系统死锁。

**问：死锁直接重试某一条 UPDATE 可以吗？** 通常应重试被回滚的完整业务事务，而不是只重放一个不确定处于何种状态的 SQL。并且要区分死锁、库存不足和网络结果未知，只对允许重试的错误做有限重试，并保证创建订单等副作用具有幂等设计。

**问：循环更新改成批量 SQL 就解决了吗？** 批量可以减少数据库往返，但不自动解决锁顺序、业务条件判定和部分失败处理。要能确认每个商品都满足条件，不能只看到批处理没报异常就认为都扣成功。

### Q7：购物车清理必须放进强一致事务吗？

#### 面试时可以这样回答

> 不一定必须。当前实现把清理购物车放在下单全局事务中，目的是下单失败时，购物车删除也能随数据库分支一起回滚，用户仍能看到原购物车内容。这种实现比较直观，也适合练习跨服务事务。
>
> 但从业务重要性看，订单和库存直接关系到成交，而购物车短暂保留已经购买的商品通常可以容忍。因此另一种设计是订单成功后异步清理购物车，清理失败再重试。这样能减少下单主链路的同步依赖和事务范围，不过要接受短暂不一致，并处理消息重复、用户重新加购等问题。

#### 追问与详细答案

**问：异步清理直接按商品 ID 删除可以吗？** 不一定。假设下单后用户又把同一商品加进购物车，迟到的清理消息如果按商品 ID 无条件删除，可能删掉新加入的数据。需要携带购物车项 ID、版本或本次下单对应的数量/快照，明确只清理本次成交所对应的状态。

**问：清理失败会导致下单失败吗？** 当前同步方案会把调用失败作为主链路失败的一部分；异步方案则通常不撤销已成功订单，而是记录并补偿购物车清理。二者是业务取舍，不能同时承诺“完全解耦”和“任何购物车失败都立即回滚订单”。

**问：你项目已经改成异步了吗？** 没有，当前普通下单仍是同步调用购物车服务；异步清理是我能解释取舍的改进方案，不冒充已完成工作。

### Q8：@GlobalTransactional 能保证延迟关单消息与订单原子提交吗？

#### 面试时可以这样回答

> 不能。@GlobalTransactional 对接入 Seata 的数据库分支进行协调，而当前 RabbitTemplate 的普通消息发送没有自动变成 AT 数据库分支。createOrder 方法内调用发送成功，只能说明发送链路完成到了某个阶段，不代表订单全局事务已经与消息共同原子提交。
>
> 当前消费者查询不到订单会直接返回，能减轻部分无效消息的影响，但不能据此证明消息可靠性已经完整解决。我会把延迟检查消息作为触发机制，再增加数据库到期未支付订单的扫描兜底；如果要采用事件表，也要保证只在全局结果确定后发布对应事件，而不是仅依赖某个分支的本地提交。

#### 具体失败窗口

- 消息已经发出，后面全局提交失败：消息存在，订单可能回滚。
- 某次发送抛异常但 Broker 实际已收到：消息可能残留，后续也可能重复。
- 订单最终存在，但延迟消息没能可靠保留或处理：订单可能不能按时关闭。

#### 追问与详细答案

**问：在交易服务加一个 afterCommit 就够吗？** 先要分清它监听的是哪个事务。Seata AT 分支本地提交不代表全局事务最终成功。如果事件在分支提交时就被发布，仍可能早于全局结果。应使用与全局完成结果协调的机制，并为异常恢复保留持久化依据。

**问：订单扫描如何做？** 按未支付状态和过期时间建立查询条件及合适索引，分批取到期订单，再调用具有幂等和资金结果协调能力的关单流程。扫描不能另写一套无条件改状态、回库存的逻辑，否则会绕开支付安全检查。

**问：延迟多久？** 源码默认值和配置覆盖要区分：普通订单配置当前是演示用 120000 毫秒，即 2 分钟，不应把生产建议时长说成当前实际配置。

## 三、余额支付与幂等：最值得讲透的 9 道题

### Q9：为什么要把业务订单、支付单、扣款流水分开？

#### 面试时可以这样回答

> 三者分别描述交易、支付和资金动作，不应该混在一张状态表里。业务订单记录买了什么、买了多少、应付金额以及履约状态；支付单记录这笔订单的支付渠道、支付状态和支付关联信息；扣款流水记录用户服务实际执行过的资金扣减，供幂等和对账使用。
>
> 这样拆分后，即使支付服务没有拿到成功响应，也可以根据用户侧的已提交流水判断资金是否实际扣过，而不是只相信支付单目前的状态。当前实现通过业务订单号唯一约束限制同一业务订单只生成一张支付单，用支付单主键作为用户侧扣款流水的幂等键。

#### ID 与状态必须讲清

- **业务订单 ID / biz_order_no**：连接交易订单与支付单。
- **支付单主键 id**：余额扣款接口传入的 pay_order_id，也是扣款幂等键。
- **pay_order_no**：另外生成的支付单号，当前不能和数据库主键混用。
- **pay_message.id**：消息投递与确认关联键，不是资金扣减依据。
- 业务订单和支付单的状态值也不相同：当前业务订单未支付为 1、已支付为 2、关闭为 5；支付单成功判断使用支付枚举，不能直接套业务订单数字。

#### 追问与详细答案

**问：以后要支持一个订单多次支付尝试怎么办？** 当前“一业务订单一支付单”的模型需要扩展。可以区分支付意图与支付尝试，每次渠道请求有独立尝试号，但业务订单只能有符合规则的有效成功结果；重复扣款、迟到成功和退款仍需以资金记录核对。不能直接删掉唯一约束却不补新的状态控制。

**问：为什么流水不能只写日志文件？** 应用日志不具备与余额修改的同库事务约束，也不是可靠的唯一键竞争机制。数据库流水才能在当前方案里与余额一起提交、一起回滚，并接受唯一约束保护。

### Q10：一句“保证幂等”到底在哪几层实现？

#### 面试时可以这样回答

> 我不是用一个锁解决全部幂等，而是分层控制。申请支付单时，先查业务订单关联的支付单，数据库再用 biz_order_no 唯一索引挡住并发创建；执行支付时，用支付单行锁串行检查状态；真正扣余额时，用户服务用 pay_order_id 唯一的流水防止重复扣款；最后支付状态和交易订单状态都使用带原状态条件的更新，防止重复推进。
>
> 每一层对应不同的重复来源。唯一索引解决“两个请求都先查到不存在”，行锁解决正常并发付款，流水解决远程扣款成功后本地回滚再重试，状态条件更新解决消息重投或补偿与正常请求重叠。它们不能简单互相替代。

#### 一个完整例子

同一订单两个请求同时申请支付：两者可能都先查不到，但只有一个能插入满足唯一约束的支付单，另一个捕获重复键后查询已有记录。之后两个付款请求来到同一个支付单，后来的请求等待行锁；若前一个本地提交成功，后一个看到已支付状态，不再扣款。若前一个在远程扣款后本地失败，第二个虽然还能进入扣款调用，用户侧流水仍会阻止第二次资金扣减。

#### 追问与详细答案

**问：只先查询有没有记录，不建唯一索引行不行？** 不行。查询和插入之间有并发窗口，两个线程都可以看到不存在。需要数据库约束或其它覆盖该窗口的并发机制，当前选择唯一索引作为最后防线。

**问：有支付幂等，就没有重复订单吗？** 不是。两个不同业务订单会对应不同支付幂等键，仍可能各扣一次。创建订单幂等和支付幂等是两个问题。

**问：只要 SQL 文件里有唯一索引就算完成吗？** 不算，必须确认数据库已迁移成功，且历史重复数据经过清理。源码核对只能证明设计和迁移脚本存在，不能证明目标环境约束已经生效。

### Q11：为什么支付服务有行锁，用户服务还需要扣款流水？

#### 面试时可以这样回答

> 行锁能保证同一支付单的并发请求在本地事务中排队，但不能保证跨服务调用只执行一次。最典型的情况是：支付服务持锁调用用户服务，用户服务已经扣款并提交，可支付服务在更新支付单前宕机。支付服务本地事务回滚后，支付单仍然待支付，锁也会释放，用户重试就会再次调用扣款。
>
> 因此我在用户服务保存扣款流水，以支付单 ID 建唯一约束，并让流水与余额扣减同事务提交。第二次请求即使真的到达用户服务，也会因为唯一流水已存在而不再执行扣款。行锁负责当前并发，流水负责跨请求、跨故障恢复的持久化幂等。

#### 为什么换 Redis 锁也不能单独解决

把行锁换成分布式锁，仍无法回答“之前那次远程请求到底扣过钱没有”。锁可能释放、过期或随进程故障失去持有者，它不是资金结果的持久化记录。除非还配套持久化结果、严格的状态协议等机制，否则只是换了互斥工具，没有解决重复资金动作。

#### 追问与详细答案

**问：两个不同支付单同时扣一个用户的钱，支付单锁还有用吗？** 它们锁的是不同支付单，互不阻塞。同一账户余额的正确性最终由用户服务那一行余额的条件 UPDATE 和本地事务保证。

**问：行锁什么时候释放？** 随当前数据库事务提交或回滚释放，不是查完 FOR UPDATE 立即释放。当前余额支付方法有 @Transactional，使锁覆盖校验、RPC 调用和支付状态更新，但 RPC 较慢也会延长持锁时间。

**问：有什么性能风险？** 同支付单的请求排队，长时间持锁还占用数据库连接。应该设置合理调用超时、控制事务时长并观测锁等待；不能为了缩短事务就简单去掉锁而不补状态协调。

### Q12：为什么先写扣款流水，再扣余额？流水存在就一定代表扣款成功吗？

#### 面试时可以这样回答

> 用户服务先校验金额、密码和账户状态，再尝试插入以支付单 ID 为唯一键的扣款流水，随后执行带余额和账户状态条件的扣款 SQL。两步处在同一个本地事务中。如果流水插入成功但余额不足，扣款更新不到记录就抛异常，前面的流水也回滚。
>
> 因此在这段特定实现里，已提交的流水可以作为扣款事务已成功提交的依据。另一个相同支付单请求插入相同唯一键时会发生唯一冲突，当前代码按已扣款处理，不再执行余额扣减。关键不是“先写了流水”这一动作，而是流水与余额必须具有共同提交、共同回滚的约束。

#### 并发时序

A 插入流水后尚未提交，B 插入同一唯一键时由数据库协调冲突。如果 A 最终提交成功，B 不能再提交第二条相同唯一键记录；如果 A 回滚，后续请求才可能获得这次扣款的执行资格。不能把未提交流水当成其它请求已经能可靠观察到的成功结果。

#### 追问与详细答案

**问：事务中间宕机，会不会留下流水但没扣钱？** 在相同 InnoDB 本地事务的前提下，不应出现“仅流水已提交、余额未提交”的半提交结果；进程宕机后由数据库事务恢复处理。若把两步拆成独立事务，这个结论就不成立。

**问：同一个幂等键，第二次传的金额不同怎么办？** 应查询已有流水，对比用户、金额等关键参数，相同才返回原结果，不同应拒绝并记录冲突。当前重复键分支直接返回，缺少这层参数一致性校验，不能声称已完整处理同号不同请求。

**问：先扣余额再插流水可以吗？** 在同一个本地事务、重复键冲突确保整笔回滚的严格前提下也可能做到原子性，但更容易因异常被捕获处理不当而留下错误效果。当前先竞争唯一流水，再扣余额，幂等分支更直观。

### Q13：余额扣减如何防止扣成负数？为什么还要校验金额为正？

#### 面试时可以这样回答

> 我把账户正常、余额充足和余额扣减放到同一条 SQL 中，而不是只在 Java 里先查余额。SQL 要求用户 ID 匹配、status 为正常、balance 大于等于本次金额，然后执行 balance = balance - amount。影响行数不是 1，就抛异常，让本地流水插入一起回滚。
>
> 同时金额必须大于 0，因为 amount 如果是负数，减法就变成加钱，balance >= amount 也不能阻止它。支付服务实际传给用户服务的金额来自已保存的服务端支付单，而不是直接用客户端临时传来的扣款金额。

~~~sql
UPDATE user
SET balance = balance - :amount
WHERE id = :userId AND status = 1 AND balance >= :amount;
~~~

#### 追问与详细答案

**问：支付前已经查过余额，为何 SQL 还要判断？** 查完后另一个订单可能马上扣款，原查询结果会失效。SQL 条件是执行资金修改当下的最终裁决，前置查询只能用于交互提示，不能作为并发正确性的唯一依据。

**问：为什么 SQL 里还判断账户状态？** 账户可能在初次检查后被冻结。把正常状态作为更新条件，可以按数据库实际更新时的状态进行判断，而不是一直依赖较早读取的 User 对象。

**问：金额为什么用整数分？** 当前金额单位是分，可以避免二进制浮点对十进制金额的表示误差。但整数也有范围限制，单价乘数量、总额累加都需做溢出检查。若涉及折扣、税费和汇率等小数计算，可以使用 BigDecimal 并明确精度与舍入规则，最后转换为合法金额单位。

**问：余额永不为负就是支付正确吗？** 不是，还要满足流水与扣款一致、支付与业务订单状态协调，以及退款等逆向流程正确。余额下限只是其中一个业务不变量。

### Q14：重复支付请求直接报“已支付”，算不算幂等？

#### 面试时可以这样回答

> 幂等首先关注的是重复执行后是否产生重复业务副作用。当前接口如果第一次成功，第二次因为支付单已成功而报“已支付或关闭”，虽然响应不相同，但只要不会再扣钱，就实现了资金动作层面的幂等。更好的 API 体验通常是同一个合法支付请求重试时，已成功则返回原支付结果，让客户端把它当作成功恢复，而不是笼统报错。
>
> 但已经关闭和已经支付是不同状态，不能都按成功返回。请求中的用户和关键参数也要与原操作一致，避免别人的请求借用相同幂等键得到不属于自己的结果。

#### 追问与详细答案

**问：幂等是不是要求每次返回完全相同？** 不必把所有接口一概而论。数学意义强调重复作用不改变最终结果，工程中更需要明确定义副作用和响应契约。支付通常既要确保不重复扣款，也应该提供稳定的结果查询，以便客户端在超时后恢复。

**问：重复请求还要验密码吗？** 当前用户服务在插入流水前进行密码和账户校验，所以重复请求可能因为当前密码/账户状态变化而返回失败，这不代表产生了第二次扣款。是否允许经授权查询原支付结果，应作为独立接口或明确协议设计，而不是依靠再次执行扣款接口猜状态。

**问：前端按钮禁用能不能替代幂等？** 不能。网络重试、多个标签页、自动化调用和消息重投都可以绕过前端交互限制；服务端和数据库必须自己守住副作用边界。

### Q15：支付 RPC 超时，是不是可以当作扣款失败？

#### 面试时可以这样回答

> 不能，RPC 超时只是调用方没有在规定时间拿到结果，不是远程事务一定失败。请求可能根本没执行，也可能执行失败，还可能用户服务已经扣款成功，只是响应在网络中丢失。因此支付服务不能一超时就认定未扣款，更不能换一个新的幂等键重新扣款。
>
> 当前设计依靠原支付单 ID 做幂等重试，并通过用户侧流水查询核实结果。如果实际已扣款，重复调用不会再减余额；对账任务也可以补齐仍待支付的支付单并补发通知。但关单与结果未知交错的情况还需要更完整的状态机，这也是当前边界。

#### 结果恢复流程

1. 客户端收到超时，先展示处理中或待确认，而非立即宣布支付失败。
2. 保持原业务关联和幂等键，查询支付结果。
3. 系统通过已提交的扣款流水确认资金动作。
4. 补齐支付状态并通知交易服务，或者确认未执行后按协议重试。
5. 如果资金成功但业务订单已关闭，进入明确的异常补偿/退款流程，而不是忽略。

#### 追问与详细答案

**问：查不到流水就能立即关单吗？** 不一定。原远程请求可能还在执行，查询时没有流水，之后才提交。要么协调请求执行状态，要么有可靠处理迟到扣款的后续补偿，不能把单次“查不到”当成永久不会扣款。

**问：把超时时间调大不就好了？** 调大只能降低部分误超时概率，不能消除进程宕机、响应丢失和网络分区，还会延长持锁与连接占用。正确性来自幂等与状态恢复，不来自无限等待。

### Q16：为什么下单用 Seata，余额支付却用本地事务和补偿？

#### 面试时可以这样回答

> 当前项目实际上用了两种一致性处理方式。下单的订单、购物车、库存数据库修改通过 Seata 协调；余额支付没有把用户和支付服务纳入同一 Seata 事务，而是各自维护本地事务，再用流水幂等、可靠通知和对账处理跨服务差异。
>
> 支付时用户服务保证“写流水和减余额”一起提交，支付服务保证“支付状态和待发送通知”一起提交。它们之间仍有失败窗口，所以需要凭流水恢复状态，而不能假设支付服务回滚会撤销用户扣款。这种设计能明确处理远程调用结果未知，但也把异常状态、对账和逆向补偿的责任交给业务代码。

#### 方案比较

- **Seata AT**：业务改造相对集中，适合当前支持的数据库操作，但需要协调器、代理、undo_log 和全局锁，跨服务慢调用会增加事务成本。
- **本地事务＋补偿**：各服务提交边界清晰，适合异步通知，但短暂不一致是设计的一部分，必须定义失败恢复、超时、退款和人工介入路径。
- 不应把当前余额扣减直接称为“完整 TCC”：它没有展示规范的 Try/Confirm/Cancel 资金预留协议。

#### 追问与详细答案

**问：支付能不能也用 Seata？** 技术上并非绝对不能，特别是完全受控的数据库余额操作，但仍需考虑吞吐、锁竞争、故障模型及外部支付渠道是否可参与。外部渠道的真实扣款通常不能仅靠本地数据库 undo 恢复。

**问：补偿是不是保证最终一定一致？** 只有在补偿覆盖所有必要状态、任务能持续处理、失败有人处置等前提下才能讨论最终收敛。当前待支付对账是主要路径，不代表已完成所有资金异常闭环。

### Q17：扣款成功、支付单没更新，当前对账如何恢复？

#### 面试时可以这样回答

> 当前 PayReconcileTask 默认每 30 秒执行，筛选余额支付、仍待支付且更新时间超过 1 分钟的支付单，每批最多 100 条。逐条按支付单 ID 查询用户服务是否存在已提交扣款流水。如果没有就暂不标成功；如果有，则通过带原状态条件的更新补齐支付成功，并在同一个支付本地事务中保存通知记录，通知交易服务推进订单。
>
> 使用流水而不是只看接口日志，是因为流水与真实扣款在同一个用户服务事务中提交，可以作为资金已经执行的依据。更新时间阈值主要减少与刚发起支付的请求竞争，不是严格的互斥机制；真正防止重复推进仍靠条件更新与资金幂等。

#### 追问与详细答案

**问：对账和正常支付同时更新怎么办？** 两者对支付单的更新可能发生锁等待或竞争，状态条件确保只能由符合原状态的一方完成推进。正常付款即使再次调用用户服务，也由唯一流水阻止再次扣钱。对账路径没有完全等同于余额支付入口的行锁流程，不能仅用“都加了同一把锁”解释。

**问：LIMIT 100 有什么隐患？** 查询没有稳定推进游标或轮转机制时，前一批始终没有流水的旧待支付单可能反复入选，让后面的异常单长期无法检查。可以引入下次检查时间、稳定排序/游标、分片扫描或认领机制，使处理进度可证明。

**问：支付单已关闭但实际扣过款，能修吗？** 当前任务不扫描已关闭状态，更新成功的方法也不直接接受关闭状态，所以不能承诺自动修复。需要增加资金与终态冲突核查，并根据库存和履约状态决定退款等处理，而不是简单把已关闭订单改成已支付。

**问：多实例怎么办？** 条件更新能限制重复状态推进，但不避免重复查询和扫描成本；生产化需要任务分工、认领超时回收、扫描延迟监控和单笔失败隔离。

## 四、RabbitMQ 与可靠通知：7 道高频题

### Q18：为什么只在 afterCommit 发 MQ 还不够？

#### 面试时可以这样回答

> afterCommit 解决的是消息发送时机：数据库没有成功提交之前，不要让消费者先处理一个尚未成立的业务结果。但如果数据库刚提交，进程还没执行回调就宕机，单靠内存中的 afterCommit 回调没有办法在重启后恢复这个发送任务。
>
> 所以当前支付服务先在本地事务里更新支付状态并插入 pay_message，再注册 afterCommit 尝试发送。支付事务失败，两者一起回滚；支付事务成功，即使回调没执行，数据库里仍有 PENDING 消息，定时任务可以恢复投递。afterCommit 是低延迟的首次投递手段，本地消息记录才是崩溃恢复依据。

#### 四种情况怎么处理

1. **事务提交前失败**：状态与消息记录回滚，不应产生成功通知。
2. **提交后、发送前宕机**：消息表保留 PENDING，重启后扫描。
3. **发送失败或确认未知**：继续保留待处理记录，按策略重试。
4. **Broker 收到但本地确认没落库**：可能重复投递，由消费端幂等处理。

#### 追问与详细答案

**问：消息记录写到另一个数据库可以吗？** 如果没有跨资源事务保证，支付状态提交与记录落库仍可能一成一败，就失去了本地消息表的关键价值。当前强调的是同一支付本地事务中的同库原子提交。

**问：afterCommit 回调里发送失败还能回滚支付吗？** 不能，提交已经发生。此时应该把通知失败作为后续恢复任务处理，而不是让调用方误以为钱一定没扣成功。当前发送方法捕获普通发送异常并等待重试，正是为了区分资金结果与通知结果。

**问：afterCommit 里的数据库操作随原事务提交吗？** 不能这样认为，原事务已提交。若回调还要做需要持久提交的数据库写入，应明确新的事务边界；不要依赖原事务“再提交一次”。当前核心消息记录是在提交前保存，而不是回调里才补写。

### Q19：本地消息表与事务消息、消息中间件事务有什么区别？

#### 面试时可以这样回答

> 本地消息表，也常称 outbox，核心是把业务数据修改和“需要发出某个事件”的记录放进同一个数据库事务。投递器随后把记录发给 MQ，再记录投递结果。它没有让 MySQL 和 RabbitMQ 变成一个原子提交资源，因此还会存在外部发送成功、本地尚未确认的窗口。
>
> RabbitMQ 的通道事务解决的是 Broker 侧的一组消息操作，不能直接与 JDBC 事务组合成一个统一原子事务；发布确认则是异步获知发布结果，也不是数据库事务。其它中间件的半消息、事务回查方案属于不同协议，不能把当前 RabbitMQ 本地消息表包装成已经使用那种事务消息机制。

#### 为什么重复难以彻底消除

投递器先发消息，再改数据库状态：发成功后宕机，重启会重发。反过来先标已发送，再发送：标记后宕机，会永远漏发。两个独立资源之间总有需要处理的失败窗口，因此当前方案倾向于可靠重试，配合接收方业务幂等。

#### 追问与详细答案

**问：这是不是 exactly-once？** 不是消息物理上只投递一次。更准确的表述是：以至少一次处理思路设计重试，通过唯一约束、事务和状态机限制业务效果重复；当前还有重试上限和人工处理边界，不能不加前提地承诺最终自动送达。

**问：消息表里要存什么？** 当前有业务订单号、交换机、路由键、载荷、状态、重试次数和下次重试时间等。扩展时还可考虑事件类型、版本、发生时间与发送尝试标识，以支持协议演进和回调关联，但不能说当前字段已全部具备。

**问：什么时候清理消息表？** 通常按业务审计与排障需求保留成功记录一段时间，再归档或分批清理；失败记录需先处理。不能发出消息后马上删除所有证据，否则无法分析确认异常和人工重放。

### Q20：confirm、return、消费者 ACK 分别证明什么？

#### 面试时可以这样回答

> 这三个确认处在不同环节。publisher confirm 是 Broker 对发布动作给出的确认或拒绝；mandatory return 是消息无法路由到队列时返回给发布者；consumer ACK 是消费者对一条交付消息处理结果的确认。发布确认不等于消费成功，无法路由与业务消费失败也不是同一件事。
>
> 特别容易出错的是：消息到达一个存在的交换机，但没有匹配队列，开启 mandatory 后会收到 return，同时这次发布仍可能收到 ack。因此不能把 ack 无条件等价于目标队列收到了消息。当前代码确实存在 return 安排重试后，ack 又把记录标成 SENT 的窗口，这需要修复联合判断。

#### 具体例子

发布到 pay.direct，routing key 为 pay.success。如果对应绑定不存在：消息没有进入预期队列，return 告诉发布端无法路由；confirm ack 只表示 Broker 按发布协议确认了处理，不能覆盖 return 所代表的失败。若直接标 SENT，重试扫描就漏掉这条真正没送达的通知。

#### 追问与详细答案

**问：怎么修？** 关联同一次发送的 return 与 confirm 结果，只有满足正确的发布/路由条件才标成功。可以结合实际 Spring AMQP 版本支持的 CorrelationData returned 信息或显式尝试状态实现；重试之间最好区分发送尝试，避免旧回调覆盖新结果，并用移除队列绑定的测试验证。

**问：confirm ack 是否一定代表磁盘持久化？** 不能脱离消息持久化属性、目标队列类型、持久化配置和确认语义讨论。持久化队列与持久化消息需要配合；但即使满足发布持久化保障，也不能证明消费者已完成数据库业务。

**问：消费者失败会触发 return 吗？** 不会。return 是路由问题；消费业务失败通过消费异常、确认/拒绝、重试及失败恢复流程处理。

### Q21：消息为什么会重复？消费端怎么处理？

#### 面试时可以这样回答

> 消息可能因确认丢失、发布重试、消费者处理后 ACK 丢失，以及多实例同时扫描消息表而重复。当前支付通知消费端采用状态条件更新，把“判断是否未支付”和“改成已支付”放到同一条数据库 UPDATE 中，只有 status 仍为 1 的业务订单才改成 2。
>
> 这样第一次成功后，后续相同通知不会再次推进状态，也不会重复覆盖支付时间。相比先查状态再无条件更新，条件 UPDATE 把并发判断放到了数据库执行时，避免两个消费者都在查询阶段判断为未支付。

~~~sql
-- order 为实际业务订单表；此处用反引号处理保留字
UPDATE `order`
SET status = 2, pay_time = :now
WHERE id = :orderId AND status = 1;
~~~

#### 追问与详细答案

**问：更新 0 行就是重复消息吗？** 不是，也可能订单不存在、已关闭或处于其它不允许的状态。正常重复成功可以忽略，但支付成功与订单关闭冲突需要对账/补偿。当前代码只记“已处理”的日志，这个分类还不够完整。

**问：为什么不用消息 ID 去重表？** 当前消费者的核心副作用就是这次状态迁移，条件更新比较直接。如果消费还包含多个本地写动作，可以让去重记录与所有副作用在同一事务中提交；如果包含远程副作用，仍需要下游幂等或事件驱动协议，不能靠去重表一劳永逸。

**问：先标消息已消费，再执行业务可以吗？** 如果没有同事务保护，标记后崩溃会导致业务未执行但后续被当成重复跳过。应让去重判定与本地业务结果原子提交，或通过严谨的处理中/完成状态恢复。

### Q22：数据库更新成功、消费确认失败，会不会更新两次？

#### 面试时可以这样回答

> 数据库更新已经提交、消费确认却丢失时，Broker 可能重新交付消息，所以业务代码可能执行第二次，但业务效果不一定发生第二次。当前第二次执行状态条件 UPDATE 时，订单已经不是未支付状态，就不会重复推进。我们防的是重复副作用，而不是幻想消费者方法永远只调用一次。
>
> 相反，如果先确认消息，再提交数据库，确认后进程崩溃就可能使消息不再重投，而业务又没提交，这通常更危险。因此要使消息确认与业务事务的完成顺序相匹配。当前代码使用 Spring AMQP 监听器，没有手写 basicAck，我会说明由容器配置管理确认，而不虚构手动确认实现。

#### 追问与详细答案

**问：监听方法不抛异常就一定正确吗？** 不一定，如果把数据库异常 catch 后只打印日志并正常返回，容器可能认为处理成功。所以可恢复失败通常要向容器传播，交给重试或失败恢复，不能把“日志里记录失败”当成可靠处理。

**问：所有异常都应该重试吗？** 不应无差别无限重试。临时数据库/网络故障可以有限重试；参数非法、格式不兼容或业务终态冲突需要分类处理，避免毒消息持续占用消费者。

**问：数据库提交和 ACK 能完全原子吗？** 一般不属于同一个原子资源提交，仍有提交成功但确认未知的窗口。因此即使精心安排确认时机，也需要幂等和失败恢复，而不是只依靠 ACK 模式。

### Q23：你的重试策略是什么？重试失败怎么办？

#### 面试时可以这样回答

> 当前分发布侧与消费侧两套重试。发布侧把未确认通知保留在本地消息表，默认每 5 秒扫描一次到期 PENDING 记录，每批 100 条；安排重试时增加计数，并指数退避，超过阈值标为 FAILED、记录错误，等待进一步处置。消费侧在交易服务配置了本地重试，最多尝试 3 次，耗尽后由 RepublishMessageRecoverer 把失败消息发往错误交换机与错误队列。
>
> 这两套重试解决不同问题：发布侧针对通知没确认送出，消费侧针对已收到通知但业务处理失败。当前错误队列是应用主动重新发布，不应说成已经配置了基于 DLX 的死信队列。

#### 代码数值需要准确

消息初次落库的 nextRetryTime 大约为当前时间加 5 秒；scheduleRetry 先把计数增加为 nextCount，再计算 5 × 2^nextCount 秒，因此首个这样计算出的延迟为 10 秒，随后可为 20、40、80 秒等。retry_count 达到 6 后会进入失败处理。return/nack 也可能调用该方法，所以计数不是严格的真实发送次数。

#### 追问与详细答案

**问：为什么退避？** 下游故障时立即高频重试会增加压力；逐步拉长间隔有利于恢复。多实例还可加入抖动，减少同时重试，但当前不能宣称已加入随机抖动。

**问：标 FAILED 就算处理完了吗？** 不算。需要能触达人的告警、失败查询、修复后重放及审计，当前主要只有状态记录和日志。若无人处理，不能承诺这条通知最终自动送达。

**问：错误队列会不会自己失败？** 会，它也是一次新的发布，需要验证交换机/队列持久化、发布失败恢复等机制。把消息转到错误队列不是把可靠性问题凭空消掉。

### Q24：多实例扫描会不会重复发送？retry_count 条件更新能彻底解决吗？

#### 面试时可以这样回答

> 会有重复发送的可能。两个支付实例可以同时查到同一条 PENDING 消息，当前 scheduleRetry 用 retry_count 条件更新减少覆盖，但调用方没有根据“这次条件更新是否成功”决定自己是否有资格发送，所以两个实例仍可能都执行 send。
>
> 改进是让消息先被原子认领，比如从待发送改为发送中并记录 owner、租约到期时间，只有认领成功的一方执行发送。若实例崩溃，租约到期后可重新认领。扫描也可以按稳定范围分片，或者根据数据库版本采用跳过已锁行等机制，但都需要处理任务恢复，不能只加一把永不过期的锁。

#### 追问与详细答案

**问：给定时任务加一个全局分布式锁是不是最简单？** 可以减少重复扫描，适合小规模任务，但会限制并行度，还需要处理锁续期、持有者故障和接管。它不能消除“发送已成功但确认记录没落库”的不确定窗口。

**问：有认领机制后还要消费幂等吗？** 仍然需要。认领实例把消息送到 Broker 后宕机，接管者只能看到未完成状态，重发可能是正确恢复方式，因此重复无法仅在扫描层彻底消灭。

**问：发送中状态一直卡住怎么办？** 必须有租约、超时回收或可审计的失败状态。状态机还要区分发送尝试，避免上一轮迟到的回调把新一轮状态改错。单纯增加一个 SENDING 枚举但不设计恢复路径并不完整。

## 五、网关、Feign 与动态路由：7 道题

### Q25：用户身份从登录到下游业务怎么传递？

#### 面试时可以这样回答

> 用户登录后，用户服务校验账号密码和账户状态，生成包含用户 ID 与过期时间的 JWT。客户端调用受保护接口时把 token 放到 authorization 头，Gateway 全局过滤器判断是否属于白名单；非白名单则解析并校验 JWT 的签名、时间和用户字段，失败返回 401，成功把用户 ID 放入内部 user-info 请求头。
>
> 下游 Servlet 服务的 UserInfoInterceptor 从请求头取用户 ID，保存到 UserContext 的 ThreadLocal。业务代码因此可以在当前请求线程中取到用户；如果继续调用其它服务，Feign 拦截器再把它放到下一个请求头里。请求完成后，拦截器 remove 用户上下文，避免线程复用串用户。

#### 追问与详细答案

**问：JWT 为什么不能随意改用户 ID？** 项目使用 RS256 签名，修改载荷后如果不能生成合法签名，就会验签失败。签名保护完整性，不是加密，载荷通常能被解码，因此不能放密码或不应暴露的敏感信息。

**问：认证与授权有什么不同？** 认证判断“你是谁”，授权判断“你能操作什么”。合法登录用户也不能查询别人的订单或任意把订单标成已支付。当前支付申请和支付入口有归属检查，但不能据此声称所有接口都有完整资源授权。

**问：退出登录后 JWT 立即失效吗？** 单纯自包含 JWT 通常会在到期前仍可验证。若要求立即撤销，需要黑名单、用户 token 版本或服务端会话等机制，并承担状态查询和管理成本。当前不能直接说已经实现即时注销失效。

**问：网关为什么还要剥离客户端身份头？** JWT 是认证凭据，user-info 是网关加工的内部上下文。如果直接信任客户端自带的内部头，攻击者可能绕开这层转换，所以身份头必须在可信边界统一处理。

### Q26：用户自己伪造 user-info，能不能冒充别人？

#### 面试时可以这样回答

> 如果业务服务直接信任 user-info，而外部请求又能伪造这个头或绕过网关，就存在冒充用户的风险。因此身份透传的安全前提不是“大家约定不乱传”，而是网关统一清理外部同名头，再根据可信 token 注入；业务服务不任意对公网开放，内部调用也要具备相应身份和权限边界。
>
> 当前网关白名单分支直接放行，没有统一清理身份头，而且 /items/** 是按路径放行，并未按 HTTP 方法区分只读与写入。交易控制器也有按 ID 查询和推进支付状态的方法，方法内未见完整权限校验。是否能从外部利用还取决于实际路由与部署，但不能只凭网关登录过滤器就说这些接口安全。

#### 追问与详细答案

**问：白名单接口不需要用户身份，为什么还要清头？** 下游代码可能仍读取 UserContext 执行业务；一旦原样放行伪造头，就可能把匿名请求当成指定用户。白名单代表可以匿名访问，不代表外部传来的身份可信。

**问：网络只允许网关访问就够了吗？** 能降低绕过入口风险，但不能替代资源级权限，也不能覆盖所有内部误调用或服务身份被滥用。关键接口还应验证调用者权限和业务状态，资金及订单状态更新应收紧到可信内部调用。

**问：如何改订单查询？** 外部用户查询时，以当前认证用户与订单归属做匹配，或直接把 user_id 作为查询条件。服务内部确有跨用户查询需求时，用明确的内部接口和服务身份授权，而不是对所有调用开放同一无校验入口。

**问：接口用了 PUT 就算内部接口吗？** 不算，HTTP 方法不提供权限隔离。内部接口需要路由隔离、身份鉴别和授权控制，不能靠命名或约定。

### Q27：ThreadLocal 为什么必须 remove？异步任务中还在吗？

#### 面试时可以这样回答

> ThreadLocal 让每个线程保存自己的用户值，但 Web 容器通常复用线程，一个请求结束后线程不会销毁。如果不 remove，下一次请求可能读到上一个用户的信息，尤其当前请求没有写入新用户值时，会造成串用户。值也可能随长寿命线程长期保留，因此清理既关系到隔离正确性，也关系到内存生命周期。
>
> 当前 UserInfoInterceptor 在 preHandle 写入，在 afterCompletion 清理。ThreadLocal 只在当前线程有效，Feign 之所以能传给下游，是代码主动读出并写入 HTTP 头，而不是 ThreadLocal 自己跨进程传播。定时任务、MQ 消费线程、异步线程都不能默认具有原请求用户上下文。

#### 追问与详细答案

**问：换成 InheritableThreadLocal 就能在线程池传递吗？** 不能可靠解决。它主要在创建子线程时复制上下文，而线程池线程常早已创建并反复复用，不等于每次任务提交都复制当前请求状态。需要显式参数或受控的任务上下文包装，并在任务 finally 中恢复/清理。

**问：ThreadLocal 的弱引用为什么还可能内存泄漏？** ThreadLocalMap 的 key 使用弱引用，但 value 不因此自动变成弱引用；在线程长期存活且条目未及时清理时，值可能继续保留。当前 ThreadLocal 还是静态持有，不能只背“key 一定会被 GC”来解释这段代码；主动 remove 是清晰的生命周期管理。

**问：Gateway 也能照搬这个方案吗？** Gateway 使用 Reactor，逻辑可能跨线程调度，同一个线程也可能处理多个请求片段，不宜套 Servlet 的单请求线程假设。应使用适合响应式链路的上下文机制，例如 Reactor Context。

**问：MQ 消费需要用户 ID 怎么办？** 将业务确实需要的用户标识纳入受控消息载荷，并做权限/来源设计，或者用内部服务身份执行；不要伪造一个请求线程上下文就默认拥有用户授权。

### Q28：为什么查询失败可以降级为空，扣库存失败不能吞？

#### 面试时可以这样回答

> 查询和写入失败的业务后果不同。商品信息查询失败，某些展示场景可以返回空列表或降级提示，避免一个依赖故障导致整页失败。但库存扣减失败如果被吞掉，上层会继续认为订单创建成功，可能产生有效订单却没有扣库存。因此当前库存扣减和回补的 fallback 都抛异常，让上游全局事务或 MQ 消费重试接管。
>
> 但不能把“查询都返回空”当成通用规则。购物车展示可以容忍降级；下单计价、支付结果和权限查询往往不可以把依赖不可用伪装成真实不存在。当前下单收到空商品结果会拒绝成交，避免继续生成不可信订单，但把服务异常说成商品不存在，错误语义还可以细化。

#### 追问与详细答案

**问：FallbackFactory 相比 fallback 有什么价值？** 工厂可以获得导致失败的 cause，便于区分业务异常、超时、服务不可用或熔断拒绝，并保留日志与错误信息；它不意味着所有异常都应该转成成功响应。

**问：库存不足为什么也要抛异常？** 这是正常业务拒绝，但对当前下单事务意味着不能提交订单等修改，因此需要让调用方明确知道失败并触发适当回滚，而不是用 void 正常返回。

**问：查询支付单失败返回 null，会不会直接误关单？** 当前延迟监听在 null 时会走取消尝试，但取消流程还要调用支付服务关闭支付单；关闭调用失败会抛异常，不应默认已经关闭。尽管如此，“没查到”和“查失败”仍应该尽量区分，且远程扣款结果未知的竞态需要另外解决。

**问：降级是否已经保证服务高可用？** 它只是故障时的行为策略，还需配合超时预算、隔离、限流、监控和业务可接受性。返回空但业务不可用，不等于业务能力真的恢复。

### Q29：FallbackFactory、ErrorDecoder、超时重试分别做什么？

#### 面试时可以这样回答

> ErrorDecoder 负责把非成功 HTTP 响应解码成异常，当前实现会读取下游统一错误体的 code 和 msg，尽量保留“密码错误”“库存不足”等业务语义。FallbackFactory 在调用失败时拿到 cause，决定是允许降级还是继续抛出。超时控制等待预算，重试则是再发起一次执行，它们处在不同环节，不能混为一个功能。
>
> 当前 ErrorDecoder 还处理了响应体只能读一次的问题：先读取字节，能解析业务错误就构造异常；如果不是约定格式，需要把字节重新放回响应对象，再交给默认解码器，否则后者可能拿不到原始错误内容。

#### 追问与详细答案

**问：所有错误都 HTTP 200，会有什么问题？** ErrorDecoder 通常走非成功 HTTP 状态路径，如果错误也包装成 200，就不能指望这个机制自动按错误响应处理。应该明确 HTTP 状态与业务响应协议，并在对应解码层处理，避免表面成功、实际失败。

**问：写接口超时可以自动重试吗？** 只有在具有稳定幂等键和正确恢复语义时才能安全考虑。当前余额扣款有流水去重；不能因此把所有库存或其它写接口一律设置为无限自动重试。是否实际开启及次数应看配置与 Feign/Spring Cloud 版本，不能默认框架一定会帮忙重试。

**问：上下游超时如何设置？** 根据整条请求预算分配，避免上游早已放弃而下游长期占用资源。连接超时、读取超时和整体业务超时含义不同；超时后资金结果仍需查询，不能靠配置代替一致性设计。

**问：FULL 日志有什么风险？** 它可能记录请求头、参数和响应，当前调用链涉及身份与密码等敏感数据，应进行脱敏并控制生产日志级别。日志能辅助排错，但不能以泄露凭据为代价。

### Q30：Nacos 动态路由加载的完整过程是什么？

#### 面试时可以这样回答

> 当前 DynamicRoutLoader 在启动时从 Nacos 获取 gateway-routes.json，同时注册监听器。收到配置后把 JSON 解析为 RouteDefinition 列表，通过 RouteDefinitionWriter 删除以前记录的路由，再保存新定义，并维护一组 routeIds，后续配置变化再次执行这套流程。
>
> 这完成了“监听配置并修改路由定义”的代码，但还要区分路由定义存储与 Gateway 实际匹配使用的路由缓存。当前类里没有看到显式发布 RefreshRoutesEvent，所以我不能仅凭保存定义就承诺运行时立即刷新；要核对框架版本、其它触发路径，并用真实请求验证新增、修改和删除是否生效。

#### 追问与详细答案

**问：为什么先删后加有风险？** 更新过程并非天然原子。如果删除完成但新配置保存失败，会留下路由缺失或部分更新。各操作分别 subscribe 也不等于有一个统一的完成和失败边界；应该把更新组织成可管理的过程，集中处理错误。

**问：错误 JSON 怎么处理？** 应先完整解析并校验重复 ID、URI、断言等，再修改现有路由；解析失败保留上一版有效配置并告警。空配置还要区分“有意清空路由”与“读取/发布错误”，不能一概清掉。

**问：连续发布两次配置怎么办？** 可串行化应用配置，增加版本或序号，防止较旧更新晚完成覆盖较新状态；维护 routeIds 的集合也应与更新线程模型一致，而不是默认 HashSet 在并发回调中安全。

**问：怎么做到无损切换？** 可考虑先准备完整新版本、验证后切换缓存或采用增量差异更新，并保留回退方案。能否做到特定意义的无损需要实际验证，当前简单删除再保存不能直接承诺。

### Q31：Sentinel 你实际用到了什么？

#### 面试时可以这样回答

> 当前能确认的是引入了 Sentinel，并在相关调用方启用了 Feign 整合，让 @FeignClient 的 fallbackFactory 生效。因此我可以结合商品查询降级、库存写失败抛异常来讲调用失败策略。源码里也有控制台相关配置，但没有核对实际控制台规则或压测结果，不能说自己已经配置并验证了某个具体 QPS 阈值。
>
> 原理上，限流是控制进入某个资源的流量，避免服务过载；熔断是发现依赖在一定统计条件下不健康，暂时阻断对它的调用，防止调用线程一直等待和故障扩散。降级则是在调用无法正常完成时，提供业务能接受的替代行为；不是所有接口都能返回默认成功。

#### 追问与详细答案

**问：熔断恢复怎么理解？** 通常会有关闭、打开、半开等状态：正常时观察调用结果，满足条件后暂时打开熔断，等待窗口后允许有限探测，再根据结果恢复或继续熔断。具体规则、窗口和探测行为应按实际版本配置解释，不能把概念数字当成当前设置。

**问：限流阈值怎么定？** 通过容量测试、下游承载能力、实例数、延迟目标及错误率确定，留出安全余量；不能随意写一个 QPS 就称为优化。还要观察热点资源和突发流量，单一平均值可能掩盖局部瓶颈。

**问：控制台配置了规则，重启会自动保留吗？** 不应默认。需要核对数据源与持久化集成，单纯在控制台操作不等于项目已经完成规则持久化。本次没有读取该运行配置，所以只说明需要验证。

**问：为什么不直接在 fallback 里返回成功？** 对库存和资金这类写操作，假成功会破坏一致性，应明确失败并交给事务或恢复流程；仅在展示类、业务可容忍的查询中采用合适降级结果。

## 六、面试官最可能连续追问的 5 个故障专题

### 专题 A：无路由消息收到 return，又收到 ack，会怎样？【源码中的明确风险】

当前逻辑：
1. 消息发送到存在的交换机，但没有匹配队列。
2. mandatory return 回调安排重试，记录仍是 PENDING。
3. Broker 仍可能对这次发布给出 ack。
4. onConfirm 只看 ack，把 PENDING 更新为 SENT。
5. 定时任务不再扫描该消息，但目标队列并没有收到它。

**正确回答：**return 与 confirm 是不同语义，不能只看 ack。应该关联同一次发送的 return 结果，只有满足成功路由等条件才标发送完成；重发时还要区分不同发送尝试，避免旧回调覆盖新状态。具体可使用当前 Spring AMQP 版本支持的 CorrelationData returned 信息或显式发送尝试状态，并通过无绑定队列用例验证。

### 专题 B：钱扣了，支付没成功落库，订单又超时关闭？【当前补偿不完整】

时序：
1. 用户服务扣款及流水提交。
2. 支付服务在更新状态前崩溃/回滚，支付单仍待支付，行锁释放。
3. 延迟关单先于对账执行。
4. closePayOrderByBizOrderNo 只依据支付单状态，把它关闭，没有查询或协调实际资金结果。
5. 交易订单关闭并回补库存。
6. 对账任务只扫描待支付单，已关闭记录被排除；状态更新方法也不接受已关闭状态。

**结果：**有出现“已扣款、订单关闭、未退款且无法由现有对账恢复”的窗口。正常请求下的支付单行锁并未覆盖远程资金事务的全生命周期。

**改进讨论：**
- 引入支付处理中/结果未知等状态，明确何时允许关单。
- 对账覆盖资金流水与订单终态冲突，不只盯待支付单。
- 如果订单已释放库存，不应直接标成功继续履约；需要定义退款或重新校验/占用库存的业务路径。
- 退款本身也要幂等、可追踪、可重试。
- “关单前查一次流水”还不够：超时的远程扣款请求可能仍在执行，查询时没有流水，之后才提交。需要真正协调状态，或保留处理迟到扣款的补偿闭环。

### 专题 C：没有支付单时允许关单，同时有人申请支付单呢？【跨服务竞态】

可能时序：申请支付单先查到交易订单未支付 → 关单发现尚无支付单，返回可关闭 → 交易订单关闭 → 申请请求随后创建支付单。

对已有支付单加行锁，不能无条件覆盖“支付单尚不存在”以及跨服务先查后写的整个过程。就算特定隔离级别下出现间隙锁，也不能跨两个服务事务自动建立完整业务互斥。

改进需让支付申请与关单有明确的状态协调/版本校验，不能只在申请开始查一次订单；一旦发生迟到支付，必须进入已定义的资金补偿路径。

### 专题 D：本地事务提交后删缓存，Seata 最后又回滚呢？【区分两种提交】

库存服务 evictAfterCommit 监听的是本地 Spring 事务。AT 分支本地提交后，全局事务仍可能回滚；期间缓存可能重新装入暂态库存，之后 undo 回滚不一定触发业务缓存删除。

因此“用了 afterCommit”不能直接证明全局事务场景中的缓存一致性。可讨论全局完成后失效、基于变更事件的修正、补偿删除与 TTL 等办法。

同时区分：商品页库存短暂不准是展示问题；真正扣库存仍由数据库条件更新裁决，不能让缓存展示值决定资金/库存正确性。

### 专题 E：消费端状态条件更新为 0，就一定是重复消息吗？【幂等不等于一致性】

不是。可能是已经支付，也可能是订单不存在、已关闭或其它非法状态。只是不重复更新，并不代表支付订单、资金和业务订单彼此一致。

改进是对“不满足期望状态”的情况分类，重复成功可忽略，跨终态冲突要记录异常并触发对账/退款等闭环。涉及积分、优惠券、库存等额外副作用时，单改订单状态也不能自动保证其它动作幂等。

## 八、如何证明“是你理解并做过的”？

### Q32：哪个问题最难？你怎么定位、验证？

#### 面试时可以这样回答

> 我准备重点讲“远程扣款结果未知”和“支付通知可靠性”这两个问题，而不是只讲正常流程。比如支付服务调用用户服务后，用户侧事务可能已经提交，但响应丢失或者支付进程随后退出，这时支付单还显示待支付。只加本地事务或支付单行锁都不能判断钱到底扣没扣，因此需要用户侧持久化流水、稳定幂等键和对账入口。
>
> 我会从事务提交点分析问题：先确认哪个服务的数据已经提交，再查看支付单 ID 对应的扣款流水与金额，判断应该幂等重试还是补齐状态；支付状态恢复时也要补出通知，不然交易订单仍旧未支付。与此同时，我也识别到如果关单先把支付单关闭，现有待支付扫描就覆盖不到，因此还需要补资金与终态冲突的处理。

### Q33：如果让你补测试，优先测什么？

#### 面试时可以这样回答

> 我会优先验证资金和库存不变量，而不是只测接口返回 200。资金方面，同一支付单并发请求后只能有一条有效扣款流水，余额只能减少一次；不同支付单同时扣同一账户，也不能透支。库存方面，多商品扣减失败后不能保留部分扣减，Seata 相关订单与购物车分支也要恢复到预期状态。
>
> 第二类测试是故障注入：在用户扣款提交后、支付状态提交前让支付服务退出；在支付提交后、发送 MQ 前制造故障；移除消息绑定模拟 return 与 ack；重复交付支付通知验证消费幂等。最后增加支付与关单并发，确认不会产生无人处理的已扣款已关闭订单。

#### 追问与详细答案

**问：Mock 测试够吗？** Mock 适合验证分支、参数和异常传播，但不能证明 InnoDB 锁、唯一键竞争、Seata 回滚或 Broker 确认行为。关键并发与跨服务失败需要真实数据库和中间件的集成测试。

**问：怎样保证线程真的并发？** 可用屏障或 CountDownLatch 让多个请求在目标步骤附近同时启动，并重复运行；单纯循环请求通常只是串行测试。还要设置可控故障点，避免只靠随机 sleep 猜时序。

**问：你已经都测过了吗？** 本文给的是应补的验证方案，本次未执行这些用例，也没有发现完整的支付故障回归证据，面试时只能报告真实完成的部分。

### Q34：性能优化你能讲什么？

#### 面试时可以这样回答

> 我会先讲源码中真实的优化点及其代价，不编造性能提升数字。例如下单批量查询商品，减少多次 Feign 往返；库存和余额通过条件 UPDATE 避免先查再写的并发窗口；消息扫描有批次限制，消息表也有按状态和下次重试时间的组合索引。但这些只是设计依据，提升多少必须经过一致条件下的测量。
>
> 如果要优化支付链路，我会重点观察支付单行锁持有期间的远程调用耗时，因为它可能放大锁等待和数据库连接占用。然后根据调用耗时、数据库慢查询、连接池使用率和消息积压定位瓶颈，而不是一开始就增加 Redis 或线程数。

#### 压测与定位步骤

1. 记录机器资源、实例数、数据库规模、数据分布和中间件配置。
2. 固定测试场景，区分同一热点账户/商品与分散账户/商品；热点锁竞争不能被平均数据掩盖。
3. 逐步增加并发，记录吞吐、成功率、P95/P99、超时率、数据库锁等待和连接池占用。
4. 每次只调整可解释的因素，对照测试；优化后再核对余额、流水、库存等正确性。
5. 重试引发的请求量也要计入，否则表面吞吐可能包含大量重复无效请求。

#### 追问与详细答案

**问：条件更新一定比加分布式锁快吗？** 不能脱离场景下结论。当前数据库本就持有关键余额/库存数据，条件更新实现简单且减少额外组件，但热点行仍会串行化。性能需要结合锁竞争、网络成本和业务负载测量。

**问：消息表索引怎么选？** 当前扫描按 status 等值和 next_retry_time 范围过滤，组合索引与这一访问模式匹配。数据量大时还要考虑排序分页、状态分布、历史记录清理及执行计划；有索引不等于所有扫描都高效。

**问：没有压测结果怎么回答？** 直接说已做功能与一致性方面的实践，但尚无可复核的性能对比数据；可以解释验证计划，不把理论动机包装成“提升了几倍”。

### Q35：如果重新设计，你最先改哪几处？

#### 面试时可以这样回答

> 我会先补正确性和安全性，再谈吞吐。第一，修复支付通知 return 与 confirm 的联合判断，避免无法路由的消息被标记已发送。第二，完善支付结果未知与关单之间的状态协调，让已扣款、支付待确认、订单关闭这些组合都有明确处理路径。第三，收紧外部身份头、白名单写接口、订单归属和内部状态更新权限。
>
> 然后完善扫描和运维：订单到期增加数据库扫描兜底，对账和消息投递增加进度推进、任务认领及失败告警，核实动态路由刷新与错误配置回退。最后以并发和故障回归证明这些改动有效，再根据测量结果优化锁等待、查询和调用成本。

#### 核心改进如何落地

**1. 通知状态机。** 同一次发送关联 return 和 confirm；用发送尝试标识防止迟到回调覆盖新尝试；只有符合预期成功条件才结束重试。增加无绑定、Broker 不可用、确认丢失的回归用例。

**2. 资金与关单协议。** 不能只在关单前查一次流水。可考虑在资金执行侧，围绕同一个支付业务键，让扣款与取消资格判定通过本地事务原子竞争：取消已生效则拒绝迟到扣款，扣款已提交则返回资金成功而不是假装已取消。还需为尚无记录时的并发创建设计唯一键与锁定规则。另一类场景若允许迟到成功，则必须进入幂等退款等逆向流程。上述是需要重新设计并验证的协议，不是当前已有实现。

**3. 异常资金闭环。** 对账不仅看待支付单，也识别已扣款但订单关闭、金额不匹配等冲突；已释放库存的订单不能直接改成功继续履约。退款应有独立幂等键与资金流水，保留原扣款证据，不靠删除流水“抹掉”历史。

**4. 可观测与人工处理。** 记录每笔业务关联 ID，监控最老待投递消息年龄、对账延迟、重试耗尽数及资金冲突数；提供受控重放与处理记录。仅输出一条“需要人工介入”的日志不是闭环。

#### 追问与详细答案

**问：是不是要全部重写？** 不需要。可以先修明确回调问题、补授权与测试，再逐步演进状态机和任务调度。改造要保持旧数据与在途请求兼容，不能换版本时把老待处理支付单丢在旧流程里。

**问：为什么正确性优先？** 电商资金与库存错误会直接造成损失；在错误逻辑上扩容只会更快地产生异常。吞吐目标应建立在业务不变量可验证的基础上。
