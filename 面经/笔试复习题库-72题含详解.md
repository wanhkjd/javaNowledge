## 二、四科知识唤醒：先补这些“地基”

### 2.1 Java：先分清四组东西

#### ① 值、引用、对象不是一回事

- 基本类型变量直接保存基本类型的值；引用类型变量保存一个引用，也可以为 `null`。
- `String`、数组、包装类、普通类的实例都是对象，不是基本类型。
- Java **始终按值传递**。传对象时，复制的是引用值，所以能通过副本修改同一个对象；给形参重新赋值，不会改变调用者变量里的引用。

| 类型 | 规定的位宽/取值要点 | 成员变量与数组元素默认值 |
|---|---|---|
| `byte` | 8 位有符号，−128～127 | 0 |
| `short` | 16 位有符号 | 0 |
| `int` | 32 位有符号 | 0 |
| `long` | 64 位有符号；大整数字面量常加 `L` | 0L |
| `float` | 32 位浮点；字面量常加 `F` | 0.0F |
| `double` | 64 位浮点；普通小数字面量默认类型 | 0.0D |
| `char` | 16 位无符号，表示一个 UTF-16 代码单元，不保证是完整 Unicode 字符 | `'\u0000'` |
| `boolean` | 只有 `true/false`；Java 语言规范不统一规定它在内存中占几个字节 | false |
| 引用类型 | 不是上述 8 种基本类型 | null |

**局部变量没有可直接使用的默认值**，必须在读取前明确赋值。浮点数不适合直接承担精确金额计算；金额通常考虑 `BigDecimal`，并优先由十进制字符串构造。

#### ② 比较“是不是同一个对象”和比较“内容”

- 基本类型 `==`：按相应数值或布尔规则比较。
- 引用类型 `==`：比较是否指向同一对象，或是否都为 `null`。
- `equals`：语义由类决定；`Object` 默认按身份比较，`String` 按字符内容比较。
- 合约：`a.equals(b)` 为真，必须有相同的 `hashCode`；哈希相同不保证对象相等。
- 字符串不可变，指的是对象的字符内容不能原地改；不代表变量不能改指向。

#### ③ 编译期看声明，运行期看实际对象——但不是所有成员都多态

- **重载**：同名、参数列表不同，主要在编译期选定。
- **重写**：子类覆盖可重写的实例方法，运行时动态分派。
- 字段访问、静态方法不按普通实例方法的动态分派处理。
- `final` 修饰变量：只能赋值一次；修饰方法：不能重写；修饰类：不能继承。
- `final` 引用不能重新指向另一个对象，但对象内部状态不一定不可变。
- 抽象类可有构造器、实例字段、普通方法；接口可有默认方法和静态方法（Java 8+），也可有私有辅助方法（Java 9+）。不能说“接口只能有抽象方法”。

#### ④ 集合看用途，不靠背一串类名

| 用途 | 常见选择 | 应记住的边界 |
|---|---|---|
| 按位置读写的动态列表 | `ArrayList` | 随机访问 O(1)，中间插删通常要移动元素 |
| 需要双端队列/栈 | `ArrayDeque` | 不接收 null；普通使用通常比旧的 `Stack` 更合适 |
| 去重 | `HashSet` | 依赖 equals/hashCode，不承诺遍历顺序 |
| 按键找值 | `HashMap` | 键唯一；允许一个 null 键及多个 null 值；非线程安全 |
| 保留插入顺序 | `LinkedHashMap` / `LinkedHashSet` | 与“按大小排序”不同 |
| 按键排序 | `TreeMap` | 基于有序比较，典型操作 O(log n) |
| 总是先取最小值 | `PriorityQueue` | 默认小根堆；整个迭代顺序不保证有序 |

复杂度说的是规模增长趋势。`HashMap` 的平均 O(1) 依赖哈希分布等条件，不等于所有输入、所有操作必定 O(1)。

**并发底线：**`volatile` 主要解决可见性和相关有序性，不能让 `count++` 自动成为原子操作；同一把锁保护的 `synchronized` 临界区可互斥；`AtomicInteger.incrementAndGet()` 可用于原子自增。`start()` 启动新线程，直接调用 `run()` 只是普通方法调用。

### 2.2 概率：先把中文翻译成事件

设样本空间为 Ω，事件为 A、B。

| 中文 | 数学意思 | 常用方法 |
|---|---|---|
| A 或 B 至少发生一个 | A∪B | 加法公式 |
| A 和 B 同时发生 | A∩B | 乘法公式；先判断是否独立 |
| A 不发生 | A 的补事件 Aᶜ | 1−P(A) |
| 已知 B，求 A | P(A\|B) | 把样本空间限制到 B |
| 至少一次 | 次数 ≥ 1 | 常用 1−P(一次都没有) |
| 恰好 k 次 | 次数 = k | 识别是否为二项、超几何等分布 |

**概率题四步法：**写事件 → 明确是否等可能/是否放回/是否独立 → 选模型 → 代数计算并检查结果在 0～1 之间。

#### 必背公式及其前提

```text
等可能有限样本：P(A) = 有利结果数 / 全部结果数
组合数：C(n,k) = n! / [k!(n-k)!]，0! = 1
排列数：A(n,k) = n! / (n-k)!
加法：P(A∪B) = P(A) + P(B) - P(A∩B)
条件概率：P(A|B) = P(A∩B) / P(B)，要求 P(B)>0
乘法：P(A∩B) = P(B)P(A|B)
独立时：P(A∩B) = P(A)P(B)
全概率：P(A) = Σ P(Bi)P(A|Bi)，Bi 必须互斥且覆盖全部情况
贝叶斯：P(Bj|A) = P(Bj)P(A|Bj) / Σ P(Bi)P(A|Bi)
期望：E(X) = Σ xP(X=x)；连续型时改为对 xf(x) 积分
方差：Var(X) = E(X²) - [E(X)]²
线性：E(aX+bY+c) = aE(X)+bE(Y)+c，不要求 X、Y 独立
变换：Var(aX+b) = a²Var(X)
相加：Var(X+Y) = Var(X)+Var(Y)+2Cov(X,Y)
```

**互斥 ≠ 独立。**互斥是不能同时发生；独立是知道一个发生，不改变另一个的概率。两个概率都大于 0 的互斥事件不可能独立。方差直接相加需要协方差为 0；独立是一个充分条件，但不是必要条件。

#### 分布识别表

| 分布 | 题目特征 | 核心概率 | 期望；方差 |
|---|---|---|---|
| 伯努利 Bernoulli(p) | 一次成功/失败，成功记 1 | P(X=1)=p | E=p；Var=p(1−p) |
| 二项 Bin(n,p) | n 次独立、成功率相同，数成功次数 | C(n,k)pᵏ(1−p)ⁿ⁻ᵏ | E=np；Var=np(1−p) |
| 超几何 | 有限总体中不放回抽样，数某类个数 | C(K,k)C(N−K,n−k)/C(N,n) | 均值 nK/N；本讲义重点会列概率 |
| 几何 Geom(p) | 数到第一次成功为止的总试验次数 | (1−p)ᵏ⁻¹p，k≥1 | E=1/p；Var=(1−p)/p² |
| 泊松 Pois(λ) | 给定时间/区域内的事件次数，模型假设成立 | e⁻λ λᵏ/k! | E=λ；Var=λ |
| 均匀 U(a,b) | 区间等密度 | 区间概率＝长度比 | E=(a+b)/2；Var=(b−a)²/12 |
| 指数 Exp(λ) | 泊松过程的等待时间；这里 λ 为“速率” | P(T>t)=e⁻λᵗ | E=1/λ；Var=1/λ² |
| 正态 N(μ,σ²) | 对称钟形；第二个参数是方差 | Z=(X−μ)/σ，查 Φ | E=μ；Var=σ² |

注意：有些教材的几何分布数的是“成功前的失败次数”，从 0 开始；有些教材用指数分布的“均值参数 θ”。本讲义统一采用表中的定义，不能混套公式。

连续型随机变量的概率是**面积**：P(a<X<b)=∫从a到b f(x)dx；P(X=某个精确值)=0。密度 f(x) 不一定小于等于 1，但非负且总面积必须为 1。

### 2.3 树：先约定“高度怎么数”

- 树是连通且无环的结构。这里研究有根树；除根外，每个结点恰有一个父结点。
- 结点的度＝孩子数；叶子结点没有孩子。二叉树每个结点最多两个孩子，左右位置有区别。
- **本讲义：根在第 1 层；深度按边数，根深度为 0；高度按层数，非空单结点树高度为 1，空树高度为 0。** 若教材用边数定义高度，非空树的结果应减 1。

| 名称 | 精确定义 | 不要混淆 |
|---|---|---|
| 满二叉树（本讲义对应 perfect） | 每层都达到最大结点数 | h 层有 2ʰ−1 个结点 |
| 完全二叉树（complete） | 除末层外全满，末层从左向右连续排列 | 可以不是满二叉树 |
| 严格/正则二叉树（full/proper） | 每个结点只有 0 或 2 个孩子 | 英文 full 不应直接套成中文“每层都满” |
| 二叉搜索树 BST | 整个左子树键都小于根，整个右子树键都大于根 | 不只是直接孩子满足；本讲义不允许重复键 |
| 二叉堆 | 完全二叉树＋父子间满足堆序 | 兄弟之间无大小顺序要求；不等于 BST |
| AVL 树 | BST，且每个结点左右子树高度差不超过 1 | 需要时通过旋转恢复平衡 |
| B/B+ 树 | 平衡多路搜索树 | 不是二叉树，常用于外存索引 |

```text
非空树：n 个结点，n-1 条边
森林：n 个结点、k 棵树，共 n-k 条边
二叉树第 i 层最多：2^(i-1) 个结点（根为第 1 层）
高度为 h 的二叉树：h ≤ n ≤ 2^h-1
非空二叉树：叶子数 n0 = 度为 2 的结点数 n2 + 1
完全二叉树：高度 floor(log2 n)+1；叶子数 ceil(n/2)
完全二叉树按层序从 1 编号：父 floor(i/2)，左孩子 2i，右孩子 2i+1
孩子下标必须 ≤ n 才实际存在；根没有父结点。
```

遍历口诀：**前序＝根左右；中序＝左根右；后序＝左右根；层序＝一层一层、从左到右。** DFS 常用递归或栈；层序 BFS 用队列。BST 的中序才具有有序性，不是任意二叉树的中序都排序。

### 2.4 ER 图：从业务语句到图，再从图到表

ER＝Entity–Relationship，即**实体—联系模型**。它表达“有什么对象、对象有什么属性、对象之间有什么联系”，不是执行步骤或程序流程。

**Chen 记法：**矩形＝实体类型，椭圆＝属性，菱形＝联系，属性下划线＝键属性，双椭圆＝多值属性，虚线椭圆＝派生属性，双矩形＝弱实体，双菱形＝识别联系。双线常用于表示全参与。若考试给了图例，优先遵从该图例。

**鸦脚记法：**常把属性放进实体矩形中，用连线端点表示基数。`||`＝恰好 1，`o|`＝0 或 1，`|{`＝1 或多，`o{`＝0 或多。读取某端符号时，是问“对面的一个实例，可以对应这一端多少个实例”。不要把不同记法的标注习惯混用。

建模五步：

1. 找需要独立记录的对象：学生、课程、订单……这是候选实体，而不是每个名词都要建表。
2. 给实体选能唯一识别它的键：学号比姓名可靠。
3. 找动词联系：选修、下单、包含、管理……
4. 对每条联系**双向**提问“最少几个、最多几个”：0/1/N 是业务规则，不靠猜。
5. 转表并核对主键、外键、唯一约束、非空约束及无法单靠外键表达的业务约束。

| 术语/联系 | 含义或通常的转表方式 |
|---|---|
| 超键 | 能唯一标识记录，可能含多余属性 |
| 候选键 | 最小的超键；去掉任一属性就不再保证唯一 |
| 主键 PK | 从候选键中选出的主标识；唯一且非空 |
| 外键 FK | 引用同表或另一表中被引用的候选键/唯一键；不只限于主键 |
| 1:N | 常把 1 端的键放到 N 端作外键；联系属性通常也可放 N 端 |
| M:N | 新建关联表，保存双方外键和联系自身属性 |
| 1:1 | 外键＋唯一约束，或共享主键；是否非空取决于参与约束 |
| 多值属性 | 常拆成子表，不能用逗号拼接来替代规范建模 |
| 弱实体 | 自己的部分键不够，需结合所属强实体的键来标识 |

**特别重要：**外键存在不等于“父记录至少有一个子记录”。`OrderItem.order_id NOT NULL` 只要求每条明细必须属于订单，不能自动保证每个订单都有明细。ER 图表达的业务规则，未必都能靠一条 FK 或 CHECK 完整落实。

## 六、逐题答案与详细解析

### A. Java 逐题解析

#### J01 解析｜把“工具、环境、执行器”分开

**答案：**JDK 是开发工具包，包含编译器等工具及运行所需组件；JRE 是“运行环境”的概念，包括 JVM 和运行库等；JVM 是执行 Java 字节码的虚拟机。现代 JDK 的分发不一定另带一个独立安装的 JRE 产品，不能把旧的安装目录关系当成所有版本的固定事实。

主要过程：`Hello.java → javac 编译 → Hello.class 字节码 → JVM 类加载、验证、链接及必要初始化 → 解释执行和/或 JIT 编译执行`。这是入门层面的主线，具体 VM 可采用不同实现策略。

两项判断均错误。跨平台主要依靠标准字节码和各平台上的 JVM 实现；Windows 和 Linux 上的 JVM 不必是相同二进制。编译通过只说明满足编译期规则，仍可能遇到空指针、越界、缺少类、文件不存在等运行问题。

**易错点：**Java 不是“直接把源文件交给 CPU 执行”；也不能由编译成功推出程序逻辑正确。

#### J02 解析｜默认值只对指定位置成立

**答案：B、D、F。**

- A 错：`String` 是类，字符串变量是引用类型变量。
- B 对：`char` 范围为 0～65535，是 UTF-16 代码单元。一个 emoji 等补充字符可能需要一对 `char`，所以不能把 `s.length()` 一概当作用户看到的字符数。
- C 错：不能从 Java 语言规范给 `boolean` 推出统一的内存字节数；不同存储场景和 VM 实现可能不同。
- D 对：实例字段会先取得默认值。静态字段、数组元素也有相应默认值。
- E 错：局部变量读取前必须明确赋值，否则编译器报“变量可能尚未初始化”。
- F 对：例如 `new String[3]` 的三项是 `null`，不是三个空字符串。

**迁移规则：**看到默认值题，先问变量是“字段、数组元素”还是“局部变量”，再问类型。

#### J03 解析｜先算表达式类型，再看能否赋回

**答案：**①编译错误；②s=2；③b=−128；④x=2；⑤y=2.0；⑥z=2.5；⑦k=−2147483648。

1. `s+1` 会进行数值提升，结果类型是 `int`。普通赋值不能把任意 int 隐式窄化到 short，因此①编译失败。可显式写 `(short)(s+1)`，但应知道可能截断。
2. 复合赋值含有相应的隐式类型转换，`s+=1` 就类型转换效果而言相当于把加法结果转回 short；同时左侧只求值一次。
3. `b++` 会将结果转回 byte。127 加 1 超过 byte 正范围，低 8 位变成二进制 `10000000`，解释为有符号 byte 即 −128。
4. `5/2` 两个操作数都是整数，先做整数除法得到 2。赋给 double 也只能再转成 2.0，不会恢复被截去的小数。
5. `5/2.0` 是浮点除法，得到 2.5。
6. int 加法溢出不会自动抛算术异常；结果环绕到最小 int。若需要检测溢出，可考虑 `Math.addExact`。

**易错点：**最终接收变量是 double，不代表前面所有运算都自动变成浮点运算。

#### J04 解析｜后置先取旧值，前置先增加

**输出：**

```text
4,3,false
33
123
```

求 `i++ + ++i` 时按从左到右求值：左边取 1 后令 i=2；右边先令 i=3，再取 3；因此 r=1+3=4，i=3。`false && ...` 的右侧被短路，不会执行 `++i`。

`1+2+"3"` 先做整数加法得 3，再拼接成 `"33"`。`"1"+2+3` 从第一步开始就是字符串拼接，依次得到 `"12"`、`"123"`。

**易错点：**不要为了“整理算式”交换有副作用操作的顺序；Java 表达式有明确求值规则。

#### J05 解析｜常量折叠与运行时拼接要分开

**输出：**`true / false / true / false / true`，每项一行。

- `"ja"+"va"` 是编译期常量表达式，其结果可按字符串常量规则进入常量池，与 `"java"` 指向同一字符串。
- `new String("java")` 显式创建不同对象，因此 `a==c` 为 false，但内容相同，`a.equals(c)` 为 true。
- 这里 p 不是常量变量，`p+"va"` 不是编译期常量表达式。运行时拼接所得结果不因内容相同就自动与 a 具有相同引用身份，所以 `a==d` 为 false。
- `intern()` 返回该内容的规范化池中字符串，因而最后为 true。

**变式：**若改成 `final String p="ja";`，p 是以常量表达式初始化的常量变量，后续拼接可以成为常量表达式。不能只靠“有没有加号”判断。

#### J06 解析｜对象不可变不等于引用不能变

**输出：**第一行 `ab`，第二行 `abc`。`f.append("y")` 合法，f 指向的构造器内容变为 `xy`；重新给 f 赋另一个引用会编译失败。

`String.concat` 没有原地改变原字符串，而是返回拼接结果；题中丢弃了返回值。如果写 `s=s.concat("c")`，变量 s 就改为指向新结果。

`StringBuilder.append` 则修改同一个可变缓冲区。`final` 限制的是引用变量的再次赋值，不会冻结它引用的对象。

`StringBuilder` 不提供类似 StringBuffer 的方法同步，适合常见的单线程构建；`StringBuffer` 的相关方法有同步保护。但多个方法组合成的业务操作，仍不能仅凭“单个方法线程安全”就断言整体原子。

#### J07 解析｜画出“两个引用指向同一个数组”

**输出：**`1,9,old`。

调用时：形参 x 得到数值 1 的副本；形参 a 得到调用者数组引用的副本；形参 s 得到原字符串引用的副本。

- `x=9` 仅改变形参，不改变调用者 x。
- `a[0]=9` 经引用副本访问的是**同一个数组对象**，所以调用者看到第 0 项变为 9。
- `a=new int[]{7,7}` 只让形参 a 指向新数组，调用者 a 仍指向原数组。
- `s="changed"` 同样只改变形参引用，调用者 s 仍指向 `"old"`。

**应记住的表述：**“传递对象引用的值副本”，不是“把调用者变量本身交给方法修改”。

#### J08 解析｜避免背不可靠的缓存边界结论

**答案：**①true；②true；③不能做跨实现、跨配置的固定真假保证；④拆箱时抛 `NullPointerException`。

127 的常量装箱落在规范要求保证身份共享的范围内，因此①确定。`equals` 比的是包装数值，所以两个 1000 的②确定为 true。

通常配置的 OpenJDK 中，③往往为 false，但某些实现或缓存配置可以扩大缓存范围。因此“只要大于 127，`==` 必为 false”是不可靠的通用规则。本题要求的是可移植结论，而不是某台机器的一次运行截图。

`int x=n` 需要从 Integer 提取 int 值；n 为 null，没有对象可供拆箱，于是异常。

**实战规则：**包装类比较数值优先用适当的 equals 或明确拆箱，并处理 null；不要把对象身份当数值比较。

#### J09 解析｜哈希值只负责筛选，不能代替相等判断

**答案：A、C、E。** B 把单向推论倒过来了；不同对象可以哈希碰撞。D 错，按学号重写 equals 后，也必须让 hashCode 与该相等语义一致。

所有对象都返回同一哈希值，**不一定违反正确性合同**：相等对象当然有同一哈希值，不相等对象允许碰撞。但冲突会多，性能可能很差。

理解为两步：先利用 hashCode 缩小候选范围，再按 equals 判断逻辑相等。重写 equals 时还要满足自反、对称、传递、一致，以及与 null 比较为 false 等要求。

**易错点：**“哈希相同”等于“可能需要进一步比较”，不是“已经相等”。

#### J10 解析｜构造器不继承，protected 不只是“子类都能看”

1. 类只能直接继承一个类，但可以实现多个接口。接口自身可以扩展多个接口。
2. 构造器不被子类继承；子类构造时要适当调用父类构造器。父类 private 字段不能被子类代码直接访问；对象仍包含这部分父类状态，可以通过父类提供的方法操作。
3. 在通常的类成员访问语境下：public 对所有可访问该类型的代码开放；private 受声明所在顶层类及其嵌套关系的规则限制；不写修饰符主要限同包；protected 允许同包访问，并向跨包子类提供受限制的访问。模块等额外可访问性规则也可能影响 public 类型能否被外部使用，本题不展开。
4. 跨包子类访问 protected 实例成员时，不能通过任意声明为父类类型的接收者来“打开保护门”。例如子类方法中的 `this.x`、合适的子类实例接收者可合法，而 `Base other; other.x` 一般不合法。若在同包则另按同包权限判断。

**记忆方式：**先看是否同包；跨包再判断是不是子类代码及接收者是否满足限制。

#### J11 解析｜真正动态分派的是可重写的实例方法

**输出：**

```text
P
C
P
```

p 的声明类型是 Parent，字段访问 `p.name` 按该类型找到 Parent.name；Child.name 是另一个被隐藏的字段，不是对字段进行动态重写。

`who()` 是实例方法，Child 正确重写了它；实际对象是 Child，所以执行 Child.who，返回 C。

`tag()` 是静态方法，Child 中同名静态方法属于隐藏，不是实例方法重写；此处选的是 Parent.tag。

通过 `p.tag()` 调静态方法虽然能编译，却容易让人误以为它按对象多态分派，推荐写 `Parent.tag()` 明确所属类。

#### J12 解析｜重载在编译时根据可用类型信息选择

**第一组输出：**`Object`、`String`。虽然 x 实际引用 String，但表达式 x 的编译期类型为 Object，因此先选 `pick(Object)`。

传入 null 时，Object 和 String 都能接收；String 是 Object 的子类型，是更具体的匹配，所以选 `pick(String)`。

**第二组：编译错误，调用有歧义。**String 和 Integer 互无子类型关系，null 对两者都适用，没有唯一最具体方法。可以显式写 `f((String)null)` 表达意图，但应反思重载接口是否易用。

**易错点：**不要把“重载选择”误当成“根据参数运行时对象类型动态选方法”。

#### J13 解析｜静态一次，对象部分每次一次

**输出：**`A D B C E F B C E F`（各字母后有空格）。

首次创建 Sub：先初始化父类的静态部分 A，再初始化子类静态部分 D。构造对象时，父类实例初始化块 B、父类构造器体 C 在子类实例初始化块 E、子类构造器体 F 之前。

第二次创建对象，类已初始化，所以不再输出 A、D，只输出 B C E F。

因此 A/D 各一次，B/C/E/F 各两次。这个例子没有引入复杂的字段初始化、递归初始化或从父类构造器调用可重写方法；遇到这些变式时需要额外分析，不能机械套六字口诀。

#### J14 解析｜三种“final 开头”的词不是一类机制

**判断：1 错，2 错，3 对，4 对，5 错。**

抽象类不能直接 `new`，但有构造器，用于初始化由子类对象承载的父类状态。接口在 Java 8 起就可以有 default 和 static 方法实现；Java 9 起还能有 private 辅助方法。

`final` 是修饰符，控制继承、重写或赋值；`finally` 是异常处理结构的一部分；`finalize` 是历史上的对象终结方法。

Java 21 中终结机制已经被弃用并标记为拟移除，不应依赖其执行时机，也不能拿它可靠地关闭文件、数据库连接。资源应优先通过 `AutoCloseable`、try-with-resources、显式生命周期等方式管理。

**易错点：**“final 引用”只是一根不能重新绑的绳子，并不把另一端的对象冻住。

#### J15 解析｜受检异常是编译期处理要求

**答案：A、B、E。**

`IOException` 属于受检异常，可能抛出它的方法通常必须捕获或声明。`RuntimeException` 及其子类、`Error` 及其子类属于非受检范围，所以 C 错。

更具体的 catch 应在更宽泛的 catch 之前。先写 `catch(Exception e)` 后再写 `catch(IOException e)`，后者已被前者覆盖，会导致不可达的捕获分支问题。

`throw` 真正抛出某个异常对象，如 `throw new IllegalArgumentException(...)`；`throws` 写在方法签名上，声明可能向调用者传播的异常类型。

字节流（InputStream/OutputStream）处理字节；字符流（Reader/Writer）处理字符。读取文本涉及字节到字符的解码，应明确如 UTF-8 的编码，避免“本机正常，换机器乱码”。try-with-resources 会按与声明相反的顺序关闭资源；即使处理过程中抛异常也会尝试关闭。

**易错点：**自动关闭文件是资源管理，不是等待 GC；两者的时间要求不同。

#### J16 解析｜先保存待返回值，再执行 finally

**答案：f 返回 1；g 返回 2。**

f 执行 `return x` 时先求出返回值 1，并保存待返回结果；随后 finally 修改局部变量 x，并不会把已经求好的这个 int 结果改成 2。若返回的是可变对象引用，而 finally 修改对象内部状态，调用者看到的状态则可能不同。

g 的 finally 又执行 return，覆盖了 try 原本准备返回的 1，所以得到 2。更严重的是，finally 的 return 还可能掩盖 try 中抛出的异常。因此应避免这种写法。

“finally 任何情况都执行”不准确：进程被强制终止、VM 崩溃、调用退出导致进程结束等情形，不能保证执行；try 如果一直不结束，也不会凭空进入 finally。

#### J17 解析｜先问需要哪种语义

1. **ArrayList**：下标读取 O(1)，追加通常高效。
2. **HashSet**：表达集合去重，不要求稳定顺序。
3. **LinkedHashMap**：默认保持插入顺序；它也可用不同构造方式选择访问顺序，本题按默认插入顺序。
4. **TreeMap**：按自然顺序或比较器维持键序。
5. **PriorityQueue**：默认最小元素优先；取最小用 `peek/poll`，不是指 for-each 一定从小到大。
6. **ArrayDeque**：可作为 FIFO 队列，队尾入、队头出；不放 null。

多种实现可能满足要求，关键是说明权衡。例如不应为只想查找的任务，无条件付出有序树的维护成本。

#### J18 解析｜链表 O(1) 的前提是“已定位”

ArrayList 按下标访问 O(1)，中间插删通常需移动后续元素，O(n)；LinkedList 按下标需要沿链走，通常 O(n)，但已经拿到合适迭代器/结点位置时，局部连接修改可为 O(1)。

二者按任意值线性查找通常都是 O(n)。ArrayList 使用内部数组，局部性通常较好，但容量可能有空余；LinkedList 每个元素有结点对象和前后链接等额外开销，常有更多分配及指针跳转。

均摊 O(1) 意思是：虽然某次追加可能触发扩容和复制，达到 O(n)，但按适当扩容策略考察足够长的追加序列，总体可摊为每次常数级成本。不是“每次操作都保证常数时间”。

**纠正原句：**先定位再插入的总代价，不能只算改链接；实际速度还受缓存、分配、数据量等影响。

#### J19 解析｜键是按逻辑相等合并的

**输出：**

```text
3
2
null
null
true
```

第二次 put 的 key 虽是新 String 对象，但与 `"a"` equals 相等，覆盖已有映射的值，不新增一个键。最终键为逻辑上的 `"a"`、null、`"b"` 三个。

`get("b")` 与 `get("missing")` 都得到 null，不能只靠返回值区分原因；可结合 `containsKey` 判断。

HashMap 允许 null 键、null 值，但不保证遍历顺序。某次运行看起来固定，不等于 API 承诺。也不要把 HashMap 的 null 规则直接套到 ConcurrentHashMap、TreeMap 等不同实现上。

#### J20 解析｜放入后的键不能悄悄换“身份依据”

集合插入时依据当时的哈希值组织存储；查找时依据当前状态重新计算哈希并判断相等。若 id 改变，查找可能走到不同位置，或与存储时记录的哈希不匹配。

即使查询参数是同一个对象，数据结构也未必会扫描整个集合寻找这个引用，因此不能保证找到。对影响相等比较的字段在集合内原地修改，会破坏哈希集合使用前提；本题不要武断写成“每一种实现和每一种哈希函数下都一定 false”。

安全方案：①用于相等和哈希的 id 不可变，字段 final，设计不可变键；②确有需要时，在修改前先按旧状态移除，修改后重新加入，并处理可能与已有键冲突的业务情况。也可直接使用独立、稳定的不可变标识符作为 Map 的键。

#### J21 解析｜同名 remove 与数组视图

**①最终输出 `[1]`。**`remove(1)` 参数为 int，调用按下标删除的方法，删掉下标 1 的元素 2，剩 `[1,3]`；`remove(Integer.valueOf(3))` 调用按对象删除，删掉值 3。

**②先输出 `X`，然后 `add` 抛 UnsupportedOperationException。**`Arrays.asList(raw)` 是背靠原数组的固定长度列表视图。它允许 `set` 替换已有元素，而且原数组可看到更改；但不能通过它增加或减少长度。固定长度不等于完全不可改。

**③输出 1。**泛型不能把 `int[]` 自动展开为若干 Integer。这里把整个 int 数组作为一个元素，得到 `List<int[]>`。若需要整数列表，可逐项装箱或用 `Arrays.stream(nums).boxed().collect(...)`。

#### J22 解析｜未知的具体子类型，不能随便塞值

1. 不可以。泛型通常是不变的：若 `List<Integer>` 能当 `List<Number>`，别人就能通过 Number 列表放入 Double，破坏原列表的 Integer 约束。
2. `src.add(1)` 不可编译，因为 `? extends Number` 的具体类型未知，也可能是 Double；但读出的元素可以当 Number。null 是一个特殊可添加值，不能由此误说完全不存在 add 调用。
3. `dst.add(1)` 合法，因为它表示 Integer 的某个超类型的列表；读出的结果只保证为 Object，不能无条件赋给 Integer。
4. **Producer Extends，Consumer Super**：把结构当数据生产者读，常用 extends；当 Integer 消费者写，常用 super。`List<int>` 不合法，应使用 `List<Integer>`。

**易错点：**PECS 是设计泛型参数的经验法，不是“某种通配符一定完全只读/只写”的绝对规则。

#### J23 解析｜比较器做减法，可能把方向反过来

int 最小值为 −2147483648。数学上 `MIN_VALUE-1` 更小，但 int 溢出后得到 2147483647，是正数。于是 bad 错误声称最小 int 大于 1。

安全写法：

```java
Comparator<Integer> asc = Integer::compare;
Comparator<Integer> desc = (a, b) -> Integer.compare(b, a);
// 也可 Comparator.naturalOrder() / Comparator.reverseOrder()
```

比较器只要求返回负数、0、正数来表示小于、等于、大于，不要求负数恰为 −1、正数恰为 1。还应满足一致的比较合同，例如传递性，不能任意返回相互矛盾的结果。本题输入不含 null；若可能含 null，应明确 nullsFirst/nullsLast 等政策。

#### J24 解析｜流是一条一次性处理流水线

前两行输出：

```text
[1, 9, 25]
[1, 2, 3, 4, 5]
```

filter 留下 1、3、5，map 平方得 1、9、25，collect 执行终结操作并收集结果。这些操作没有修改原列表元素或结构，所以 nums 保持原样。

创建过滤流水线时不立即遍历全部元素，属于惰性中间操作，通常在终结操作时执行。流已经被连接并消费，最后 `s.count()` 是非法复用；本例在标准 JDK Stream 实现中抛 IllegalStateException。需要重新计算时，从源头重新 `nums.stream()` 构造流水线。

**易错点：**Stream 不是可反复读取的容器，也不等于创建后已经算好的结果列表。

#### J25 解析｜线程执行与锁拥有权分别判断

`start()` 请求启动新的线程，由新线程执行 run；直接调用 `run()` 在当前调用线程正常执行。一个 Thread 对象只能启动一次，再次 start 会抛 IllegalThreadStateException，即使第一次已经执行完。

`sleep` 让当前线程暂停一段时间，但不释放其已经持有的监视器锁。调用 `obj.wait()` 必须拥有 obj 的监视器，通常位于 `synchronized(obj)` 内；等待时释放的是 **obj 这一把监视器锁**，不是所有锁，恢复前还需重新获得它。应配合条件循环，处理虚假唤醒和中断。

甲持有 A 等 B、乙持有 B 等 A，可能形成循环等待而死锁。若所有线程都严格先锁 A 后锁 B，就可消除这一例中的反向锁顺序。四个常见必要条件是互斥、占有并等待、不可抢占、循环等待；破坏适当条件是预防思路，不是用 sleep “碰碰运气”。

#### J26 解析｜“大家看得到”不等于“整步不可分割”

**不能保证最终为 20000。**`count++` 可理解为读旧值、计算加一、写回三个阶段。可能交错：

```text
甲读到 5
乙也读到 5
甲算出并写入 6
乙算出并写入 6
```

两次自增只得到一次增量。volatile 不把这整个读—改—写操作合成一个不可分割动作。主线程 join 保证等待完成及相关可见性，但不能修复此前已经发生的丢失更新。

修复一：所有相关自增由**同一把锁**保护，例如在同一共享对象的 synchronized 方法内执行。修复二：

```java
AtomicInteger count = new AtomicInteger();
// 两线程内：
count.incrementAndGet();
// 两线程均 join 后：
System.out.println(count.get());
```

若业务涉及多个字段的不变式，单个原子计数器也不自动保证整个业务原子性，应选择合适同步范围。

#### J27 解析｜区分抽象内存区域和具体实现

从 JVM 规范抽象模型理解：堆是线程共享、用于类实例和数组分配的运行时区域；每线程 JVM 栈保存方法调用的栈帧，含局部变量表、操作数栈等；方法区是共享的、保存类相关运行时结构的区域，例如方法数据、代码、运行时常量池等。

不要背成“所有基本类型在栈、所有引用在堆”：对象里的 int 字段与局部引用变量就能反驳这种过度简化。HotSpot 的元空间是方法区相关实现的一部分；逃逸分析、标量替换等优化也会让机器级布局不同于初学者画的盒子图。

方法返回不等于新建对象立即回收：对象可能通过返回值、其他对象字段等仍被引用；即使已经不可达，也只是具备回收资格，时机不由这条语句保证。

互相引用的对象若均无 GC Roots 可达路径，循环本身不阻止基于可达性分析的回收。相反，静态集合长期强引用已经不再需要的对象，会导致这些对象一直可达，形成逻辑上的内存泄漏。

#### J28 解析｜先问“出现几次”，再问“谁最先”

**参考实现：**

```java
static int firstUnique(String s) {
    if (s == null || s.isEmpty()) return -1;
    int[] count = new int[26];
    for (int i = 0; i < s.length(); i++) {
        count[s.charAt(i) - 'a']++;
    }
    for (int i = 0; i < s.length(); i++) {
        if (count[s.charAt(i) - 'a'] == 1) return i;
    }
    return -1;
}
```

第一遍把每个字母出现次数记清楚；第二遍按**原字符串下标**扫描，第一个计数为 1 的就是答案。不能遍历 count 从 a 到 z 找第一个，因为那会变成字母序，而非出现顺序。

时间 O(n)，计数数组固定 26 项，额外空间 O(1)。输入只含小写英文字母是明确前提；若换成任意 Unicode 文本，应重新定义“字符”和返回下标语义，不能直接照搬 `char-'a'`。

检查边界：null、空串、全重复、唯一字符在首位/中间/末尾。只测试题中一个示例不足以说明程序正确。



### B. 概率逐题解析

#### P01 解析｜“或者”要减去重复计算的交集

**答案：0.8、0.2、0.5。**

并集：`P(A∪B)=0.6+0.5−0.3=0.8`。直接相加会把 A、B 同时发生的部分算两遍，所以减一次交集。

都不发生是并集的补事件：`1−0.8=0.2`。

恰好一个发生包含“只 A”和“只 B”：

```text
只 A：0.6−0.3=0.3
只 B：0.5−0.3=0.2
恰好一个：0.3+0.2=0.5
```

也可直接用 `P(A)+P(B)−2P(A∩B)`。检查：都不发生 0.2＋恰好一个 0.5＋同时发生 0.3＝1，分类完整。

#### P02 解析｜抽样是否放回决定了模型

**答案：恰好 2 红 1 白为 15/28；至少 1 白为 23/28。**

抽取的 3 球不计顺序，总体共有 `C(8,3)=56` 个等可能的三球组合。

```text
恰好 2 红 1 白：C(5,2)C(3,1)/C(8,3)
              =10×3/56=15/28
至少 1 白：1−P(全红)
         =1−C(5,3)/C(8,3)
         =1−10/56=23/28
```

这属于超几何模型。不能精确按 Bin(3,5/8) 算，因为不放回时，各次抽取不独立，抽走一个球会改变剩下的组成。若总体巨大而抽样比例很小，有时可用二项近似，但本题没有必要也没有给这种近似要求。

**记录顺序时：**共有 `A(8,3)=8×7×6=336` 个等可能结果。每个三球组合对应 `3!=6` 种排列，分母从 56 变成 336，前两问的有利结果数也同样乘 6，因此概率不变。组合问“选哪些”，排列还问“先后怎么排”；样本空间计数方式变了，不代表同一事件的概率就应改变。

**易错点：**如果分母数的是无序组合，分子也必须数无序组合。不能分子乘排列，分母却不乘。

#### P03 解析｜条件出现后，分母已不是 36

**答案：2/11。**

设 B＝至少一颗为 6，A＝点数和为 8。原本有 36 个等可能有序结果，但已知 B 后，要限制到 B 内。

第一颗为 6 有 6 个结果，第二颗为 6 也有 6 个，`(6,6)` 重复，因此 B 内有 `6+6−1=11` 个结果。既满足和为 8、又至少一个 6 的结果只有 `(6,2)`、`(2,6)` 两个。

所以 `P(A|B)=2/11`。若用公式，也有 `(2/36)/(11/36)=2/11`。

**对比：**不附加条件时，“和为 8”有 5 个结果，概率是 5/36。题目加的条件既改变分母，也限制有利结果，不能只换一个数字。

#### P04 解析｜两个概念使用不同的检验式

第一组：`P(A)P(B)=0.4×0.5=0.2=P(A∩B)`，因此**独立**；交集概率 0.2 不是 0，所以**不互斥**。

第二组：互斥意味着交集为空、概率为 0；但 `P(C)P(D)=0.06`，不等于 0，所以**不独立**。

最后一句错误。独立不禁止同时发生，例如两次独立抛硬币都正面就能同时发生。若知道 C 发生，互斥的 D 就绝不会发生，其概率从原本 0.3 变为 0，显然被改变了。

**边界提醒：**“互斥与独立一定不能同时成立”的表述也过强；概率为 0 等退化情形需要另看。因此常用结论要加上两个事件概率均大于 0 的前提。

#### P05 解析｜无条件的第二次与给定第一次不是同一道题

**答案：3/5、3/4、不独立。**

求第二球红，用第一球颜色分类：

```text
P(第二红)
= P(第一红)P(第二红|第一红)
+ P(第一白)P(第二红|第一白)
= (3/5)(2/4)+(2/5)(3/4)
= 3/10+3/10=3/5
```

也可用对称性：随机排列全部球，每个位置为红的边际概率都是 3/5。

已知第一白后，袋里剩 3 红 1 白，所以第二红是 3/4。两次红事件不独立，因为 `P(第二红|第一红)=2/4=1/2`，不同于无条件的 3/5。

**易错点：**第二次仍有红球概率 3/5，并不意味着“剩余组成没有变化”；它是把不同第一球情况加权后的结果。

#### P06 解析｜并联常用“所有都坏”的补事件

**答案：0.72、0.98、约 0.6513。**

串联式要求都正常：独立条件下 `0.9×0.8=0.72`。

并联式只需一台正常，反面是两台都坏：`1−(1−0.9)(1−0.8)=1−0.02=0.98`。

10 次请求至少失败一次，反面是 10 次全成功：`1−0.9¹⁰≈0.65132156`。

**为什么不直接算 10×0.1？**各次失败事件可以同时发生，直接相加会重复计算多次失败的情况。`10×0.1=1` 是失败次数的期望，不是“至少一次失败”的概率。

若设备故障相关，以上简单相乘不能直接用；题目明确给的“独立”是关键条件。

#### P07 解析｜先算“各来源贡献了多少次品”

**答案：次品率 1.8%；次品来自 B 的概率为 2/3。**

设 D 为次品。A 的贡献为 `0.6×0.01=0.006`，B 的贡献为 `0.4×0.03=0.012`，合计：

```text
P(D)=0.006+0.012=0.018
P(B|D)=P(B∩D)/P(D)=0.012/0.018=2/3
```

可画成一棵概率树：先按来源分 A/B，再分别按是否次品分支；到同一类叶子沿路径相乘，各次品叶子再相加。

直观上，B 虽只供应 40% 产品，但次品率更高，所以在“已经确定是次品”的子群里，B 占比会升高。不能直接拿原供应比例 40% 当答案。

#### P08 解析｜低患病率会放大假阳性人群的影响

**答案：1/6，约 16.67%，不是 99%。**

设 D＝患病，+＝阳性：

```text
P(D|+) = P(D)P(+|D) / [P(D)P(+|D)+P(Dᶜ)P(+|Dᶜ)]
       = 0.01×0.99 / (0.01×0.99+0.99×0.05)
       = 0.0099/0.0594=1/6
```

用题设比例对应的 10000 人频数理解：

| 真实状态 | 人数 | 阳性人数 |
|---|---:|---:|
| 患病 | 100 | 99 |
| 未患病 | 9900 | 495 |
| 合计 | 10000 | 594 |

在 594 个阳性中，真正患病的是 99 个，因此 `99/594=1/6`。频数是按概率比例构造的解释，不是在声称现实样本一定恰好得到这些人数。

**易错点：**`P(阳性|患病)` 与 `P(患病|阳性)` 方向相反。基率、灵敏度、假阳性率三个信息都用上才完整。

#### P09 解析｜组合数负责“成功在哪几次”

**答案：X~Bin(5,0.6)。**满足固定 5 次、每次只有答对/答错、独立、成功率相同四个条件。

```text
P(X=3)=C(5,3)×0.6³×0.4²
      =10×0.216×0.16=0.3456
P(X≥1)=1−P(X=0)=1−0.4⁵=0.98976
E(X)=np=5×0.6=3
Var(X)=np(1−p)=5×0.6×0.4=1.2
```

`0.6³×0.4²` 只是某一个指定顺序（如对对对错错）的概率；恰好 3 次成功有 `C(5,3)` 种位置组合，所以不能漏组合数。

期望为 3 不是保证每次都答对 3 题，而是重复大量同模型试验时平均题数的中心位置。

#### P10 解析｜第 k 次首次成功＝前面全失败，最后成功

**答案：P(X=3)=0.128，P(X>4)=0.4096，E(X)=5，Var(X)=20，条件概率=0.64。**

```text
P(X=3)=0.8²×0.2=0.128
P(X>4)=前4次都失败=0.8⁴=0.4096
E(X)=1/p=5
Var(X)=(1−p)/p²=0.8/0.04=20
P(X>6|X>4)=0.8⁶/0.8⁴=0.8²=0.64
```

无记忆性：在已经失败 4 次的条件下，接下来还要超过 2 次才能等到首次成功的概率，与刚开始时前 2 次都失败的概率相同。独立且成功率不变的试验，不会因为前面失败多了就“该成功了”。

**易错点：**X 数的是总尝试次数，因此幂次是 k−1，期望是 1/p；若数成功前失败次数，公式要相应平移。

#### P11 解析｜E(X²) 和 [E(X)]² 要分别算

概率总和为 1：`a+2a+a=4a=1`，所以 a=1/4。

```text
E(X)=0×1/4+1×1/2+2×1/4=1
E(X²)=0²×1/4+1²×1/2+2²×1/4=1.5
Var(X)=1.5−1²=0.5
E(Y)=3E(X)+2=5
Var(Y)=3²Var(X)=9×0.5=4.5
```

加上常数 2，只把整体分布平移，离散程度不变；乘以 3，把与均值的偏差也乘 3，偏差的平方就乘 9。

**易错点：**不能把 E(X²) 直接写成 E(X)²；也不能把方差变换写成 `3Var(X)+2`。

#### P12 解析｜先把收益定义成“奖金减成本”

**答案：每轮 −1 元；100 轮 −100 元；计算总期望不要求独立。**

掷出 6 时净赚 `12−3=9` 元，其他五种点数净收益 −3 元：

```text
E(净收益)=9×(1/6)+(−3)×(5/6)=−1
```

也可先算奖金期望 `12×1/6=2`，再减确定成本 3，得到 −1。玩家长期平均意义上处于负收益，不是公平游戏；若其他规则不变，使净期望为 0 的入场费是 2 元。

设第 i 轮净收益为 Yi，只要相应期望存在，`E(ΣYi)=ΣE(Yi)=−100`，不需要独立。独立性会影响联合分布、总方差等，但不是期望线性的前提。

**注意：**期望损失 100 元不是说每次玩 100 轮就必然恰好亏 100 元。

#### P13 解析｜先统一分钟，再调整 λt

**答案：约 0.1804、0.6321；等待超过 30 秒概率约 0.3679，均值 0.5 分钟；再等超过 30 秒仍约 0.3679。**

速率是每分钟 2 次。长度 t 分钟内次数服从 Pois(2t)，所以：

```text
1分钟恰3次：e⁻²×2³/3!=(4/3)e⁻²≈0.180447
30秒=0.5分钟，参数为1
30秒至少1次：1−e⁻¹≈0.632121
```

等待时间 T 服从速率为 2 的指数分布。`P(T>t)=e^(−2t)`，因此 `P(T>0.5)=e⁻¹≈0.367879`，均值 `1/2` 分钟。

已经等了 0.5 分钟后，再至少等 0.5 分钟：

```text
P(T>1 | T>0.5)=P(T>1)/P(T>0.5)=e⁻²/e⁻¹=e⁻¹
```

连续型下“至少/超过”这个端点差异不影响概率。该结论依赖题目给出的齐次泊松过程模型，不能因为现实请求平均每分钟 2 次，就自动断言所有这些分布条件都成立。

#### P14 解析｜密度先归一化，概率再积分

**第一问：k=1/2。**总面积必须为 1：`∫从0到2 kx dx = 2k = 1`。

分布函数：

```text
F(x)=0，                     x≤0
F(x)=∫从0到x t/2 dt=x²/4，   0<x<2
F(x)=1，                     x≥2
```

因此 `P(1<X<2)=F(2)−F(1)=1−1/4=3/4`。连续型变量在单点的概率为 0，所以 `P(X=1)=0`，不是密度值 f(1)=1/2。

期望：`E(X)=∫从0到2 x·(x/2)dx = [x³/6]从0到2 = 4/3`。较大的 x 处密度更高，均值大于区间中心 1，符合直觉。

均匀变量 U 的概率是长度比：`(7−3)/(10−0)=0.4`；均值 5；方差 `10²/12=25/3`。

**易错点：**F 是从最左端累积到 x 的概率；f 是密度。看到 F 和 f，先分清大写小写含义。

#### P15 解析｜标准化时除标准差，不是方差

对第一问，`Z=(X−60)/10`，区间变为 −1 到 1：

```text
P(50≤X≤70)=Φ(1)−Φ(−1)=0.8413−0.1587=0.6826
```

25 个独立正态变量的均值**精确**服从正态：均值 60，方差 `100/25=4`，标准差 `10/√25=2`。所以 58～62 又正好是均值上下一个标准差，概率也是 0.6826。

若原总体不正态，不能宣称 n=25 就使平均值精确正态。中心极限定理说明，在适当条件下（这里用独立同分布、有限且正的方差），标准化样本和/均值随样本量增大趋向标准正态，可用于近似；不是一个达到 25 或 30 就突然精确成立的开关。

**易错点：**样本均值的标准差是 `σ/√n`，不是 `σ/n`。这就是“平均以后波动更小”的量化表达。

#### P16 解析｜先算补事件，再看信息是怎样被产生的

**生日题：约 0.5073。**反面是所有生日互不相同：

```text
P(全不同)=(365/365)(364/365)…(343/365)
P(至少两人同生日)=1−上述乘积≈0.507297
```

第 1 人没有限制；第 2 人要避开 1 个日期；第 23 人要避开 22 个已占日期，因此最后一项是 343/365。23 人有 253 对，不是只拿某个指定的人与其他人比较，所以碰撞概率上升得比直觉快。`C(23,2)/365` 不能直接当碰撞概率，因为不同“配对同生日”事件会重叠。

**三门题：始终换门赢 2/3。**按第一次选择是否正确分类：

| 初选 | 概率 | 主持人按规则开羊门后，换门结果 |
|---|---:|---|
| 一开始选到车 | 1/3 | 换到羊，输 |
| 一开始选到羊 | 2/3 | 另一未开门为车，赢 |

主持人的开门行为不是毫无信息的随机删除；他知道答案、保证开羊门、总让你换门，这套机制保留了“初选错误”占 2/3 的优势。若改变规则，例如主持人不知道位置并随意开门，就必须重新按新的信息产生机制计算，不能照搬 2/3。



### C. 树结构逐题解析

#### T01 解析｜边数可由树性质得出，高度不能瞎补

**答案：12 条边；R 的度为 2，A 的度为 3；高度和叶子数不能确定；森林有 16 条边。**

任意一棵含 n 个结点的非空树有 n−1 条边，因此 13−1=12。不需要知道每个结点放在哪一层。

“度”在这里指孩子数，不是父边与子边相加的无向图度数。R 有 A、B 两个孩子；A 有 C、D、E 三个孩子。

没有指定剩余结点连接位置，可能继续接成长链，也可能分散接到不同分支，高度和叶子数因此不唯一。不能为了给出数字而自行假设缺失结构。

森林的边数是每棵树的 `(结点数−1)` 相加，总计 `20−4=16`。

#### T02 解析｜同一组边，用两种方式计数

设三类结点数量为 n0、n1、n2，则 `n=n0+n1+n2`。

按“每个非根结点有一条父边”，边数为 n−1；按“每个结点贡献几条孩子边”，边数为 `n1+2n2`。所以：

```text
n0+n1+n2−1 = n1+2n2
n0 = n2+1
```

给定 n0=20，得 n2=19；再加 n1=7，得 `n=20+19+7=46`，边数 45。

**易错点：**公式适用于非空二叉树，不要求完全、满或平衡；但不能直接套到任意多叉树，也不能拿空树 n0=0、n2=0 代入。

#### T03 解析｜最少拉成链，最多层层填满

1. 高度 5 最少有 5 个结点：每层一个，形成长链。最多 `2⁵−1=31` 个。
2. 100 个结点尽量压低时，需找到最小 h 使 `2ʰ−1≥100`。6 层最多 63，不够；7 层最多 127，够，所以最小高 7。拉成一条 100 结点链，最大高为 100。
3. 完全二叉树紧凑靠左排列，`floor(log₂100)+1=7`。
4. 根在第 1 层，第 5 层最多 `2^(5−1)=16` 个。

**易错点：**若题目按最长向下路径的边数定义高度，非空树的高度应比本讲义少 1。本讲义按层数计高，所以单结点高 1；不要把“根的深度为 0”与“整棵树的高度”混淆。

#### T04 解析｜不存在的数组下标不是实际孩子

从 1 编号时，结点 10 父编号是 `floor(10/2)=5`。结点 5 左孩子 10 存在，右孩子候选 11 超过 n=10，因此没有右孩子。

最后一个非叶结点为 `floor(n/2)=5`；叶子是 6、7、8、9、10，数量 5。不要把结点 5 因为缺右孩子就当成叶子，它还有左孩子。

从 0 编号改为：

```text
左孩子：2i+1
右孩子：2i+2
父结点：floor((i−1)/2)，只对 i>0 使用
```

根没有父结点；左右孩子编号要小于 n 才存在。编号规则必须一开始统一，不能父公式用 1 起始、孩子公式用 0 起始。

#### T05 解析｜看“层形状”和看“每个结点孩子数”是两件事

**甲：不是满，是完全，不是严格。**甲的末层有 D、E、F，从左到右连续占据三个位置，其上各层满，因此完全。末层没有全部占满，所以非满；C 只有一个孩子，所以非严格。

**乙：不是满，不是完全，是严格。**乙每个非叶结点 A、C 都有两个孩子，所以严格；但末层在右子树下有结点，左子树相应位置为空，不满足靠左连续，所以非完全，更不是满。

**记忆结论：**满二叉树一定完全且严格，但严格不推出完全，完全也不推出严格。英语 full 在常见教材中指 0/2 孩子性质，考试看到中英文名词时，务必核对它给出的定义。

#### T06 解析｜把“访问根”的时机固定下来

**答案：**

```text
前序：A B D E G C F
中序：D B G E A C F
后序：D G E B F C A
层序：A B C D E F G
高度：4
```

前序先 A，再完整遍历 B 子树（B、D、E、G），再 C 子树（C、F）。中序要先完成整个左子树：D、B、G、E，然后 A，再 C、F。后序中 B 要等 D、E 子树处理完才访问，E 又要等 G，因此左半段为 D、G、E、B。

层序按队列顺序：A；B/C；D/E/F；G。根到 G 的路径有 4 个结点、3 条边，按本讲义树高为 4。

不是完全二叉树：C 左孩子缺失但右孩子 F 存在，出现“左侧空位之后还有结点”。

**训练方法：**每个结点分别标前/中/后三个访问时机，照规则读一次，比只背序列稳。

#### T07 解析｜前序找根，中序分左右

**重建结果：**

```text
          G
        /   \
       D     M
      / \   / \
     B   F J   P
```

后序是 `B F D J P M G`。

前序第一个是 G，所以 G 是根。中序在 G 左边的是 B、D、F，右边的是 J、M、P，因此左右子树各 3 个结点；前序余下部分相应切为 `D B F` 与 `M J P`。对子树重复：D 左 B 右 F，M 左 J 右 P。

**前序＋后序不一定唯一。**最小反例是 2 个结点：

```text
   A         A
  /           \
 B             B
```

两者前序都是 A B，后序都是 B A，但左右位置不同。本题前序＋中序能唯一重建依赖标签互不相同；重复标签会带来额外歧义。

#### T08 解析｜递归题先写空树，再写整树与子树的关系

**代码：**

```java
static int size(Node root) {
    if (root == null) return 0;
    return 1 + size(root.left) + size(root.right);
}
static int height(Node root) {
    if (root == null) return 0;
    return 1 + Math.max(height(root.left), height(root.right));
}
```

size：本结点 1 个，加左右子树的全部结点数。height：从根向下只能沿一条路径取最大层数，所以是左右高度的**最大值**再加根这一层，不是左右高度相加。

每个结点各访问一次，两个方法各自时间 O(n)。递归栈深度 O(h)：平衡时 O(log n)，链状最坏 O(n)。输入是合法无环树是前提；极深树还可能导致栈溢出，需要迭代实现或其他策略。

#### T09 解析｜BST 约束的是“整棵子树”

插入后：

```text
          50
        /    \
       30     70
      / \    / \
     20 40  60 80
```

中序 `20 30 40 50 60 70 80`。查 65：65>50 走右；65<70 走左；65>60 走右，遇空，查找失败。实际比较结点依次是 50、70、60。

50 的中序后继是右子树最小键 60。用 60 替换根，并从原位置删除 60：

```text
          60
        /    \
       30     70
      / \      \
     20 40     80
```

如果题目没限定，也可使用中序前驱，但本题指定后继，应按指定步骤。

查找、插入等主要代价随树高增长，为 O(h)。普通 BST 按已排序数据连续插入可能退化成长链，最坏 O(n)；平衡树才能在相应操作条件下给出 O(log n) 的高度保证。

#### T10 解析｜插入先放末尾，删顶先拿末尾补根

**插入 85：**先放下一个末位（第 8 个位置），与父 20 比，大则上浮；再与父 70 比，大则上浮；遇 90 停止。

```text
初放：[90,70,80,20,40,60,50,85]
一步：[90,70,80,85,40,60,50,20]
最终：[90,85,80,70,40,60,50,20]
```

**独立从初始堆删顶：**末尾 50 补到根，删除原末尾。下沉时选择较大的孩子 80 交换，再与 60 交换：

```text
补根：[50,70,80,20,40,60]
一步：[80,70,50,20,40,60]
最终：[80,70,60,20,40,50]
```

复杂度：看堆顶 O(1)，插入 O(log n)，删除堆顶 O(log n)，自底向上建堆 O(n)。

建堆不是 n 个结点都完整下沉 log n 层：大量结点接近叶层，移动很少，把各高度代价加起来是线性的。若采用“从空堆逐个插入”的建法，其一般最坏总成本才是 O(n log n)。

#### T11 解析｜LR 是先把折线拉直，再转根

普通插入后的形态：

```text
      30
     /
    10
      \
      20
```

30 左侧太高，新结点在“左孩子的右子树”，所以是 LR。先对 10 左旋，得到 30 的左孩子为 20、20 的左孩子为 10；再对 30 右旋：

```text

      /  \
     10  30
```

旋转保持中序序列不变，所以仍保持 BST 的键序，同时改变高度分布。

AVL 对每个结点要求左右高度差不超过 1；红黑树不使用这同一条逐结点高度差约束，而通过着色规则约束高度。二者均能维持对数级高度，但“都是平衡树”不等于平衡条件完全相同。

#### T12 解析｜每次只合并当前最小的两项

**合并过程：**

```text
5+9=14          剩12,13,14,16,45
12+13=25        剩14,16,25,45
14+16=30        剩25,30,45
25+30=55        剩45,55
45+55=100       完成
```

WPL 等于各叶权重乘以其到根的边数之和，也等于每次合并产生的新权值之和：

```text
WPL=14+25+30+55+100=224
平均码长=224/(5+9+12+13+16+45)=2.24 位/符号
```

可行编码之一：

| 符号 | 权值 | 编码 | 长度 | 权值×长度 |
|---|---:|---|---:|---:|
| A | 5 | 1100 | 4 | 20 |
| B | 9 | 1101 | 4 | 36 |
| C | 12 | 100 | 3 | 36 |
| D | 13 | 101 | 3 | 39 |
| E | 16 | 111 | 3 | 48 |
| F | 45 | 0 | 1 | 45 |

没有一个码字是其他码字的前缀，所以能从左到右无歧义解码。左右分支交换会得到不同但同样有效的编码，不能只认一种 0/1 排列。

**易错点：**WPL 中的路径长度按边数/码长计，不是本讲义“树高按层数”中的层号。

#### T13 解析｜每层都要继承祖先留下的范围限制

该树**不是 BST**。6 虽小于其直接父结点 15，但它处在根 10 的右子树中，必须大于 10，因此不合法。只检查直接父子关系，会遗漏祖先约束。

**参考代码：**

```java
static boolean isValidBST(Node root) {
    return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);
}
static boolean valid(Node node, long low, long high) {
    if (node == null) return true;
    long v = node.val;
    if (v <= low || v >= high) return false;
    return valid(node.left, low, v)
        && valid(node.right, v, high);
}
```

范围取开区间 `(low,high)`。进入左子树时提高要求为 `<当前值`；进入右子树时要求 `>当前值`，同时保留更远祖先的界限。

初始用 long 上下界，允许 int 最小值和最大值作为合法结点，不必通过 `val−1`/`val+1` 调整边界，从而避免溢出。严格不等式表示不允许重复键；若业务允许重复，必须重定义重复放哪边及校验规则。

每结点至多访问一次，O(n) 时间；递归辅助空间 O(h)。

#### T14 解析｜磁盘访问次数比“指针少写几行”更关键

**按常见教材模型：**B 树的非叶和叶结点都可以存储键对应的记录或记录指针；B+ 树非叶结点主要存索引分隔键和子指针，所有记录项/记录指针在叶层，叶结点通常按键序连接。

B+ 树定位到范围起点后，可以沿叶链顺序扫描后续键，适合范围查询；B 树并非不能做范围查询，只是遍历组织方式不同。具体数据库的聚簇/非聚簇索引、叶层存整行还是主键/行定位符等，是实现细节，不可一概而论。

多路结点可以利用一个磁盘页容纳许多键和子指针，扇出大，树更矮，访问少数几层就能缩小搜索范围；平衡性避免普通 BST 退化为长链。缓存和页布局同样重要，并非“所有情况下 B+ 树都绝对最快”。

题目给出最多 m 个孩子，则对应最多 **m−1 个关键字**：m 个孩子区间用 m−1 个分隔键区分。其他教材可能用最小度 t 等参数，因此要先读定义。

#### T15 解析｜bit[i] 存的是一段区间，不是第 i 个原值

6 的二进制为 110，最低有效 1 对应 2，所以 lowbit(6)=2。bit[6] 覆盖 `[6−2+1,6]=[5,6]`，初值 `5+2=7`。

查前缀 6，先加 bit[6]，再跳到 `6−2=4` 加 bit[4]，再跳到 0 结束：`7+(2+1+3+4)=17`。原 `[3,6]` 和为 `sum(6)−sum(2)=17−3=14`。

更新 a[3] 加 2：下标依次 `3→4→8`，分别给覆盖 a[3] 的聚合区间加 2。更新后 sum(6)=19，[3,6] 和=16。bit[6] 自身不含 a[3]，不需要改。

**核心代码（bit 为长度 n+1 的 long 数组）：**

```java
static void add(long[] bit, int i, long delta) {
    if (i <= 0 || i >= bit.length) {
        throw new IllegalArgumentException("index out of range");
    }
    for (; i > 0 && i < bit.length; i += i & -i) {
        bit[i] += delta;
    }
}
static long sum(long[] bit, int i) {
    if (i < 0 || i >= bit.length) {
        throw new IllegalArgumentException("index out of range");
    }
    long ans = 0;
    for (; i > 0; i -= i & -i) {
        ans += bit[i];
    }
    return ans;
}
// 区间[l,r]：sum(bit,r)-sum(bit,l-1)
```

单次更新、前缀查询均 O(log n)，存储 O(n)。使用 long 降低普通 int 求和溢出风险，但仍不是无限精度。更新循环中的 i>0 也避免极大下标下一跳发生 int 溢出后继续访问负下标。add 的索引必须从 1 开始，i=0 会让 lowbit 为 0，若不校验会陷入不前进的循环。

**学习优先级：**如果考纲只说普通树结构，先稳住 T01–T10；本题属于扩展，不必一开始就在位运算上耗时。

#### T16 解析｜一轮只处理“进入这一轮之前”的结点

**参考实现：**

```java
static List<List<Integer>> levelOrder(Node root) {
    List<List<Integer>> ans = new ArrayList<>();
    if (root == null) return ans;
    Deque<Node> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int levelSize = queue.size();
        List<Integer> level = new ArrayList<>();
        for (int i = 0; i < levelSize; i++) {
            Node node = queue.poll();
            level.add(node.val);
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
        ans.add(level);
    }
    return ans;
}
```

每层开始时队列恰好装有这一层的结点数。处理当前层时，新孩子会加入队尾，属于下一层，所以必须保存 levelSize；不能让本轮循环边界跟着变化后的 queue.size 走。

示例得到 `[[3],[9,20],[15,7]]`。每结点入队、出队各一次，时间 O(n)；不计结果，辅助队列空间 O(w)，w 为最大层宽，最坏 O(n)。若把返回结果也计入，结果本身需要 O(n) 空间。

ArrayDeque 不接收 null，所以入队前判断左右孩子是否为空；空树也要先返回。



### D. ER 图逐题解析

#### E01 解析｜先说“有哪些东西”，再说“它们有什么关系”

**答案：**

- **实体（entity）**：业务中能够区分的对象。例如某一位学生、某一门课程。画图时通常画的是“学生”“课程”这样的实体类型，而不是把每位学生都画一个框。
- **属性（attribute）**：对实体或联系的描述。例如学生的学号、姓名，课程的学分，选课联系上的成绩。
- **联系（relationship）**：实体之间的关联。例如“学生选修课程”“教师讲授课程”。联系不是操作步骤。

Chen 记法：

| 图形 | 含义 | 例子 |
|---|---|---|
| 矩形 | 实体类型 | 学生、课程 |
| 菱形 | 联系类型 | 选修 |
| 椭圆 | 属性 | 姓名 |
| 属性名下划线 | 键属性 | 学号 |
| 双椭圆 | 多值属性 | 一个人的多个联系电话 |
| 虚线椭圆 | 派生属性 | 由出生日期和当前日期算出的年龄 |

补充：双矩形常表示弱实体，双菱形常表示标识联系；弱实体的部分键常用虚线下划线。具体考试应遵守题干采用的记法，不同工具的符号可能不同。

第 3 问**错误**。ER 图主要描述数据结构和业务约束；“先登录，再付款，再发货”的执行顺序更适合流程图或活动图。ER 图中的连接线也不是按时间前后执行的箭头。

**做题口诀：**名词里找实体，描述里找属性，动词里找联系；但最后仍要根据业务含义判断，不能只按词性机械划分。

#### E02 解析｜姓名不唯一，年龄会随时间变

**答案：**学号是合适的键；地址是复合属性；联系电话是多值属性；年龄是派生属性。

1. **键属性：学号。**题目保证它唯一。姓名可能重名，不能据此唯一识别学生。
2. **复合属性：地址。**它可拆成省、市、街道。关系表中可分别设 `province`、`city`、`street` 列；是否进一步结构化取决于业务查询需要。
3. **多值属性：电话。**同一学生可能有多个电话号码。
4. **派生属性：年龄。**它由出生日期与计算时点推导。一般保存 `birth_date`，查询时按日期计算实足年龄，不能简单认为“当前年份减出生年份”总是准确，因为还要看当年生日是否已到。

若需要保留“入学时年龄”等历史事实，应明确记录该时点或相关快照；这与存一个永远不更新的“当前年龄”不是同一语义。

电话的典型关系设计：

```text
Student(
  sid PK,
  name,
  province, city, street,
  birth_date
)
StudentPhone(
  sid FK → Student.sid,
  phone,
  PK(sid, phone)
)
```

`StudentPhone` 中一个电话占一行；复合主键防止同一学生重复登记同一号码。题目没有说不同学生不能共用联系电话，所以不能擅自给 `phone` 单列加全局唯一约束。

逗号拼接字符串会把多个业务值塞入一列，使按号码查询、去重、单个号码修改和约束检查变得困难。对于本题的常规关系模型，应拆成子表；不要用字符串拼接代替关系设计。

#### E03 解析｜“最多几个”和“至少几个”是两件事

| 场景 | 最大基数 | 从左方看右方 | 从右方看左方 |
|---|---|---|---|
| 部门—员工 | 1:N | 一个部门有 0..N 名员工 | 一名员工属于 1..1 个部门 |
| 用户—档案 | 1:1 | 一个用户有 0..1 份档案 | 一份档案属于 1..1 个用户 |
| 学生—课程 | M:N | 一个学生选 0..N 门课程 | 一门课程由 0..N 名学生选修 |

`0..N` 中的 N 表示“多”，不是一个事先给定的固定人数。`1..1` 是恰好一个，`0..1` 是可有可无但最多一个。

**鸦脚表达：**

```text
Department ||--o{ Employee
```

读作：**每名员工必须且只属于一个部门；每个部门可以有零名或多名员工。**

- 靠近 Department 的 `||`，表达的是“一名员工对应多少个部门”：恰好一个。
- 靠近 Employee 的 `o{`，表达的是“一个部门对应多少名员工”：零到多个。

**易错点：**读鸦脚端点时，要从另一端的一个实例出发。最大基数 1:N 并不能单独告诉你“部门可不可以没有员工”，还必须看最小参与数。

#### E04 解析｜候选键要求“唯一而且不能再删字段”

**答案：**

1. `{sid}`、`{email}` 是候选键；题目列出的三组 **都是超键**。
2. 选择 sid 为主键后，email 是**备选键**。
3. dept_id **不必唯一**；是否允许 null 取决于业务规则，不能只看它是外键。
4. 外键不只能够引用“另一张表的主键”。

**为什么 `{sid,name}` 不是候选键？**因为只用 sid 已经可以唯一识别一行，name 是多余的。超键只要求能唯一识别；候选键还要求在包含关系上最小，即去掉任何属性后都不再是超键。这里的“最小”不是比较所有键的字符长度，也不要求所有候选键的字段个数相同。

多个学生可以属于同一部门，因此他们的 dept_id 可以相同。若业务规定每个学生必须属于一个部门，应加 `NOT NULL`；若允许尚未分配部门，可以允许 null。非空外键值必须满足相应引用约束。

在通常关系数据库中，外键可引用目标表符合数据库要求的唯一键，例如主键或相应的 `UNIQUE` 键；也可以**自引用同一张表**，如分类的 parent_id 引用 Category.category_id。具体可引用键及 null 的细节遵循所用数据库规则。仅给 email 加允许多个 null 的 UNIQUE，并不等同于题目中“唯一且非空”的候选键条件。

#### E05 解析｜把“一方的键”放在“多方”

**一种合理关系模式：**

```text
Department(
  dept_id PK,
  dept_name
)
Employee(
  emp_id PK,
  name,
  dept_id NOT NULL FK → Department.dept_id,
  joined_on NOT NULL
)
```

主键字段按主键语义唯一且非空。题目没有声明部门名或员工姓名唯一，不应擅自把它们当作候选键。

**步骤：**

1. 部门与员工是 1:N：一个部门可以被多行 Employee 引用。
2. 每名员工恰好一个部门：Employee 中的 dept_id 是单值、非空外键。
3. “加入当前部门的日期”描述的是**这名员工与其当前部门的联系**。因为每名员工当前最多只有这一条部门联系，可把 joined_on 一起并入 Employee。
4. 本题不保存调动历史；若改为保存历史，才需要另设计任职/调动记录及生效日期等，不能继续用一列覆盖全部历史。

部门号在 Department 中是它自己的**主键**；在 Employee 中才是引用部门的**外键**。不能把 Department 的 dept_id 理解为“员工外键”。把一个 emp_id 塞进 Department 也无法代表一个部门的多名员工。

**约束边界：**这套 PK/FK/NOT NULL 能防止员工引用不存在的部门，却不会强迫每个部门至少有一名员工；这正符合题目“部门可以为空”的规定。

#### E06 解析｜M:N 联系变成独立的关联表

**1. 概念 ER 图。**下图采用 Chen 风格：方框是实体、菱形是联系，圆括号是属性；文字注明键属性。学生、课程均为可选参与，不要求已有选课记录。

<!-- DIAGRAM:E06 -->
```text
 (学号 PK)  (姓名)                         (课程号 PK)  (课程名)  (学分)
      \      /                                  \       |       /
       [学生] -------- M ------ ◇选修◇ ------ N -------- [课程]
                                 /    \
                           (选课日期) (成绩，可空)

 每个学生可选 0..N 门课程；每门课程可被 0..N 名学生选修。
 PK 表示键属性；正式手绘 Chen 图时给属性名加下划线。
```
<!-- /DIAGRAM:E06 -->

**2. 转为关系表：**

```text
Student(sid PK, name)
Course(cid PK, title, credits)
Enrollment(
  sid NOT NULL FK → Student.sid,
  cid NOT NULL FK → Course.cid,
  enrolled_on NOT NULL,
  score NULL,
  PK(sid, cid)
)
```

逻辑上的两条 1:N 联系为：

```text
Student ||--o{ Enrollment
Course  ||--o{ Enrollment
```

一条选课记录恰好属于一个学生和一门课程；一个学生或一门课程都可以尚无选课记录。概念图中的“选修”是联系；转换到关系模型后，用 Enrollment 关联表保存它，不是把一门课程的多个学生号拼到同一列。

**3. 成绩的归属。**一个学生在不同课程中可能有不同成绩；一门课程中不同学生也有不同成绩。因此成绩依赖 `(sid,cid)` 这个组合，不是 sid 或 cid 单独决定的。放在 Student 表会导致“一名学生只能存一个成绩”；放在 Course 表会导致“整门课程只能存一个成绩”。

**4. 防重复。**`PRIMARY KEY(sid,cid)` 同时保证组合唯一与主键列非空，自然阻止重复选同一门课；再分别建立两条外键，保证学生和课程存在。即使另设 enrollment_id 为独立主键，也仍需 `UNIQUE(sid,cid)` 落实本题的防重规则。

**易错点：**“没出成绩”不等于 0 分。score 的 null 表达尚无成绩；0 是已经确定的数值。不要用 0 偷换“未知”。

#### E07 解析｜外键保证“找得到”，唯一约束保证“最多一个”

**方案一：共享主键。**

```text
User(user_id PK, ...)
Profile(
  user_id PK AND FK → User.user_id,
  ...
)
```

Profile 的 user_id 同时是主键与外键：

- PK 保证一个 user_id 在 Profile 中最多出现一次，并且非空。
- FK 保证这份 Profile 对应的 User 存在。
- User 中可以有某一行而 Profile 中没有对应行，体现用户可没有档案。

**方案二：档案有独立主键。**

```text
User(user_id PK, ...)
Profile(
  profile_id PK,
  user_id NOT NULL UNIQUE FK → User.user_id,
  ...
)
```

这里三类约束各司其职：FK 保证用户存在；UNIQUE 限制一位用户最多一份档案；NOT NULL 保证档案不能不属于任何用户。profile_id 只保证档案自己的编号不重复，不能代替 user_id 上的唯一约束。

**只有外键不够。**若 user_id 仅有 FK 而没有唯一性限制，多份档案可以都指向用户 1，这就变成了一对多。允许 null 的 UNIQUE 也不能自动代替“每份档案必须有用户”的要求。

这里的 User 是概念名称；实际写 SQL 时可改为 AppUser，避免与某些数据库的关键字冲突。

#### E08 解析｜弱实体需要“拥有者的键＋自己的部分键”

**答案：**部分键是 `line_no`，完整主键是 `(order_id,line_no)`。

例如订单 1001 第 1 行与订单 1002 第 1 行不是同一条明细，所以 line_no 不能在全部明细中单独作主键。先确定所属订单，再给出行号，才能唯一定位一条明细。

```text
PurchaseOrder(order_id PK, ...)
Product(product_id PK, ...)
OrderItem(
  order_id NOT NULL FK → PurchaseOrder.order_id,
  line_no NOT NULL,
  product_id NOT NULL FK → Product.product_id,
  quantity NOT NULL,
  unit_price NOT NULL,
  PK(order_id, line_no)
)
```

通常再约束 `line_no>0`、`quantity>0`、`unit_price>=0`。同一订单的第 1 行不能出现两次，但不同订单的第 1 行可以共存。

在 Chen 弱实体画法中，OrderItem 可画双矩形，与 PurchaseOrder 的标识联系画双菱形，line_no 标为部分键，并表达明细对订单的完全参与。**是否自动级联删除是另一条生命周期策略**，不能仅从“弱实体”一词推出所有数据库必须写 `ON DELETE CASCADE`。

**有外键不自动意味着弱实体。**普通员工虽然有 dept_id 外键，仍可能凭全局唯一的 emp_id 独立标识。弱实体的关键在于此概念模型中不能仅凭自己的属性独立标识，需要借助拥有者的键；一般的存在依赖、引用关系与这种标识依赖要区分。

#### E09 解析｜把“课程目录”与“某次具体开课”拆开

**关键变化：**“数据库原理”是一门课程；“2026 秋季数据库原理 02 班”才是具体的一次开课。学生在不同学期重修时，course_id 相同，offering_id 不同。

一种可行设计：

```text
Course(course_id PK, title, credits)
Teacher(teacher_id PK, name)
Student(student_id PK, name)
Offering(
  offering_id PK,
  course_id NOT NULL FK → Course.course_id,
  term NOT NULL,
  section_no NOT NULL,
  teacher_id NOT NULL FK → Teacher.teacher_id,
  UNIQUE(course_id, term, section_no)
)
Enrollment(
  student_id NOT NULL FK → Student.student_id,
  offering_id NOT NULL FK → Offering.offering_id,
  score NULL,
  PK(student_id, offering_id)
)
```

`term` 应能区分年份与学期，例如“2026-Fall”，不能只写会每年重复的“秋季”。这里假定班号在“某课程、某学期”内部唯一，所以三者组成一个候选键；使用全局唯一 offering_id 可以简化外键引用。

关系为：

```text
Course   ||--o{ Offering
Teacher  ||--o{ Offering
Student  ||--o{ Enrollment
Offering ||--o{ Enrollment
```

每个开课班必须有一个课程和一个负责教师；教师可以不带班或带多个班。这里允许课程暂未开班、开课班暂无学生，题目没有要求它们必须已有人选。

**为什么不能用 `(student_id,course_id)`？**同一学生第一次修课和后来重修会得到相同的这组值，无法保存两条记录。正确标识应关联“学生＋具体开课班”，所以成绩也依赖 `(student_id,offering_id)`。

题目只禁止“同一学生重复选同一开课班”，没有禁止同一学期选同课程的不同班。若真实业务还禁止后者，需要再补充跨表业务约束，不能把未给出的规则当作唯一正确答案。

#### E10 解析｜自引用外键能表示父子，但不会保证无环

**关系模式：**

```text
Category(
  category_id PK,
  name,
  parent_id NULL FK → Category.category_id,
  CHECK(parent_id IS NULL OR parent_id <> category_id)
)
```

- 非根分类的 parent_id 指向一个现有分类；根分类的 parent_id 为 null。
- 一行只有一个 parent_id，所以一个分类最多一个父分类。
- 多行可以有相同 parent_id，所以一个分类可有多个孩子。
- 多行都可以 parent_id 为 null，表示有多个根，即森林；不必强制只有一个根。

**外键不能防环。**A 的父分类为 B、B 的父分类为 A 时，两条引用都能找到目标，外键完全可能满足，但结构有环，不是森林。

`CHECK(parent_id<>category_id)` 只能拦住 `A→A` 这样的长度为 1 的自环，拦不住 `A→B→A` 或更长循环。显式加 `parent_id IS NULL` 是为清晰表达根可空；还应理解 SQL CHECK 对 UNKNOWN 的具体语义。

**需要额外的无环校验：**将分类 X 挂到新父分类 Y 之前，从 Y 沿 parent_id 向上查祖先；如果遇到 X，则拒绝修改。可使用递归查询、触发器或业务层的祖先遍历落实。

校验与写入应在适当事务和并发控制下完成。否则两个事务可能各自检查“目前无环”，随后分别把 A 挂到 B、B 挂到 A，最终仍形成环。实际方案可采用适当锁定、可串行化事务或其他一致性机制；不是只在页面上限制选项就能保证。

#### E11 解析｜两两“有关系”不等于这个三元组合成立

**设计：**

```text
Supplier(supplier_id PK, ...)
Part(part_id PK, ...)
Project(project_id PK, ...)
Supply(
  supplier_id NOT NULL FK → Supplier.supplier_id,
  part_id NOT NULL FK → Part.part_id,
  project_id NOT NULL FK → Project.project_id,
  quantity NOT NULL,
  PK(supplier_id, part_id, project_id)
)
```

每一行表达一个完整事实：“某供应商为某项目供应某零件，汇总数量是多少”。数量依赖三者组合；如果要记录每次送货，而非按组合汇总，就需要送货编号/时间等另一套标识，本题不作该扩展。

真实三元组为：

```text
(S1, P1, J1)
(S1, P2, J2)
(S2, P1, J2)
```

投影成三张二元表后分别得到：

| 供应商—零件 SP | 供应商—项目 SJ | 零件—项目 PJ |
|---|---|---|
| S1,P1 | S1,J1 | P1,J1 |
| S1,P2 | S1,J2 | P2,J2 |
| S2,P1 | S2,J2 | P1,J2 |

再连接时会出现虚假的 **`(S1,P1,J2)`**：

- S1 确实供应过 P1，但实际是给 J1。
- S1 确实给 J2 供过货，但实际供应的是 P2。
- J2 确实用过 P1，但实际供应商是 S2。

三张二元表都能找到对应的两两组合，却没有证据表明“S1 给 J2 供应 P1”。这是有损分解后连接产生的**伪元组**。原来各三元组合的数量也无法仅凭这些两两关系正确归属。

**结论：**没有额外的业务依赖保证时，三元联系不能任意拆成三个二元联系。不能因为三角形看起来连接齐全，就认为表达的信息相同。

#### E12 解析｜先把业务语句逐条变成约束

**1. 逻辑 ER 图及关系模式。**为避免关键字冲突，SQL 名称用 AppUser、PurchaseOrder，而不用 USER、ORDER。图中“订单至少一行”针对**已提交订单**。

<!-- DIAGRAM:E12 -->
```text
AppUser       ||----------o{ PurchaseOrder
                               ||
                               |   已提交订单：1..N 条明细
                               |{
                            OrderItem }o----------|| Product

一条明细恰属一个订单，且恰好引用一种商品。
用户可以没有订单；商品可以还没有出现在任何明细中。
```
<!-- /DIAGRAM:E12 -->

四张表：

```text
AppUser(user_id PK, name)
PurchaseOrder(
  order_id PK,
  user_id NOT NULL FK → AppUser.user_id,
  ordered_at NOT NULL
)
Product(product_id PK, name, current_price NOT NULL)
OrderItem(
  order_id NOT NULL FK → PurchaseOrder.order_id,
  line_no NOT NULL,
  product_id NOT NULL FK → Product.product_id,
  quantity NOT NULL,
  unit_price NOT NULL,
  PK(order_id, line_no)
)
```

因为同一种商品可以出现在同订单的不同明细行，所以 **不能把 `(order_id,product_id)` 作为主键或唯一键**，否则会错误禁止题目允许的情况。`(order_id,line_no)` 才能区分行。

以上可以理解为只保存已提交订单的简化模型。若也保存草稿，应增加 status 等状态属性，通常把整张订单表到明细的静态基数画为 **0..N**，另注明条件约束：`status=SUBMITTED ⇒ 明细数≥1`。不要把仅针对已提交订单的要求无条件套到所有草稿上。

**2. 成交单价必须保存历史快照。**商品现价可能随促销、调价而改变。若昨天买入时每件 80 元，今天现价变为 100 元，昨天订单的金额不能被重算成 100 元一件。因此 `unit_price` 属于订单明细，保存当时的实际成交单价；`Product.current_price` 表达当前报价，两者含义不同，不是无意义的数据重复。金额应使用合适的精确小数类型，并按业务统一舍入规则。

**3. 外键不能保证父记录至少有一个孩子。**OrderItem.order_id 的 FK 只检查“已有明细的订单存在”，不会反向要求“每一个订单都已有明细”。

实际可在提交订单的事务中写入/校验明细，再把订单标记为已提交；也可使用数据库支持的可延迟约束触发器等方式，在恰当时点校验。只检查提交动作还不够：还应防止已提交订单的最后一条明细被删除、被移到别的订单，或在并发操作下消失。需要统一写入入口、适当锁或相应数据库约束机制。普通的行级 `CHECK(quantity>0)` 不等于跨表行数约束。

**4. 明细表 SQL。**假定 PurchaseOrder 和 Product 已存在，其主键均为 BIGINT；以下采用常见 SQL 写法，落地时按具体数据库调整语法及功能支持：

```sql
CREATE TABLE OrderItem (
    order_id   BIGINT        NOT NULL,
    line_no    INTEGER       NOT NULL,
    product_id BIGINT        NOT NULL,
    quantity   INTEGER       NOT NULL,
    unit_price DECIMAL(12,2) NOT NULL,

    CONSTRAINT pk_order_item
        PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_item_order
        FOREIGN KEY (order_id)
        REFERENCES PurchaseOrder(order_id),
    CONSTRAINT fk_item_product
        FOREIGN KEY (product_id)
        REFERENCES Product(product_id),
    CONSTRAINT ck_item_line
        CHECK (line_no > 0),
    CONSTRAINT ck_item_quantity
        CHECK (quantity > 0),
    CONSTRAINT ck_item_price
        CHECK (unit_price >= 0)
);
```

PK 防止同一订单同行号重复；两个 FK 保证目标存在；NOT NULL 排除缺失值；CHECK 排除非正数量、负价格等。CHECK 与 NOT NULL 不能相互替代。`DECIMAL(12,2)` 是一个示例精度，业务应另核对金额上限。此 SQL **不声称**已实现“已提交订单至少一条明细”，也不擅自规定删除级联策略。

**5. 重复姓名要区分语义。**若订单中复制的是“用户当前姓名”，用户更名时许多订单可能更新不一致，属于应警惕的冗余和更新异常；通常引用 AppUser 即可。若保存的是“当时的收货人姓名”，它是订单的历史事实，可能不同于账户姓名，也不应随用户改名一起改变，保存快照反而合理。

**建模检查清单：**每个框代表什么 → 每条关系双向读一遍 → 最少与最多分别标 → PK 是否真正唯一 → FK 放哪边 → 哪些列可空 → 哪些规则需要 UNIQUE/CHECK → 哪些规则仅靠外键无法表达。
