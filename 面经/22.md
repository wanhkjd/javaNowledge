# 一、JVM 篇

### 1. JVM 运行时数据区各自存什么？哪些区域会发生 OOM？

*   **是什么（存储内容）**：
    *   **程序计数器（Program Counter Register）**：当前线程所执行的字节码行号指示器。唯一一个在 JVM 规范中**没有规定任何 OOM** 的区域。
    *   **Java 虚拟机栈（Java Virtual Machine Stacks）**：线程私有，生命周期同线程。每个方法执行时创建栈帧，存储**局部变量表**（基本类型、对象引用）、**操作数栈**、**动态链接**、**方法出口**等。
    *   **本地方法栈（Native Method Stacks）**：为 JVM 调用 Native（C/C++）方法服务，类似虚拟机栈。
    *   **Java 堆（Heap）**：线程共享，JVM 启动时创建。存储**几乎所有对象实例和数组**，也是垃圾收集器管理的主要区域。
    *   **元空间（Metaspace，JDK 8+）**：使用本地内存（Native Memory），存储**类元信息（Klass）、运行时常量池、字段与方法数据、方法字节码**。
*   **为什么 / 哪些会 OOM**：
    *   **堆 OOM**（`java.lang.OutOfMemoryError: Java heap space`）：对象分配速率远超回收速率，或发生内存泄漏，堆空间耗尽。
    *   **虚拟机栈 / 本地方法栈**：
        *   `StackOverflowError`：栈深度超限（常见于无终止递归）。
        *   `OutOfMemoryError`：若允许动态扩容栈空间，无法申请到足够内存时报错；或并发创建海量线程耗尽系统内存。
    *   **元空间 OOM**（`java.lang.OutOfMemoryError: Metaspace`）：动态生成大量类（如大量使用 CGLIB、JSP 热编译、动态脚本引擎未卸载 ClassLoader）。
    *   **直接内存 OOM**（`OutOfMemoryError: Direct buffer memory`）：NIO `ByteBuffer.allocateDirect()` 申请堆外内存，未被及时回收。

### 2. 对象什么时候从 Eden 进入 Survivor？什么时候晋升老年代？大对象会直接进老年代吗？

*   **是什么（分配与晋升流程）**：
    1.  **新生代流转**：绝大多数对象在 Eden 区分配。Eden 满时触发 Minor GC（Young GC），存活对象通过复制算法拷贝到 Survivor 0（From），年龄设为 1。之后每次 Minor GC 存活，年龄 +1，并在 S0 和 S1 之间来回复制。
    2.  **年龄阈值晋升**：对象年龄达到 `-XX:MaxTenuringThreshold`（默认 15，CMS 默认 6）时进入老年代。
    3.  **动态年龄判定（Dynamic Age Calculation）**：Survivor 空间中**相同年龄所有对象大小的总和大于 Survivor 空间的一半**（可通过 `-XX:TargetSurvivorRatio` 配置，默认 50%），年龄大于或等于该年龄的对象直接进入老年代，无需等到 15 岁。
    4.  **空间分配担保机制**：Minor GC 前，若老年代最大可用连续空间小于新生代所有对象总空间，且担保失败，会直接触发 Full GC。
*   **为什么大对象直接进老年代**：
    *   **配置**：`-XX:PretenureSizeThreshold`（Serial/ParNew 生效；G1 中超过 Region 大小 50% 的称为 Humongous 对象，分配在连续的巨型 Region 中）。
    *   **设计原因**：避免大对象在 Eden 和两个 Survivor 区之间发生高频率、大批量的内存复制开销，同时防止大对象迅速填满 Survivor 触发动态年龄误晋升。

### 3. G1 和 CMS 的核心区别？什么场景选 G1，什么场景考虑 ZGC？

*   **是什么（核心机制对比）**：
    *   **CMS（Concurrent Mark Sweep）**：基于“标记-清除”，分为初标、并发标、重标、并发清理。追求低停顿，但**会产生内存碎片**，碎片过多或并发收集失败（Concurrent Mode Failure）时会退化为 Serial Old 导致长时间 STW。
    *   **G1（Garbage-First）**：将堆划分为约 2048 个大小相等的独立 **Region**（1MB~32MB），逻辑保留分代。采用“标记-整理/复制”，按 Region 回收价值优先级（Garbage-First）回收，支持设置期望停顿时间（`-XX:MaxGCPauseMillis`）。
*   **为什么 / 选型对比**：
    *   **选 CMS**：堆内存较小（< 4~6GB），CPU 资源有限，JDK 8 环境。
    *   **选 G1**：堆内存较大（6GB ~ 几十 GB），多核 CPU，业务要求停顿时间可控且避免内存碎片（JDK 9+ 默认）。
    *   **考虑 ZGC**：
        *   **机制**：基于**读屏障（Load Barrier）**与**着色指针（Colored Pointers）**，几乎全阶段并发（并发标记、并发转移）。
        *   **场景**：超大堆（百 GB 甚至 TB 级），对延迟**极度敏感**（SLA 要求 GC STW 控制在 1ms ~ 10ms 内，如高频交易、低延迟核心网关），可以容忍少量吞吐量下降。

### 4. 线上服务频繁 Full GC 排查步骤与工具使用

*   **怎么用（实战排查排查步骤）**：
    1.  **紧急止血**：若影响生产流量，先摘除流量（节点下线/降级），**保留一台故障节点 dump 内存与现场日志**，其余节点重启或扩容恢复可用性。
    2.  **指标与日志分析**：
        *   检查监控（GC 频率、老年代曲线是否呈锯齿状陡增无法回落）。
        *   分析 GC 日志：排查是 `Allocation Failure`、`System.gc()`、还是元空间扩容触发。
    3.  **在线工具快速诊断**：
        *   `jstat -gcutil <pid> 1000 10`：观察各代内存占比与 GC 速率。
        *   **Arthas**（首选无侵入工具）：
            *   `dashboard`：查看线程、内存全局概况。
            *   `thread -n 3`：查找最消耗 CPU 的线程栈（排除频繁 GC 伴随的 CPU 飙高）。
            *   `profiler start --event alloc`：生成内存分配火焰图，直观定位哪个业务方法在疯狂 new 对象。
    4.  **离线 Dump 分析**：
        *   生成 Dump：`jmap -dump:live,format=b,file=heap.hprof <pid>`（生产环境谨慎使用，会导致 STW；推荐预先配置 `-XX:+HeapDumpOnOutOfMemoryError`）。
        *   **MAT (Memory Analyzer Tool) / JProfiler** 分析：
            *   查看 **Histogram** 和 **Dominator Tree**，按 Retained Heap 排序，找出最大引用对象。
            *   查看对象的 GC Roots 引用链，判定是内存泄漏还是短时流量冲击。
    5.  **根因定位常见类型**：
        *   *业务代码 Bug*：未做分页全表查询、静态集合无界增长、`ThreadLocal` 未清理。
        *   *参数不当*：元空间设置过小、Survivor 过小导致本该年轻代销毁的对象频繁提前早亡晋升。

# 二、并发编程篇

### 1. synchronized 和 ReentrantLock 的区别？各自底层实现？

*   **是什么（区别）**：
    *   **语法层次**：`synchronized` 是 JVM 关键字，自动加锁与释放；`ReentrantLock` 是 JUC 提供的 API 类，需在 `finally` 中显式 `unlock()`。
    *   **功能扩展**：`ReentrantLock` 支持公平/非公平锁选择、可中断响应（`lockInterruptibly`）、超时尝试（`tryLock`）、支持通过多个 `Condition` 精准唤醒指定线程。
*   **为什么（底层实现）**：
    *   **synchronized 底层**：
        *   依赖对象头的 **Mark Word** 和内部的 **ObjectMonitor**（C++ 实现）。
        *   经历**锁升级过程**：无锁 $\rightarrow$ 偏向锁（JDK 15+ 默认禁用） $\rightarrow$ 轻量级锁（CAS 拷贝 Mark Word 到线程栈的 Lock Record） $\rightarrow$ 重量级锁（指向互斥量，调用 OS `pthread_mutex` 挂起线程，产生用户态到内核态切换）。
    *   **ReentrantLock 底层**：
        *   基于 **AQS（AbstractQueuedSynchronizer）**。
        *   维护一个 `volatile int state`（0 表示未锁，>0 表示重入次数）和一个双向 FIFO 等待队列（CLH 变体）。
        *   线程通过 CAS 修改 state，失败则将当前线程封装成 Node 节点入队，并调用 `LockSupport.park()` 挂起。

---

### 2. volatile 能保证原子性吗？可见性和有序性是怎么实现的？

*   **是什么**：
    *   **不能保证原子性**：仅保证单个变量读写原子性，无法保证复合操作（如 `i++` 分为读取、递增、写回三步）的原子性。
*   **为什么（底层实现机制）**：
    *   **可见性**：
        *   *JMM 规则*：对 volatile 变量的写会强制刷新到主内存；对它的读会使工作内存失效，直接从主内存读取。
        *   *硬件层面*：底层汇编添加 `lock` 指令前缀，触发 CPU 的**缓存一致性协议（如 MESI）**和写缓冲区刷新，同时让其他核心的缓存行失效。
    *   **有序性**：
        *   *JMM 规则*：禁止特定的编译器重排序与处理器重排序。
        *   *实现方式*：插入 **JMM 内存屏障（Memory Barrier）**：
            *   写操作前后：`StoreStore` 屏障（防止前面写重排到写后） + `StoreLoad` 屏障（防止写与后面读重排）。
            *   读操作后：`LoadLoad` 屏障 + `LoadStore` 屏障（防止读与后面读写重排）。

### 3. ThreadLocal 的原理是什么？为什么会内存泄漏？怎么避免？

*   **是什么（原理）**：
    *   每个 `Thread` 线程对象内部持有一个 `ThreadLocalMap`。
    *   `ThreadLocalMap` 是一个自定义哈希表，其内部的 `Entry` 结构继承自 `WeakReference<ThreadLocal<?>>`。
    *   调用 `threadLocal.set(val)` 实际是将 `(ThreadLocal对象, val)` 存入当前线程自身的 `ThreadLocalMap`。
*   **为什么会内存泄漏**：
    *   **弱引用 Key 与强引用 Value**：`Entry` 对 `ThreadLocal` 是弱引用，但对 `Value` 是强引用。
    *   当外部将 `ThreadLocal` 变量置为 null 后，发生 GC 时 Key 会被回收变为 `null`。
    *   如果当前线程长期存活（**尤其是线程池中的核心线程**），引用链路为：`Thread Ref -> Thread -> ThreadLocalMap -> Entry -> Value`。只要线程不销毁，Key 为 null 的 Value 永远无法被回收，导致内存泄漏。
*   **怎么用（避坑指南）**：
    *   **必须在 `finally` 块显式调用 `remove()`**：
      ```java
      try {
          userContext.set(userInfo);
          doBusiness();
      } finally {
          userContext.remove(); // 强制清理
      }
      ```

### 4. ConcurrentHashMap 在 JDK 7 和 JDK 8 的本质区别？为什么放弃分段锁？

*   **是什么（结构区别）**：
    *   **JDK 7**：`Segment` 数组 + `HashEntry` 数组 + 链表。`Segment` 继承 `ReentrantLock`，分段加锁，默认并发度 16。
    *   **JDK 8**：`Node` 数组 + 链表 / 红黑树。采用 **CAS + synchronized** 锁住每个桶的**头节点（First Node）**。
*   **为什么放弃分段锁**：
    1.  **锁粒度更细**：JDK 7 分段锁粒度是 Segment（多个 Hash 桶共用把锁）；JDK 8 锁粒度降到了每个槽位（Hash 桶），冲突概率大幅降低，并发度从 16 提升至数组长度 N。
    2.  **内存占用更优**：JDK 7 的 Segment 对象和多层结构带来大量额外内存开销；JDK 8 扁平化结构更省内存。
    3.  **JVM 锁优化红利**：`synchronized` 经过 JVM 偏向锁、轻量级锁、锁粗化/消除等优化后，低冲突场景下性能极佳，且能随 JVM 版本升级持续享受官方优化。

# 三、集合与数据结构篇

### 1. HashMap 的 put 流程？为什么要用红黑树？负载因子为什么是 0.75？

*   **是什么（put 流程）**：
    1.  **扰动计算**：`(h = key.hashCode()) ^ (h >>> 16)`，让高 16 位参与异或运算，减少低位碰撞。
    2.  **初始化检查**：若数组为空，调用 `resize()` 分配初始容量（默认 16）。
    3.  **计算寻址**：通过 `(n - 1) & hash` 快速定位槽位。
    4.  **碰撞处理**：
        *   槽位无数据：直接 CAS / 写入新节点。
        *   槽位有数据：先比较头节点 key，相同则覆盖；若为 `TreeNode`，走红黑树插入；若为普通链表，尾插法遍历，达到 8 时且数组长度 $\ge 64$ 转为红黑树（数组不足 64 先扩容）。
    5.  **容量检查**：元素总数超过 `threshold = capacity * 0.75`，触发 `resize()` 扩容为 2 倍。
*   **为什么用红黑树**：
    *   防恶劣碰撞时查询时间退化为 $O(n)$。红黑树能把最坏时间复杂度稳定在 $O(\log n)$。
    *   为什么不直接全用红黑树：`TreeNode` 大小是普通 `Node` 的两倍左右，且自平衡旋转有额外 CPU 开销。在散列良好时，阈值 8 几乎难以触发。
*   **为什么负载因子是 0.75**：
    *   **时空权衡（Time-Space Trade-off）**：过大（如 1.0）虽然空间利用率高，但 Hash 冲突激增，查询变慢；过小（如 0.5）虽然冲突极少，但频繁扩容，内存浪费严重。
    *   **数学支撑（泊松分布）**：源码注释指明，在 0.75 负载因子下，单个 Hash 槽位链表长度达到 8 的概率小于千万分之一（$0.00000006$）。

### 2. ArrayList 和 LinkedList 的区别？场景？ArrayList 扩容机制？

*   **是什么（核心差异）**：
    *   **底质差异**：`ArrayList` 底层是连续 Object 数组；`LinkedList` 底层是双向链表。
    *   **访问与增删**：
        *   `ArrayList` 支持 $O(1)$ 随机访问（实现了 `RandomAccess`，基于指针偏移）；指定位置插入/删除需要 `System.arraycopy` 移动元素（$O(n)$）。
        *   `LinkedList` 随机访问需遍历（$O(n)$）；首尾增删为 $O(1)$，但中间增删寻址依然是 $O(n)$。
*   **为什么 / 选型场景**：
    *   **绝大多数业务场景无脑选 `ArrayList`**：因为连续内存对 **CPU 缓存行（Cache Line）友好**，具备空间局部性。
    *   `LinkedList` 仅在需要非常频繁的首尾插入/删除（如队列/栈）时考虑，但即使做队列，`ArrayDeque` 性能也通常优于 `LinkedList`（LinkedList 每个节点都有两个指针的额外开销，且产生大量内存碎片）。
*   **ArrayList 扩容机制**：
    *   默认初始容量为 10（延迟到首次 `add()` 时才真正分配）。
    *   扩容逻辑：`int newCapacity = oldCapacity + (oldCapacity >> 1)`，即扩容为原来的 **1.5 倍**。
    *   底层使用 `Arrays.copyOf()` 调用底层 native 方法进行数组内存迁移。

# 四、Spring 生态篇

### 1. Spring IOC 容器启动流程？Bean 生命周期有哪些阶段？

*   **是什么（启动核心流程，基于 `refresh()`）**：
    1.  `prepareRefresh()`：校验必需环境属性。
    2.  `obtainFreshBeanFactory()`：创建 `DefaultListableBeanFactory`，加载 `BeanDefinition`。
    3.  `prepareBeanFactory()`：注册类加载器、Aware 处理器等基础设施。
    4.  `invokeBeanFactoryPostProcessors()`：执行 `BeanFactoryPostProcessor`（处理 `@Configuration`、`@ComponentScan` 等）。
    5.  `registerBeanPostProcessors()`：注册 `BeanPostProcessor`（AOP 和代理的核心拦截器）。
    6.  `onRefresh()`：模板方法，SpringBoot 在此启动嵌入式 Web 容器（Tomcat/Undertow）。
    7.  `finishBeanFactoryInitialization()`：**实例化并初始化所有非懒加载单例 Bean**。
    8.  `finishRefresh()`：发布上下文刷新事件。
*   **为什么 / 生命周期 4 大阶段**：
    1.  **实例化（Instantiation）**：反射或 CGLIB 调用构造器分配内存空间。
    2.  **属性赋值（Populate）**：依赖注入（`@Autowired`、setter），解决循环依赖。
    3.  **初始化（Initialization）**：
        *   调用 Aware 接口注入环境（`BeanNameAware`、`ApplicationContextAware`）。
        *   `BeanPostProcessor.postProcessBeforeInitialization`。
        *   执行初始化方法（`@PostConstruct` $\rightarrow$ `InitializingBean.afterPropertiesSet()` $\rightarrow$ 自定义 `init-method`）。
        *   `BeanPostProcessor.postProcessAfterInitialization`（**AOP 动态代理在此生成**）。
    4.  **销毁（Destruction）**：容器关闭时触发（`@PreDestroy` $\rightarrow$ `DisposableBean.destroy()`）。

### 2. Spring AOP 实现原理？JDK 动态代理 vs CGLIB 怎么选？

*   **是什么（原理）**：
    *   基于**动态代理模式**，在 Bean 生命周期的初始化后置处理阶段，拦截目标对象并织入切面逻辑生成代理对象。
*   **区别与底层机制**：
    *   **JDK 动态代理**：依赖 `java.lang.reflect.Proxy`。目标类**必须实现接口**。生成的代理类继承 `Proxy` 并实现目标接口，调用时走 `InvocationHandler.invoke()`，基于反射。
    *   **CGLIB 代理**：基于底层的 **ASM 字节码框架**。运行时动态生成目标类的**子类**，重写父类非 final 方法，调用时走 `MethodInterceptor`，基于 FastClass 机制（索引分发，性能略高）。
*   **为什么 / 选型规则**：
    *   Spring Framework 原生策略：目标类有接口用 JDK 代理；无接口用 CGLIB。
    *   **Spring Boot 2.x+ 改变**：默认全部采用 CGLIB（`spring.aop.proxy-target-class=true`），避免由于开发者习惯按实现类类型注入而导致依赖注入失败。

### 3. Spring 事务在什么情况下会失效？@Transactional 传播行为有哪些？

*   **是什么（事务失效典型场景）**：
    1.  **同类方法自调用（Self-invocation）**：类内 `methodA()` 直接调用带注解的 `this.methodB()`，绕过了 Spring AOP 代理（解决：注入自身代理或通过 `AopContext.currentProxy()`）。
    2.  **方法非 public**：Spring 事务切面默认只检查 public 方法，声明在 protected/private 上静默失效。
    3.  **异常被代码吞掉**：业务代码 `try-catch` 捕获了异常且未向外 rethrow，AOP 切面感知不到异常，正常提交。
    4.  **抛出非运行时异常**：Spring 默认只在遇到 `RuntimeException` 和 `Error` 时回滚，发生受检异常（如 `SQLException`、`IOException`）不回滚（解决：显式声明 `@Transactional(rollbackFor = Exception.class)`）。
    5.  **多线程调用**：子线程内的数据库操作无法融入父线程事务，因为数据库连接通过 `ThreadLocal` 绑定在当前线程。
    6.  **存储引擎不支持**：如 MySQL 选用了 MyISAM。
*   **为什么（核心传播行为）**：
    *   `REQUIRED`（默认）：有事务则加入，无事务则新建。
    *   `REQUIRES_NEW`：无论当前有无事务，挂起当前事务并新建独立事务（常用于审计日志、计费独立提交）。
    *   `NESTED`：在外层事务中作为嵌套事务运行（基于数据库 Savepoint），内层失败不影响外层，外层回滚会连带回滚内层。

---

### 4. Spring 如何解决循环依赖？三级缓存分别存的是什么？

*   **是什么（三级缓存结构）**：
    *   `singletonObjects`（一级缓存）：存放**完全初始化完成**的成型 Bean。
    *   `earlySingletonObjects`（二级缓存）：存放**提前暴露的半成品 Bean**（已实例化，尚未赋值/初始化完整）。
    *   `singletonFactories`（三级缓存）：存放**ObjectFactory 工厂 Lambda**（`() -> getEarlyBeanReference(beanName, mbd, bean)`）。
*   **为什么必须是三级缓存（能不能只要两级）**：
    *   **如果只解决普通循环依赖，二级缓存完全足够**。
    *   **引入第三级缓存的核心原因是为了支持 AOP 代理**：
        *   Spring 的核心设计原则是：**AOP 代理对象应当在 Bean 走完初始化后置处理器时才创建**。
        *   三级缓存存的是一个工厂函数。如果发生循环依赖，提前调用 `getEarlyBeanReference` 生成代理对象放入二级缓存；**若未发生循环依赖，三级缓存中的工厂函数根本不会提前执行**，代理对象依然在初始化最后一步正常生成。

# 五、数据库与缓存篇

### 1. MySQL 索引底层结构？什么情况下索引失效？

*   **是什么（B+ 树优势）**：
    *   InnoDB 选用 **B+ 树**作为索引结构。
    *   *相比 B 树*：非叶子节点仅存键值和指针，不存数据，使得单页（16KB）能容纳更多分支，**树高更矮（通常 3~4 层支持千万级数据），磁盘 I/O 极低**；所有叶子节点构成双向链表，对**范围查询和排序极度友好**。
*   **为什么索引会失效（常见规约）**：
    1.  **违背最左前缀法则**：联合索引 `(a, b, c)`，查询缺少 `a`。
    2.  **索引列上做计算、函数或隐式转换**：如 `WHERE SUBSTR(name, 1, 3) = 'abc'`，或字符字段查数字 `WHERE phone = 138000`。
    3.  **头部模糊查询**：`LIKE '%abc'` 无法利用 B+ 树有序性走索引，`LIKE 'abc%'` 可以。
    4.  **范围查询后列失效**：联合索引 `(a, b, c)`，`WHERE a = 1 AND b > 10 AND c = 5`，`c` 无法利用索引。
    5.  **OR 条件存在未索引列**：`WHERE a = 1 OR b = 2`，只要 `b` 无索引即全表扫描。
    6.  **CBO 优化器成本估算**：若查询结果集占全表比例过大（如超过 20%~30%），优化器认为回表代价高于全表扫描，自动放弃索引。

### 2. MySQL 四种隔离级别与 MVCC 实现原理？

*   **是什么（隔离级别与解决问题）**：
    *   **读未提交（Read Uncommitted）**：存在脏读、不可重复读、幻读。
    *   **读已提交（Read Committed, RC）**：解决脏读。
    *   **可重复读（Repeatable Read, RR, MySQL 默认）**：解决脏读、不可重复读，通过 MVCC + Next-Key Lock 基本解决幻读。
    *   **串行化（Serializable）**：解决所有问题，性能极差。
*   **为什么（MVCC 底层机制）**：
    *   主要用于实现**无锁快照读**（读写不互斥）。
    *   **核心组成**：
        1.  **隐藏列**：`trx_id`（最后修改该行的事务 ID）、`roll_pointer`（回滚指针，指向历史版本）。
        2.  **Undo Log 版本链**：多次修改形成的旧版本链表。
        3.  **ReadView（一致性视图）**：包含 `m_ids`（活跃事务列表）、`min_trx_id`（最小活跃事务）、`max_trx_id`（系统预分配下一个事务 ID）、`creator_trx_id`（当前事务 ID）。
    *   **可见性判断**：
        *   `trx_id < min_trx_id`：已提交，可见。
        *   `trx_id >= max_trx_id`：未来事务，不可见。
        *   `min_trx_id <= trx_id < max_trx_id`：若在 `m_ids` 中，说明未提交，不可见；不在则已提交，可见。
    *   **RC 与 RR 本质区别**：
        *   **RC**：在事务中**每次执行 SELECT 都会重新生成一个新的 ReadView**（能读到别人已提交的数据，不可重复读）。
        *   **RR**：在事务中**仅在第一次执行 SELECT 时生成 ReadView**，后续复用（保证事务内多次读取一致）。

### 3. 缓存穿透、击穿、雪崩分别是什么？解决方案？

| 现象 | 是什么（原因） | 解决方案（怎么用） |
| :--- | :--- | :--- |
| **缓存穿透** | 查询一个**数据库和缓存都不存在**的数据，请求直接击穿到底层 DB，高并发下导致 DB 宕机（多见于黑客恶意攻击）。 | 1. **布隆过滤器（Bloom Filter）**：在访问缓存前先校验是否存在。<br>2. **空值缓存（Cache Null）**：DB 查不到也缓存空值，TTL 设为 1~3 分钟。<br>3. **接口层强校验**：非法 ID 格式在网关层直接拦截。 |
| **缓存击穿** | 某一个**极度热点的 Key** 在过期瞬间，并发量过大，瞬时全部涌入 DB。 | 1. **互斥锁（Mutex Lock / 分布式锁）**：缓存失效时仅允许一人查 DB 回填，其余重试等待。<br>2. **逻辑过期（Logical Expiration）**：物理不过期，Value 内嵌逻辑过期时间，后台异步线程定时刷新。 |
| **缓存雪崩** | **大量不同的 Key 在同一时间段集中过期**，或者 Redis 节点宕机，海量请求倾泻到底层 DB。 | 1. **随机过期时间（Jitter）**：基础过期时间上增加 1~5 分钟随机抖动（`TTL = base + rand()`）。<br>2. **高可用集群**：Redis Cluster / 主从哨兵，多可用区容灾。<br>3. **本地缓存降级**：结合 Caffeine 构建多级缓存 + 限流降级（Sentinel）。 |

# 六、分布式与中间件篇

### 1. 分布式锁方案？Redis 锁的问题与 Redisson 原理？

*   **是什么（常见方案）**：
    *   MySQL 唯一键（性能差）。
    *   Zookeeper / etcd：临时顺序节点 + Watcher，强一致 CP，稳定性高。
    *   Redis：基于 AP 架构，性能极致。
*   **为什么（原生 Redis 锁的隐患）**：
    1.  `SETNX` 与 `EXPIRE` 必须原子化（使用 `SET key val NX PX`）。
    2.  误删他人锁（业务耗时过长导致锁过期，A 释放了 B 刚拿到的锁，需利用 UUID + Lua 校验删除）。
    3.  业务未执行完提前过期（缺乏自动续期）。
    4.  主从切换丢锁（Master 加锁成功但未同步到 Slave 即宕机，Slave 晋升导致两客户端同时持锁）。
*   **怎么用（Redisson 解决方案）**：
    *   **Lua 脚本**：保证加锁、解锁全流程原子性。
    *   **看门狗（Watchdog）机制**：加锁不指定 leaseTime 时默认 30s。后台启动定时任务（Netty 时间轮），每隔 10s（`leaseTime / 3`）自动续期至 30s，直到业务主动释放。
    *   **可重入性**：使用 Redis Hash 结构记录客户端唯一标识与重入次数。
    *   *针对主从丢锁*：若追求强一致，选 Zookeeper 或 etcd；Redis 体系可尝试 Redlock（但在实际业务中因运维复杂度高与时钟漂移，更推荐合理设计业务幂等或容忍极端补偿）。

### 2. 消息队列如何保证消息不丢失？如何保证幂等消费？

*   **是什么（保证不丢的三个阶段）**：
    1.  **生产阶段**：启用确认机制。RabbitMQ 开启 Confirm 回调；Kafka 设置 `acks=all`（`-1`）且配置 `retries` 重试。
    2.  **Broker 存储阶段**：Broker 收到消息强制刷盘（或至少同步至大多数副本）才向生产者返回 ACK。Kafka 配置 `min.insync.replicas >= 2`，RabbitMQ 队列与消息均设为 `durable`。
    3.  **消费阶段**：**关闭自动 ACK**，业务完全执行成功后再手动 ACK。发生异常走重试队列或死信队列（DLQ）。
*   **为什么 / 怎么用（保证消费幂等性）**：
    *   MQ 协议基本只保证 **At-least-once（至少一次消费）**，网络抖动必然导致偶发重复投递，必须由**消费端业务层兜底幂等**：
        1.  **唯一业务流水号 + DB 唯一索引**：如支付流水号、订单防重表，插入冲突即代表已处理。
        2.  **Redis 分布式锁 / SETNX 状态机**：消费前先查业务状态机（如“待支付”才转“已支付”，重复请求直接判定成功跳过）。
        3.  **数据库乐观锁**：`UPDATE account SET balance = balance - 100, version = version + 1 WHERE id = 1 AND version = #{version}`。

### 3. 分布式事务有哪些方案？Seata AT vs TCC 选型？

*   **是什么（主流方案）**：
    *   **2PC / 3PC (XA)**：强一致性，性能较差，锁资源时间长。
    *   **TCC（Try-Confirm-Cancel）**：业务层两阶段，柔性事务。
    *   **本地消息表 / MQ 事务消息**：最终一致性，性能最高，异步解耦首选。
    *   **Seata**：阿里开源的一站式分布式事务解决方案（支持 AT、TCC、Saga、XA）。
*   **为什么（Seata AT vs TCC 对比）**：
    *   **Seata AT 模式**：
        *   *机制*：**无侵入**。一阶段拦截业务 SQL，自动生成更新前后的**镜像日志（before/after image）**并存入 `undo_log` 表，同时向 TC 申请全局锁；二阶段若成功异步清理日志，若失败根据 `undo_log` 反向生成补偿 SQL 回滚。
        *   *代价*：依赖关系型数据库，高并发下全局锁存在竞争瓶颈。
    *   **Seata TCC 模式**：
        *   *机制*：**业务侵入**。需要手动实现三个方法：`Try`（资源检查与预留）、`Confirm`（真正扣除预留资源）、`Cancel`（释放预留资源）。
        *   *代价*：代码改造成本极高，需要自行解决空回滚、幂等、防悬挂问题。
*   **怎么用（业务选型）**：
    *   **选 AT**：企业内部中后台系统、微服务调用链路短、并发量适中、全链路都是关系型数据库（MySQL），追求开发效率与代码整洁度。
    *   **选 TCC**：核心高并发交易链路（如电商秒杀、支付网关）、涉及跨异构系统（Redis + MySQL + 第三方外部接口），对事务性能有极致要求的场景。
