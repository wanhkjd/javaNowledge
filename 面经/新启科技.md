## 一、Spring Boot 配置原理

“配置原理”通常包含两部分：**自动配置原理**和**配置文件的加载、绑定原理**。

### 1. 自动配置原理

**核心：根据项目中的依赖、已有 Bean 和配置属性，按条件创建需要的 Bean，减少手动配置。**

入口是 `@SpringBootApplication`，主要包含三个注解：

```java
@SpringBootConfiguration  // 本质上是配置类
@EnableAutoConfiguration  // 开启自动配置
@ComponentScan            // 扫描当前包及子包中的组件
```

java

自动配置的主要流程：

```text
启动 Spring Boot
    ↓
@EnableAutoConfiguration 开启自动配置
    ↓
AutoConfigurationImportSelector 导入自动配置候选类
    ↓
根据 @Conditional 系列注解判断条件
    ↓
条件满足的配置生效，向容器注册 Bean
```

text

自动配置候选类从哪里来？

- **Spring Boot 2.6 及以前**：主要通过 `META-INF/spring.factories`。
- **Spring Boot 2.7**：引入新的自动配置注册方式。
- **Spring Boot 3.x**：通过  
    `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。

常见条件注解：

|注解|作用|
|---|---|
|`@ConditionalOnClass`|类路径存在指定类时生效|
|`@ConditionalOnMissingBean`|容器中没有指定 Bean 时生效|
|`@ConditionalOnProperty`|配置属性满足条件时生效|

例如，数据源自动配置会结合相关依赖、配置属性以及是否已有 `DataSource` 等条件，决定是否创建数据源。

**如果用户自己定义了相应 Bean，自动配置通常会退让，而不是强行覆盖。**

另外，**Starter 主要负责聚合依赖，自动配置类负责按条件创建 Bean**，两者不是一回事。

### 2. 配置文件如何生效

大致流程：

```text
application.yml / properties、环境变量、启动参数等
    ↓
加载到 Environment 的各个 PropertySource
    ↓
按优先级解析属性
    ↓
绑定到配置对象，或注入 Bean
```

text

例如：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/test
    username: root
    password: xxx
```

yaml

这些属性会绑定到对应的配置对象，再用于创建数据源。

常见读取方式：

- `@ConfigurationProperties`：通过 Binder 批量绑定配置，适合结构化配置。
- `@Value`：注入单个属性。
- `Environment`：直接读取属性。

常见来源中，优先级通常为：

```text
命令行参数 > JVM 系统属性 > 操作系统环境变量 > 配置文件
```

text

这里只列了常见来源，不是完整优先级列表。

**面试总结：**

> Spring Boot 通过 `@EnableAutoConfiguration` 导入自动配置候选类，再利用条件注解，根据依赖、已有 Bean 和配置属性选择性生效。配置属性统一进入 Environment，并通过属性绑定参与 Bean 创建，从而实现约定大于配置。

## 二、MySQL 底层索引

这里以最常用的 **InnoDB 引擎的普通索引**为例。

### 1. 底层为什么使用 B+ 树

InnoDB 索引主要使用 **B+ 树**：

- 非叶子节点保存索引键和子页指针。
- 叶子节点保存索引记录。
- 叶子页之间通过双向链表连接，方便范围扫描。
- 数据按页组织，默认页大小为 **16KB**。

选择 B+ 树的主要原因：

**① 树矮，页面访问少**

一个节点可以容纳很多索引键，分叉多，树的高度通常较低，能够减少页面访问及潜在的磁盘 I/O。实际访问还会利用 Buffer Pool 缓存，并不一定每层都读磁盘。

**② 范围查询方便**

例如：

```sql
WHERE age BETWEEN 20 AND 30
```

sql

定位起点后，可以沿叶子页顺序扫描。

**③ 适合排序和有序遍历**

索引按键值排序，合适的索引可以帮助处理 `ORDER BY` 等操作。

相比之下：

- 二叉树分叉少，大数据量下树更高。
- B 树非叶子节点也存数据记录，通常能容纳的索引键更少。
- 哈希结构擅长等值查找，但不适合有序范围查询。

### 2. 聚簇索引和二级索引

#### 聚簇索引

**叶子节点存放行记录，InnoDB 通常按主键组织聚簇索引。**

```text
主键 → 聚簇索引 → 行记录
```

text

如果没有显式主键，InnoDB 会选择合适的唯一非空索引；仍没有则生成隐藏行 ID。

#### 二级索引

**叶子节点主要存放二级索引列的值，以及对应的主键值。**

假设有：

```sql
user(
    id PRIMARY KEY,
    name,
    age,
    email,
    INDEX idx_name_age(name, age)
)
```

sql

执行：

```sql
SELECT email FROM user WHERE name = '张三';
```

sql

如果使用 `idx_name_age`，通常需要：

```text
通过二级索引查到主键 id
    ↓
使用 id 查聚簇索引
    ↓
获取 email
```

text

第二次查聚簇索引的过程叫 **回表**。

### 3. 什么是覆盖索引

如果查询所需字段都能从索引中取得，就可以避免常规回表。

例如：

```sql
SELECT id, age
FROM user
WHERE name = '张三';
```

sql

`idx_name_age` 中有 `name、age`，二级索引还包含主键 `id`，因此可以形成**覆盖索引**。

### 4. 联合索引与最左前缀

联合索引 `(name, age)` 的排序方式是：

```text
先按 name 排序，name 相同时再按 age 排序
```

text

因此通常适合：

```sql
WHERE name = '张三'
WHERE name = '张三' AND age = 20
```

sql

只按 `age` 查询，通常不能直接利用最左前缀进行高效定位；具体仍由优化器决定，部分场景存在跳跃扫描等优化。

**面试总结：**

> InnoDB 的普通索引主要基于 B+ 树，特点是分叉多、树高低、叶子页有序连接，适合磁盘访问和范围查询。聚簇索引叶子存行记录，二级索引叶子存索引列和主键；二级索引查到主键后再查聚簇索引叫回表，覆盖索引可以减少回表。

## 三、系统运行慢，如何排查

**核心思路：先确定慢在哪里，再用证据定位原因，不要一上来就调 JVM、加索引或者重启。**

整体顺序：

```text
确定影响范围 → 定位耗时环节 → 分层排查 → 针对性修复 → 验证效果
```

text

如果线上已经严重受影响，应在保留必要证据后，先通过限流、降级、回滚等方式恢复服务，再继续分析根因。

### 1. 先明确“慢”的表现

先确认：

- 所有接口慢，还是某一个接口慢？
- 一直慢，还是偶发、定时变慢？
- 是平均耗时增加，还是只有 P95、P99 明显升高？
- QPS、并发量、错误率是否发生变化？
- 是否刚发布、改配置，或者有定时任务执行？

例如：

> 发布后所有接口变慢，优先检查发布和配置变化；只有查询接口慢，优先关注 SQL、数据库等待以及数据量变化。

### 2. 通过调用链定位耗时

结合 APM、链路追踪、日志时间戳，拆解：

```text
客户端 → 网关 → 应用 → 数据库 / Redis / 外部服务
```

text

重点区分：

- 请求是否在排队？
- 业务代码是否计算耗时高？
- SQL 执行慢，还是获取数据库连接慢？
- 是否在等待 Redis、RPC 或 HTTP 调用？

**先定位具体耗时段，再深入对应组件。**

如果用户体验很慢，但服务端耗时正常，还要检查网络、DNS、TLS 和前端渲染。

### 3. 检查服务器和 JVM

以下工具以 Linux 部署为例：

|现象|重点排查|常用工具|
|---|---|---|
|CPU 高|热点代码、死循环、频繁 GC|`top`、`pidstat`、JFR|
|内存异常|对象持续增长、GC 后占用不回落|GC 日志、`jstat`、堆分析|
|磁盘延迟高|数据库 I/O、日志写入、磁盘饱和|`iostat -x`|
|CPU 不高但请求慢|锁等待、连接池等待、远程调用|线程栈、调用链、池监控|

**CPU 高的典型排查步骤：**

```text
top 找到高 CPU 进程
    ↓
top -Hp <pid> 找到高 CPU 线程
    ↓
线程 ID 转十六进制
    ↓
在线程栈中匹配 nid
    ↓
定位对应代码
```

text

**CPU 不高不代表系统没问题**：请求可能大量阻塞在锁、线程池、连接池或下游服务上。

线程栈需要结合多次采样和业务指标判断，不能看到 `WAITING` 就认为有故障。

### 4. 排查数据库

重点看：

1. **慢 SQL**：慢查询日志、SQL 耗时和执行次数。
2. **执行计划**：使用 `EXPLAIN` 查看索引、扫描行数、排序和临时表。
3. **锁等待**：是否存在长事务、行锁等待或元数据锁等待。
4. **连接池**：活跃连接、等待连接数、获取连接耗时。
5. **资源瓶颈**：数据库 CPU、磁盘延迟、缓存命中情况。

常见问题包括：

- 缺少合适索引。
- 扫描数据太多、回表太多。
- 深分页。
- N+1 查询。
- 长事务导致其他请求等待。
- 连接未释放，导致连接池耗尽。

注意：**`EXPLAIN ANALYZE` 会实际执行查询，生产环境要谨慎使用。**

### 5. 排查缓存、外部依赖与线程池

- Redis 是否有热点 Key、大 Key、慢命令？
- 缓存失效是否导致流量集中打到数据库？
- 外部接口是否延迟增加？
- 是否缺少超时，或者重试过多放大故障？
- 线程池队列是否持续增长？
- 是否存在大量锁竞争，或者线程相互等待？

### 6. 修复后验证

不能只看“感觉快了”，应在可比负载下比较：

- P95、P99 响应时间。
- 吞吐量和错误率。
- CPU、GC 暂停和内存趋势。
- SQL 扫描行数和执行耗时。
- 线程池、连接池等待情况。

**面试总结：**

> 我会先确认影响范围、发生时间和流量变化，再通过监控与链路追踪定位耗时环节。随后分层检查服务器资源、JVM、线程和连接池、数据库及外部依赖。CPU 高就定位热点线程和代码，CPU 不高但响应慢就重点检查各类等待。最后根据证据修复，并用响应时间、吞吐量和错误率验证效果。
