## 环节一：小说平台项目——海量数据、分库分表与多级缓存

### Q1：关于分库分表与 ShardingSphere-JDBC 的设计
> **面试官提问**：
> “你在小说项目中针对 `book_content` 表做了水平分表，拆为 10 张物理表，选用 `chapter_id` 作为分片键。
> 1. 为什么单独对正文表分表，小说基本信息表（`book_info`）为什么不分？
> 2. 为什么分片键选 `chapter_id` 而不是 `book_id`？
> 3. 如果后台运营需要按 `book_id` 导出整本小说的所有章节正文，由于分片键是 `chapter_id`，这会导致全路由广播查询（Scatter-Gather），你如何应对这种跨分片查询痛点？”

#### 🎯 考察意图
考察是否真正理解分库分表的动机（大文本与冷热分离、B+ 树深度与 Buffer Pool 污染），以及分片键选型权衡、非分片键查询方案。

#### 💡 标杆回答解析
*   **为什么只拆正文表**：
    小说元数据（`book_info`）通常字段较短，单行几百字节，千万级数据量在 B+ 树上也仅 3~4 层深度；而章节正文（`book_content`）单章通常几千到上万字（`TEXT`/`MEDIUMTEXT`），属于大字段。若放在单表，会导致 InnoDB 数据页能容纳的行数极少，B+ 树体积急剧膨胀，严重污染 InnoDB Buffer Pool 内存缓存，导致索引效率恶化和深分页缓慢。因此必须做**大文本垂直拆分与正文水平分表**。
*   **为什么分片键选 `chapter_id`**：
    小说业务中，读流量 95% 以上是**读者翻页阅读**，查询场景几乎全部是精确的单条点查：`SELECT content FROM book_content WHERE chapter_id = ?`。以 `chapter_id` 做分片键进行哈希路由（`hash(chapter_id) % 10`），能精准单库单表定位，无跨分片开销。
*   **跨分片/按 `book_id` 查询痛点的解法**：
    *   **读写分离与架构解耦**：在 C 端展示章节列表时，仅查章节元数据表（`chapter_info`，包含 `chapter_id`, `title`, `book_id`，不含正文），正文只在点击具体章节时才加载；
    *   **基因法（ID 嵌入）**：生成 `chapter_id` 时，将 `book_id` 的后几位哈希值作为基因拼入 `chapter_id` 的固定位，这样通过 `book_id` 或 `chapter_id` 查询时都能路由到同一分片；
    *   **离线/运营端解耦**：运营管理端的大批量导出走 Elasticsearch 全量索引或定时同步到数仓/ClickHouse/读写分离的只读从库，不在 C 端核心 OLTP 库上做广播扫描。

### Q2：Caffeine + Redis 多级缓存与一致性保障
> **面试官提问**：
> “你提到基于 Caffeine + Redis 实现了多级缓存，且配置了差异化 TTL。
> 1. 读写操作的具体链路是怎样的？
> 2. 如果应用是分布式多节点部署，作者在后台修改了章节，节点 A 处理写请求并删除了本地和 Redis 缓存，节点 B 上的 Caffeine 怎么感知失效？如何解决节点间的缓存不一致？”

#### 🎯 考察意图
考察多级缓存标准读写流程（Cache Aside）、分布式环境下本地缓存失效机制（Redis Pub/Sub、MQ 广播模式）。

#### 💡 标杆回答解析
*   **多级缓存读写流程**：
    *   **读流程**：先查 Caffeine（本地 L1，命中耗时微秒级）→ 命中直接返回；未命中查 Redis（分布式 L2，耗时毫秒级）→ 命中则回填 Caffeine 并返回；未命中则查 MySQL，查到后写入 Redis（设置差异化 TTL + 随机过期时间防雪崩）并写入本地 Caffeine。
    *   **写流程**：先更新 MySQL 数据库，再主动删除 Redis 缓存与当前节点 Caffeine（遵循 Cache-Aside 模式）。
*   **分布式集群下 Caffeine 同步失效方案**：
    *   **方案一（MQ 广播）**：更新数据后，向 RabbitMQ 的 `Fanout Exchange`（广播交换机）投递一条失效消息。每个实例节点绑定一个独占的匿名临时 Queue，每个微服务实例监听到消息后，主动调用本地 `caffeine.invalidate(key)`。
    *   **方案二（Redis Pub/Sub）**：发布一条通知到 Redis 频道，各服务监听该频道执行本地清除。
    *   **方案三（TTL 短时兜底）**：本地 Caffeine 强制设置很短的过期时间（例如 10s~30s），对于强一致性敏感度较低的场景（如首页推荐、详情），容忍数秒的不一致，大幅简化架构。

### Q3：消息可靠性与事务边界（Spring 事务同步器）
> **面试官提问**：
> “你简历中写到‘借助 Spring 事务同步器保证事务提交后再发消息’。
> 1. 为什么不能在 `@Transactional` 方法内直接发 MQ？
> 2. 底层使用了哪个类？
> 3. 如果事务成功提交了，但是在执行发消息的那一瞬间进程挂了或网络超时发失败了，数据不就丢失同步了吗？该怎么彻底解决？”

#### 🎯 考察意图
考察事务生命周期感知、`TransactionSynchronizationManager`、分布式场景下数据库事务与 MQ 消息的“双写一致性”、本地消息表方案。

#### 💡 标杆回答解析
*   **为什么不能在事务内发 MQ**：
    *   如果先发 MQ，事务还没提交，MQ 消费者就已经收到消息去查数据库，此时会发生**脏读**或根本**查不到数据**；
    *   如果发完 MQ 之后，数据库提交因异常发生回滚，但消息已经发出去被消费了，造成**幽灵数据**（数据回滚但异步任务已执行）；
    *   在事务方法内包含网络 IO（发 MQ），会拉长数据库事务周期，长时间持有数据库行锁，导致连接池枯竭。
*   **代码与底层类**：
    使用 `TransactionSynchronizationManager.registerSynchronization`，重写 `afterCommit()` 钩子方法：
    ```java
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            rabbitTemplate.convertAndSend(exchange, routingKey, msg);
        }
    });
    ```
*   **极端网络宕机导致消息丢失的终极方案**：
    `afterCommit` 只能解决“避免事务回滚却发消息”，但无法解决“提交成功但由于宕机/断网导致消息未发出”。
    *   **工业级终极解法**：**本地消息表（Outbox Pattern）**。在写业务表的同一数据库事务中，顺带向本地 `message_record` 表插入一条状态为 `INIT` 的消息记录。利用事务保障业务数据与消息记录百分之百同成功同失败。后台启动定时任务（或结合 CDC/Canal）抓取未发送成功的消息进行重试投递，投递成功后置为 `SUCCESS`。

### Q4：Spring AI、Function Calling 与流式乱码治理
> **面试官提问**：
> “你落地了 Spring AI 智能书童，用到了 Function Calling 和流式打字机输出。
> 1. 大模型自己会执行你的 Java 方法吗？Function Calling 的底层原理是什么？
> 2. 为什么 SSE 流式传输 `Flux<String>` 时会出现 Emoji 截断乱码？你是如何用 Unicode 码点分块修复的？”

#### 🎯 考察意图
考察对大模型交互协议机制的真实理解（拒绝将大模型当黑盒），以及计算机底层编码（Unicode、UTF-16 代理对）、响应式流（Reactive/Flux）的掌握深度。

#### 💡 标杆回答解析
*   **Function Calling 底层原理**：
    大模型本身**绝不直接执行后端代码**。底层是两次 HTTP 交互协议：
    1.  客户端发起请求时，将注册的 4 个 Tools（通过 `@Description` 提取出函数名、参数名、类型与描述信息）序列化为标准的 **JSON Schema** 随 Prompt 发给大模型；
    2.  大模型根据用户意图进行模式匹配，判定需要调用工具，回复一个特殊的 JSON 数据，指明：`call: findBook(keyword="科幻")`；
    3.  Spring AI 框架拦截到该响应，根据函数名找到本地 Spring Bean 方法，用 Jackson 将参数反序列化，在本地 JVM 中执行真实业务方法并拿到返回数据；
    4.  Spring AI 将方法返回值包装为 `role: tool` 的上下文消息，再次发起请求发给大模型；
    5.  大模型结合工具返回的真实数据，最终总结生成自然的回答给用户。
*   **Emoji 截断乱码与 Unicode 码点分块**：
    *   **乱码成因**：在 Java 中，`String` 内部是基于 UTF-16 编码的，普通的英文字符和基础汉字占用 1 个 `char`（2 字节），但 Emoji（如 😊、🚀 等）以及生僻汉字属于辅助平面字符，占用 4 字节，由两个 `char`（高代理 High Surrogate + 低代理 Low Surrogate）拼成一个完整字符。当大模型按 Token 流式返回或者框架按固定 byte/char 切割字符串时，如果恰好把高低代理对拆开切碎，前端在收到半个 Emoji 时由于字节序列不完整就会直接显示为乱码（如 `` 或 `\uD83D`）。
    *   **解决思路**：在响应式 `Flux<String>` 推流切块时，不能简单按字符长度或字节数硬切。使用 `Character.isHighSurrogate(ch)` 或 `String.codePoints()` 按完整**码点（Code Point）**聚合。若检测到当前字符为高代理项，必须将紧随其后的低代理项绑定作为一个整体单元输出，保证推给前端的每一个 SSE Chunk 都是语义合法的完整 UTF-8/UTF-16 字符。

## 环节二：商城微服务系统——网关、RPC 通信与分布式一致性

### Q5：网关鉴权与 Feign 上下文丢失排查
> **面试官提问**：
> “在万佳商城微服务中，用户请求经过 Gateway 校验 JWT 登录态后，下游服务是如何知道当前是谁在操作的？另外，很多同学在使用 OpenFeign 进行跨微服务调用时，发现下游的 `UserContext` 经常变成 null，这是为什么？你怎么解决的？”

#### 🎯 考察意图
考察微服务网关请求转发模型、Header 改写、ThreadLocal 生命周期、Feign 的 `RequestInterceptor` 拦截器机制。

#### 💡 标杆回答解析
*   **网关传递用户信息**：
    在 Gateway 的 `GlobalFilter` 中解析 JWT Token，校验通过后，通过 ServerWebExchange 变异请求头：
    ```java
    ServerHttpRequest mutatedRequest = exchange.getRequest().mutate()
        .header("X-User-Id", userId)
        .header("X-User-Role", role).build();
    return chain.filter(exchange.mutate().request(mutatedRequest).build());
    ```
    下游微服务配置一个 Spring MVC 的 `HandlerInterceptor`，在 `preHandle` 中提取 `request.getHeader("X-User-Id")`，存入全局静态 `ThreadLocal<UserContext>` 中，方便 Service 层无感知使用。并在 `afterCompletion` 中调用 `remove()` 防止内存泄漏。
*   **Feign 调用上下文丢失原因及解法**：
    *   **原因**：Feign 本质上是微服务内部重新构造的一个 HTTP Client 发起的新请求。默认情况下，Feign 不会自动拷贝当前入站 HTTP 请求的任何 Header 信息，导致跨服务调用下游时 Header 是空的；
    *   **解决方案**：实现 Feign 的 `RequestInterceptor` 接口：
        ```java
        @Component
        public class FeignAuthRequestInterceptor implements RequestInterceptor {
            @Override
            public void apply(RequestTemplate template) {
                ServletRequestAttributes attributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
                if (attributes != null) {
                    HttpServletRequest request = attributes.getRequest();
                    template.header("X-User-Id", request.getHeader("X-User-Id"));
                }
            }
        }
        ```
    *   *注：若 OpenFeign 开启了 Hystrix 线程池隔离或自定义了异步线程池，`RequestContextHolder` 是基于普通 ThreadLocal 的，会跨线程失效，需要配置隔离级别为 `SEMAPHORE` 或使用 Alibaba `TransmittableThreadLocal` (TTL) 进行线程上下文修饰。*

### Q6：下单主链路——Seata AT 模式原理与高并发库存扣减
> **面试官提问**：
> “你在下单主链路使用了 Seata `@GlobalTransactional`，库存扣减采用了数据库原子更新语句。
> 1. Seata AT 模式两阶段提交的具体过程是什么？它为什么不需要像 XA 那样长时间锁定资源？
> 2. 如果是秒杀场景，Seata AT 模式能扛得住吗？会有什么性能瓶颈？业界高并发库存扣减标准方案是什么？”

#### 🎯 考察意图
考察 Seata AT 模式与 XA 模式的区别、UndoLog、全局锁竞争瓶颈，以及从“强一致低性能”向“最终一致/缓存预扣高并发”的架构演进思维。

#### 💡 标杆回答解析
*   **Seata AT 模式两阶段原理**：
    *   **一阶段（准备阶段）**：解析业务 SQL，在业务执行前生成 **Before Image（前镜像）**；执行业务 SQL 后生成 **After Image（后镜像）**；在同一个本地事务中将前/后镜像写入 `undo_log` 表；在本地事务提交前向 TC（Transaction Coordinator）申请**全局行锁**；申请成功后即可**立刻提交本地数据库事务**，释放本地数据库物理连接与行锁（因此性能远高于传统的 2PC/XA 强一致模式）。
    *   **二阶段（提交/回滚）**：
        *   若全局所有分支都成功：异步、批量删除各分支库的 `undo_log`，释放全局锁；
        *   若有任一分支异常失败：各分支回滚，利用 `undo_log` 校验当前数据是否被脏写，用 Before Image 还原数据，完成后释放全局锁。
*   **AT 模式在高并发（秒杀）下的瓶颈**：
    在秒杀或热点商品库存扣减场景下，大量的线程争抢同一个商品 ID 的全局锁和本地行锁。Seata 的 TC 全局行锁申请、频繁的 `undo_log` 序列化读写会导致严重的锁冲突与超时，极易将数据库连接池打满，导致雪崩。
*   **高并发秒杀扣库存的标准解法**：
    *   将热点商品库存预热到 **Redis** 中；
    *   下单时通过 **Lua 脚本**在 Redis 中原子性校验并预扣库存（`stock > 0` 则 `decrby`）；
    *   扣减成功后，向 RocketMQ/RabbitMQ 发送下单消息，由交易服务异步消费落库。即使后续下游出现故障，通过反向增加 Redis 库存实现补偿回滚。

### Q7：支付防重与消息幂等
> **面试官提问**：
> “支付完成后你通过 MQ 异步通知交易服务更新订单状态为已支付。网络抖动可能造成消息重复投递，如何保证交易服务消费的绝对幂等？另外，支付成功后发 MQ 失败，简历写的是‘记录日志降级，不阻塞支付主流程’，那订单一直处于未支付，怎么保证订单闭环？”

#### 🎯 考察意图
考察消息幂等性的设计方案（防重表、状态机条件更新）、以及异步通知失败时的对账与主动轮询机制。

#### 💡 标杆回答解析
*   **消费端绝对幂等设计**：
    *   **方案一：状态机原子更新（天然幂等）**：
        利用 SQL 条件更新控制状态机流转：
        ```sql
        UPDATE t_order SET status = 'PAID', update_time = NOW()
        WHERE order_id = #{orderId} AND status = 'WAIT_PAY';
        ```
        若由于网络重试重复消费，第一次更新返回影响行数 1，第二次由于状态已是 `PAID`，返回影响行数 0，直接判定为重复消费并向 MQ 回复 ACK 即可。
    *   **方案二：防重表（唯一键约束）**：
        以 `pay_order_no` 或 `msg_id` 作为唯一键建立消费记录表，消费处理前先插入，利用数据库唯一索引约束避免重复执行。
*   **订单状态未更新的兜底机制（主动轮询与对账）**：
    仅仅记录日志降级无法形成闭环。生产环境必须有两套兜底机制：
    1.  **延时消息/定时任务主动轮询**：用户支付后，前端通常会轮询订单状态或跳转完成页；若超过指定时间（如 30 秒）订单仍为 `WAIT_PAY`，前端或后台任务主动向支付服务/第三方支付网关发起查单接口（Check Pay Status），核实后主动推进订单状态；
    2.  **日终/定时对账脚本**：定期拉取“已创建但超时未支付”的订单，核对支付平台流水，自动跑批平账。

## 环节三：Java 基础、并发与底层原理

### Q8：ThreadLocal 内存泄漏与线程复用问题
> **面试官提问**：
> “你在项目中频繁使用 ThreadLocal 传递用户上下文，那 ThreadLocal 为什么会发生内存泄漏？为什么 Key 已经是弱引用了还会泄露？在结合 Tomcat 线程池使用时，不 remove 会带来什么业务灾难？”

#### 🎯 考察意图
考察 JVM 垃圾回收（弱引用机制）、ThreadLocalMap 内部结构、线程池复用场景下的数据安全。

#### 💡 标杆回答解析
*   **内存泄露原因**：
    `ThreadLocal` 变量本身并不持有数据，数据保存在当前线程的 `Thread.currentThread().threadLocals`（即 `ThreadLocalMap`）中。`ThreadLocalMap` 的 `Entry` 继承自 `WeakReference<ThreadLocal<?>>`，其 **Key** 是对 `ThreadLocal` 对象的弱引用，而 **Value** 是强引用。
    *   当外部没有对 `ThreadLocal` 对象的强引用时，一旦发生 GC，**Key 会被回收变为 null**；
    *   但是只要所属线程没有终止（比如 Web 容器的 Tomcat 线程池中核心线程长久存活），强引用链路：`Thread Ref -> Thread -> ThreadLocalMap -> Entry -> Value` 依然成立！导致 Key 为 null 的那个 Value 永远无法被回收，发生**内存泄漏**。
*   **线程池复用带来的业务灾难（脏数据/身份越权）**：
    Tomcat 线程池的工作线程是长期复用的。如果前一个请求（用户 A）在处理完毕后没有清理 `ThreadLocal`，当该线程被分配给后一个请求（用户 B）时，用户 B 的代码读取 `UserContext` 就会直接读到用户 A 的身份信息，造成严重的**越权漏洞与数据错乱**。
*   **避坑最佳实践**：
    必须在拦截器的 `afterCompletion` 中，或者业务代码的 `try-finally` 块中无条件执行 `UserContext.remove()`。

### Q9：MySQL 为什么针对大文本和深分页慢？
> **面试官提问**：
> “你的项目提到解决了‘正文大文本导致深分页慢查’。从 MySQL InnoDB 存储引擎底层原理解释一下，为什么 `SELECT * FROM book_content WHERE book_id = 100 ORDER BY id LIMIT 1000000, 20` 会非常慢？怎么优化？”

#### 🎯 考察意图
考察 InnoDB 聚簇索引、二级索引、回表（Random Disk I/O）、覆蓋索引与延迟关联。

#### 💡 标杆回答解析
*   **慢查底层本质**：
    执行上述 SQL 时，MySQL 假设使用了二级索引：
    1.  需要在二级索引树上扫描满足 `book_id = 100` 的前 **1,000,020 条**记录的主键 ID；
    2.  拿到每一个主键 ID 后，去聚簇索引（B+ 树）进行回表查询，读取整行数据（包含占用极大的正文 `TEXT` 字段），这个过程产生了 100 多万次**磁盘随机 I/O**；
    3.  最后内存抛弃前 1,000,000 条，仅仅将最后的 20 条返回给客户端。99.9% 的回表 IO 全被浪费掉了。
*   **优化方案**：
    *   **方案一：延迟关联（覆盖索引扫描，最推荐）**：
        ```sql
        SELECT t1.* FROM book_content t1
        JOIN (
            SELECT id FROM book_content
            WHERE book_id = 100 ORDER BY id LIMIT 1000000, 20
        ) t2 ON t1.id = t2.id;
        ```
        利用覆盖索引只在二级索引树上扫 ID（纯内存高速），只对最后筛选出的 20 个 ID 进行回表，将 100 万次回表减少为 20 次。
    *   **方案二：基于上一次游标（Seek 分页）**：
        如果前端支持瀑布流，记录上一页最大的 `id`：
        ```sql
        SELECT * FROM book_content WHERE book_id = 100 AND id > #{lastMaxId} ORDER BY id LIMIT 20;
        ```
        直接定位到 B+ 树叶子节点向后扫描 20 条，性能不受偏移量大小影响，时间复杂度稳定为 $O(\log N)$。
