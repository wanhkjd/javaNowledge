### 1. G1 垃圾回收器相比 CMS 做了哪些核心优化？它的可配置停顿时间是如何实现的？

#### (1) 相比 CMS 的核心优化
1. **内存布局与分代模型**：
   - **CMS**：基于传统的物理分代连续内存空间（固定大小的年轻代与老年代）。
   - **G1**：打破物理连续分代，将整个堆内存划分为约 2048 个大小相等且独立的 **Region**（1MB~32MB），每个 Region 动态扮演 Eden、Survivor、Old 或 Humongous（大对象）区域，内存管理粒度更细、更灵活。
2. **垃圾回收算法与内存碎片**：
   - **CMS**：老年代采用 **Mark-Sweep（标记-清除）** 算法，会产生大量内存碎片，当无连续空间分配大对象时会退化为 Serial Old 触发耗时极长的 Full GC。
   - **G1**：局部（Region 之间）采用 **Copying（标记-复制）** 算法，全局采用 **Mark-Compact（标记-整理）** 思想，回收时将存活对象复制整理到空闲 Region，**从根本上消除了内存碎片**。
3. **回收范围与收益比（Garbage-First）**：
   - **CMS**：必须对整个老年代进行全量回收。
   - **G1**：后台维护各 Region 回收价值优先级列表（即垃圾占比与预计耗时），优先回收垃圾最多、收益最大的 Region（Garbage-First），支持 **Mixed GC**（混合回收新生代 + 部分老年代）。
4. **并发漏标解决方案**：
   - **CMS** 使用**增量更新（Incremental Update）**，重新标记阶段需重新扫描黑色对象，STW 时间不稳定。
   - **G1** 使用 **SATB（Snapshot-At-The-Beginning，原始快照）** 结合写前屏障（Write Barrier），将变动的旧引用记录到 SATB 队列中，配合 RSet（Remembered Set）大幅缩短重新标记（Remark）的 STW 时间。

#### (2) 可配置停顿时间（`-XX:MaxGCPauseMillis`）的实现原理
- G1 内部构建了基于**衰减标准差的衰减平均历史预测模型（Decay Average Model）**。
- 在运行过程中，G1 实时统计每个回收阶段的实际耗时（如单个 Region 复制耗时、RSet 扫描与更新耗时、卡表清理耗时等）。
- 当触发 GC 时，G1 根据用户设置的期望停顿目标（默认 200ms），结合预测模型计算在限定时间内最多能回收多少个 Region，动态构建当次回收的 **CSet（Collection Set，回收集）**，确保停顿时间尽量不超出目标值。

### 2. 如果业务配置的期望停顿时间过小，会出现什么问题？

`-XX:MaxGCPauseMillis` 是一个软目标（Soft Target），如果设置过小（例如堆有 8G 却设置了 10ms）：
1. **单次回收的 CSet 极小**：为了满足极短的停顿时间，G1 每次 GC 只能选择极少量的 Region 进行清理，释放的内存空间杯水车薪。
2. **GC 触发频率暴增，吞吐量断崖式下跌**：由于每次回收的内存太少，堆很快再次被填满，导致 Young GC / Mixed GC 频繁触发。虽然单次停顿时间短，但 **GC 耗时在应用总运行时间中的占比（GC Overhead）显著上升**，导致系统处理业务请求的整体吞吐量严重下降。
3. **内存回收速度跟不上对象分配速度**（Reclaim Rate < Allocation Rate）。
4. **最终引发并发失败（Concurrent Mode Failure）并退化为单线程 Full GC**：老年代被迅速填满，无法容纳晋升对象或大对象，G1 被迫退化为长时间全堆 STW 的 Full GC，导致秒级甚至数十秒的服务不可用，彻底违背低停顿的初衷。

### 3. Java 中对于共享变量做无锁并发处理有哪些常用方式？说明 CAS 的实现逻辑。

#### (1) 常用无锁并发方式
1. **J.U.C 原子类（`java.util.concurrent.atomic`）**：
   - 基本类型：`AtomicInteger`、`AtomicLong`、`AtomicBoolean`。
   - 引用类型：`AtomicReference`、带版本号防 ABA 的 `AtomicStampedReference`。
   - 高并发分段累加器：`LongAdder`、`LongAccumulator`（采用分段 `Cell[]` 数组分散热点，高并发下性能远高于单一 CAS 的 `AtomicLong`）。
2. **无锁并发容器与队列**：
   - `ConcurrentLinkedQueue`（基于 Michael & Scott 无锁队列算法）、`ConcurrentSkipListMap`（无锁跳表）。
3. **线程本地隔离**：
   - `ThreadLocal`（在 `novel` 和 `hmall` 项目中均用来无锁隔离用户登录上下文，杜绝线程复用串号）。
4. **底层 Unsafe / VarHandle**：通过 JVM 提供的直接内存原子更新指令实现状态变更。

#### (2) CAS（Compare-And-Swap）的实现逻辑
- **核心三要素**：内存位置 $V$（Variable）、预期原值 $A$（Expected）、拟写入的新值 $B$（New）。
- **逻辑流程**：
  1. 读取内存地址 $V$ 处的当前值；
  2. 比较当前值是否等于预期值 $A$；
  3. 若相等，说明在此期间无其他线程修改该变量，原子地将 $V$ 更新为新值 $B$，并返回 `true`；
  4. 若不相等，说明存在并发冲突，不执行更新并返回 `false`（上层调用通常配合 `while` 自旋重试）。
- **底层调用**：Java 通过 `Unsafe` 本地方法（native）调用 HotSpot JVM 的 `Atomic::cmpxchg`。

### 4. ABA 问题会引发什么样的具体业务错误？

#### (1) ABA 问题本质
线程 1 读取变量为 A，准备更新；此时线程 2 将变量修改为 B，随后又修改回 A。线程 1 执行 CAS 时比对数值依然是 A，判定无修改并执行更新成功。虽然数值相同，但对象的**状态、版本、拓扑结构或业务语义已经发生了隐式改变**。

#### (2) 具体业务错误场景
1. **无锁栈（Treiber Stack）节点复用导致野指针与节点丢失**：
   - 栈顶为 `Top -> A -> B -> C`。
   - 线程 1 准备出栈 A，读取 `Top = A`，记录 `next = B`，随后被挂起；
   - 线程 2 连续出栈 A、B，之后 A 节点被重新分配并压入栈顶（当前栈为 `Top -> A -> C`，而 B 此时已被释放或移作他用）；
   - 线程 1 恢复执行 `CAS(Top, A, B)` 成功，导致栈顶 `Top` 错误指向了已废弃的 B，节点 C 彻底从链表中丢失，造成内存泄漏与数据错乱。
2. **电商/金融账户交易业务状态回退**：
   - 假设用户账户余额为 100 元，某营销活动逻辑判定“若余额为 100 且状态正常则发放专属返现”；
   - 期间用户发生了一笔 50 元扣款（余额变 50），随后又有一笔 50 元退款入账（余额变回 100）；
   - 若仅靠 CAS 判断余额数值为 100，会误判为“账户无状态变化”，导致重复触发状态变更或流水对账错乱。
3. **解决方案**：引入版本号/时间戳控制，Java 中使用 `AtomicStampedReference` 维护 `[引用, stamp]`，MySQL 中使用乐观锁 `version` 字段（在 `hmall` 项目的支付状态机更新中即采用乐观条件判断）。

### 5. CAS 在底层实现上为什么不会被多线程上下文切换打断呢？

1. **单条硬件级汇编指令**：在 x86/x64 架构下，CAS 最终被编译为单条 CPU 汇编指令 `cmpxchg`（Compare and Exchange）。
2. **多核 CPU 下的 `lock` 前缀**：在多核环境下，JVM 会在指令前加上 `lock` 前缀，即 `lock cmpxchg`。
3. **硬件级锁定保证原子性**：
   - **总线锁（早期）**：拉低 CPU 总线上的 `LOCK#` 信号，在指令执行期间独占总线，阻断其他核心的内存访问。
   - **缓存锁（现代）**：基于 **MESI 缓存一致性协议**，锁定目标数据所在的 Cache Line（缓存行），在当前核心完成比对和写入之前，其他核心对该缓存行的读写都会被阻塞或使缓存失效。
4. **为什么不会被上下文切换打断**：
   - 操作系统进行线程上下文切换依赖于 **CPU 中断**（如时钟中断、系统调用中断）；
   - **CPU 在硬件执行流水线层面，必须在当前微指令/单条汇编指令执行完毕（Instruction Boundary）之后，才会响应并处理外部中断请求**；
   - `lock cmpxchg` 作为一条不可分割的硬件级原子指令，CPU 绝不会在指令执行到一半时挂起当前线程去进行上下文切换。

### 6. 创建联合索引时字段放置顺序会不会影响查询效率？为什么？

**结论：会极大地影响查询效率。**

**原因**：
1. **B+ 树多列物理排序机制**：联合索引（如 `INDEX(a, b, c)`）严格按照字段定义的先后顺序进行全局多级排序（先按 `a` 排序；在 `a` 相同的前提下按 `b` 排序；在 `a, b` 都相同的前提下按 `c` 排序）。
2. **最左前缀匹配限制**：如果不按最左前缀查询（如仅查询 `WHERE b = 1 AND c = 2`），由于 `b, c` 在全局并非有序，B+ 树无法进行二分查找定位，导致索引失效，引发全表或全索引扫描。
3. **范围查询的中断效应**：如果查询包含范围条件（如 `WHERE a = 1 AND b > 10 AND c = 2`），在 `b > 10` 之后的字段 `c` 将无法继续利用 B+ 树做有序快速定位，因为在 `b` 的不同值区间内，`c` 仅是局部有序。因此工程上通常建议**等值字段在前，范围字段在后**。
4. **字段区分度（Cardinality）过滤性**：高区分度字段放在前缀，能使 B+ 树在树形向下遍历的早期阶段迅速收敛搜索分支。

### 7. 最左前缀匹配原则下，如果联合索引的三个字段在查询条件里都用到了等值匹配，这时候调整这几个字段在索引中的先后顺序，还会不会影响查询效率？

1. **对于该特定全等值查询本身**：
   - **MySQL 优化器（Optimizer）会自动重排 `WHERE` 条件顺序**：无论 SQL 写成 `WHERE a=1 AND b=2 AND c=3` 还是 `WHERE c=3 AND b=2 AND a=1`，优化器都会重排为与索引匹配的顺序，**均能 100% 命中联合索引进行 B+ 树二分查找**；
   - 从根节点到叶子节点的查找路径与树高一致，单次查询的效率几乎没有区别。
2. **但在实际工程与全局业务场景中，索引字段顺序依然至关重要**：
   - **索引复用能力**：索引 `(a, b, c)` 可以支持 `where a=1`、`where a=1 and b=2` 的查询；如果改成 `(c, b, a)`，只有 `where a=1` 的查询就无法命中索引。必须将**通用性更强、覆盖查询场景更多**的字段放在前面。
   - **排序与分组（Avoid filesort）**：如果查询包含 `ORDER BY b, c`，只有索引为 `(a, b, c)` 时，在 `a=1` 的前提下才能利用索引天然有序性消除 `Using filesort`。

### 8. 区分度高的字段放前面可以更早过滤数据，那在 InnoDB 的 B+ 树联合索引结构里，多个等值查询条件下，字段区分度的高低到底是怎样影响实际扫描的索引记录数量的？

1. **全等值且命中唯一确定叶子节点的场景**：
   - 若 `WHERE a=1 AND b=2 AND c=3` 无论索引是 `(a, b, c)` 还是 `(c, b, a)`，最终在 B+ 树叶子节点上满足条件的物理记录总行数是完全相同的，**最终扫描读取的叶子结果记录数没有差异**。
2. **区分度高低影响实际扫描效率与行数的深层机制**：
   - **B+ 树非叶子节点（目录页）的查找与比较开销**：
     若首字段区分度极高（如 `user_id`），非叶子节点在每层做二分查找时，仅通过第一列即可快速确定下一层子节点指针；若首字段区分度极低（如只有 0/1 的 `status` 字段），非叶子节点的大量键值第一列完全相同，CPU 必须反复比对第二、第三列，增加了目录页查找的指令周期。
   - **部分等值查询场景下的扫描行数差异**：
     业务常出现只传部分字段的情况。若区分度高的 `a` 在前，`WHERE a = 1` 仅需扫描定位极窄的叶子区间（几条记录）；若将区分度极低的字段放在第一列，当只有首列查询时，需要扫描大半个叶子链表（数十万条记录）。
   - **ICP（Index Condition Pushdown，索引下推）与范围过滤**：
     高区分度字段在前能极早收窄 B+ 树索引扫描的初试边界区间，减少引擎层向 Server 层传递的记录行数与回表（Look up）次数。

### 9. 说明 TCP 三次握手的完整流程，以及为什么不能改成两次握手？

#### (1) 完整流程
1. **第一次握手（SYN）**：客户端随机生成初始序列号 `seq = X`（`client_isn`），向服务端发送 `SYN = 1, seq = X` 报文，客户端进入 `SYN_SENT` 状态。
2. **第二次握手（SYN + ACK）**：服务端收到后，分配资源，随机生成服务端初始序列号 `seq = Y`（`server_isn`），向客户端发送 `SYN = 1, ACK = 1, seq = Y, ack = X + 1` 报文，服务端进入 `SYN_RCVD` 状态。
3. **第三次握手（ACK）**：客户端收到确认后，发送 `ACK = 1, seq = X + 1, ack = Y + 1` 报文，客户端进入 `ESTABLISHED` 状态；服务端收到该 ACK 报文后，也进入 `ESTABLISHED` 状态。连接正式建立（第三次握手可携带应用层数据）。

#### (2) 为什么不能改成两次握手？
1. **确认双方双向收发能力的最小握手次数**：
   - 第一次握手：服务端确认“客户端发正常、服务端收正常”；
   - 第二次握手：客户端确认“服务端收发正常、客户端收发正常”；
   - 若只有两次握手，**服务端无法得知客户端是否成功收到了自己的 SYN 报文**，即服务端无法验证自己的发送能力和客户端的接收能力。
2. **双方初始序列号（ISN）的可靠同步**：
   TCP 是面向字节流的可靠传输，双方必须获知并确认彼此的起始序号。两次握手只能确认客户端收到了服务端的序列号，但服务端的初始序列号 `server_isn` 没有收到客户端的 ACK 确认。
3. **防止历史滞留的旧 SYN 报文建立无效错误连接（RFC 793 核心原因）**。

### 10. 如果客户端发出的第一个 SYN 报文并没有丢失，只是在网络中长时间滞留，等它到达服务端触发两次握手的连接建立后，会造成服务端的什么资源浪费？

#### 场景过程
客户端发送 SYN1 因网络延迟滞留；客户端超时后重发 SYN2，正常通信完毕并关闭连接。随后滞留的旧 SYN1 到达服务端。若是**两次握手**，服务端只要收到 SYN1 发出 ACK 就会直接进入 `ESTABLISHED` 状态并分配资源；而客户端处于 CLOSED 状态，收到服务端的 SYN+ACK 会直接回复 RST 甚至忽略。

#### 造成的服务端资源浪费：
1. **Socket 文件描述符（FD）耗尽**：操作系统为每个 Socket 分配文件句柄，大量幽灵连接会耗尽系统的 `nofile` / `max_files` 限制。
2. **内核传输控制块（TCB, Transmission Control Block）内存占用**：Linux 内核必须为每个 Established 状态连接分配 TCB 结构体，维护滑动窗口、序列号、重传定时器等信息。
3. **Socket 读写缓冲区内存浪费**：内核为每个连接预分配接收与发送缓冲区（默认数 KB 到数十 KB），海量僵尸连接会吞噬物理内存。
4. **工作线程/连接池资源被占满**：如果是传统的多线程/BIO 架构（或 Tomcat 工作线程池），一个 Established 连接可能长期绑定一个 Worker 线程，导致线程池被耗尽，拒绝正常客户端的新请求。
5. **CPU 保活定时器轮询开销**：内核需要定期运行 KeepAlive 定时器进行心跳探测，增加无谓的 CPU 调度开销。

### 11. 设计一个积分抽奖系统，支持每秒一万次抽奖请求，奖品库存有限，你会怎么设计核心流程？

结合在 **「万佳商城电商系统」** 与 **「novel 小说系统」** 中的高并发架构经验（Redis + Sentinel 限流 + RabbitMQ 削峰解耦 + 幂等设计）：

```
[客户端请求 10,000 QPS]
       │
       ▼
[Spring Cloud Gateway / Sentinel] ──> 单用户/IP限流防刷、QPS匀速排队
       │
       ▼
[抽奖服务集群 (无状态)]
       │
       ├─> 1. Redis Lua 执行用户积分预扣减 (decrby points) ──(积分不足)──> 快速失败
       │
       ├─> 2. Redis Lua 执行加权随机选奖 & 奖品库存原子扣减 (decr stock)
       │       ├── 扣减成功 ──> 命中奖品
       │       └── 库存为 0 ──> 降级为安慰奖/谢谢参与 (无库存扣减)
       │
       ├─> 3. 即时组装抽奖结果，内存直接响应前端 (< 10ms，抗住万级并发)
       │
       ▼
[RabbitMQ 异步解耦削峰] (Publisher Confirm + 事务同步器保证可靠投递)
       │
       ▼
[异步落库消费者 Consumer] (基于 draw_id 唯一索引实现幂等)
       │
       ├─> 插入中奖流水记录表 (唯一键防重)
       ├─> 真实扣减 MySQL 用户积分
       └─> 乐观 SQL 扣减 MySQL 奖品库存: WHERE stock > 0
```

#### 核心流程四步走：
1. **入口层防护与限流**：
   - 网关层 JWT 统一鉴权，提取用户上下文；
   - 接入 Sentinel 配置单用户/IP 频次限制（防外挂连点器）及系统级 QPS 匀速排队防护。
2. **全内存高速判定（Redis Lua 脚本原子化执行）**：
   - **积分校验与预扣**：在 Redis 中维护用户积分，Lua 脚本内先判断 `points >= cost`，满足则 `DECRBY`，不满足直接返回积分不足。
   - **选奖与库存预扣减**：基于加权随机算法在 Redis 内存中计算目标奖品，并执行 `HINCRBY prize_stock -1` 原子扣减库存。
3. **极速响应与 MQ 削峰**：
   - 抽奖结果在内存生成后立即响应用户，接口响应时间控制在 5~10ms，轻松支撑 10,000 QPS；
   - 将中奖上下文（`userId`, `drawId`, `prizeId`, `costPoints`, `timestamp`）投递至 RabbitMQ 消息队列。
4. **异步事务落库与消费幂等**：
   - 消费端平滑消费，开启本地事务：
     - 插入中奖记录表，以 `draw_id` 为唯一索引实现**消费幂等**；
     - 扣减 MySQL 积分与奖品库存（乐观更新 `WHERE stock >= num`）；
     - 若消费异常，配合死信队列（DLX）与重试机制保障数据最终一致性。

### 12. 用 Redis 做库存预扣减，异步落库的流程。那在这个流程里，你会怎么设计奖品的概率控制，来保证不同奖品的实际中奖概率符合预设值，同时不会出现超发？

#### (1) 保证不同奖品实际中奖概率符合预设值
- **离散区间映射法（绝对概率空间模型）**：
  1. 设定总概率空间基数（如 $100,000$，对应精度 0.001%）；
  2. 按照各奖品预设概率划分非重叠区间，例如：
     - 特等奖（1%）：$[1, 1000]$
     - 一等奖（5%）：$[1001, 6000]$
     - 二等奖（10%）：$[6001, 16000]$
     - 谢谢惠顾/未中奖（84%）：$[16001, 100000]$
  3. 每次抽奖生成独立随机数 $R \in [1, 100000]$，根据 $R$ 所在区间判定命中奖品。
- **关键原则（避免概率扭曲）**：
  当 $R$ 落在特等奖区间，若此时特等奖 Redis 库存已被扣完（`stock <= 0`），**绝不能将抽奖请求顺延给一等奖或重新抽奖**（否则会导致其他奖品实际中奖概率被动升高），而**必须直接降级判定为“未中奖/谢谢参与”**。这样能严格保证所有奖品在其库存消耗期间，实际中奖概率与预设数学期望完全吻合。

#### (2) 保证绝对不会超发（防超卖）
1. **Redis 层面原子校验扣减**：
   所有库存预扣减封装在单段 Lua 脚本中执行：
   ```lua
   local stock = tonumber(redis.call('HGET', KEYS[1], ARGV[1]))
   if stock and stock > 0 then
       redis.call('HINCRBY', KEYS[1], ARGV[1], -1)
       return 1 -- 扣减成功
   else
       return 0 -- 库存不足
   end
   ```
2. **MySQL 异步落库行级条件兜底**：
   ```sql
   UPDATE prize SET stock = stock - 1 WHERE id = #{prizeId} AND stock > 0;
   ```
   更新受影响行数若为 0，触发告警并补偿回滚 Redis 积分。

### 13. 把未发完的奖品放入候选池做加权随机，那这个加权随机的具体计算逻辑是怎么实现的？怎么保证在高并发下这个计算过程既高效又不会出错？

#### (1) 加权随机具体计算逻辑实现
针对动态候选池（仅包含当前 `stock > 0` 的奖品），推荐采用 **前缀和 + 二分查找法（Prefix Sum + Binary Search）**：
1. 获取当前候选池中 $n$ 个奖品的剩余权重数组 $W = [w_1, w_2, \dots, w_n]$；
2. 构建权重前缀和数组 $S = [s_1, s_2, \dots, s_n]$，其中 $s_k = \sum_{i=1}^k w_i$，总权重 $S_{total} = s_n$；
3. 生成随机数 $R = \text{Random}(1, S_{total})$；
4. 利用二分查找在 $S$ 数组中定位第一个满足 $s_k \ge R$ 的索引 $k$，奖品 $k$ 即为命中结果。
   - 时间复杂度仅为 $O(\log n)$，在候选池规模 $n \le 100$ 时仅需 5~6 次 CPU 比较，耗时在微秒级。

#### (2) 高并发下高效且不出错的保障机制
1. **高效性保障（全内存执行）**：
   - 候选池元数据与权重数组常驻 Redis Hash / ZSet（或应用层本地缓存），所有前缀和计算与随机查找在内存中完成，无任何磁盘或网络 I/O 阻塞。
2. **不出错与并发一致性保障（Lua 脚本原子闭环）**：
   - 将 **“读取有效奖品池 -> 计算动态权重前缀和 -> 随机二分命中 -> 原子扣减库存 -> 若遇极端售罄则移出候选池重试”** 完整打包在单一 Redis Lua 脚本中。
   - 利用 Redis 单线程执行 Lua 脚本的原子隔离性，杜绝多线程并发计算时产生的竞态条件与脏读，确保并发下的绝对正确。

### 15. 落地这个方案的时候，有没有遇到过一开始判断出错，后来被实际测试或者线上反馈推翻调整的具体情况？

> **真实踩坑与架构调整案例**：**在 `@Transactional` 事务内直接发送 RabbitMQ 消息导致的并发脏读与数据不一致问题**。

#### (1) 初始判断与方案
在实现业务更新与异步消息解耦时（例如支付成功更新订单状态，或小说平台中作家更新章节后发送 MQ 驱动 Elasticsearch 同步），最初的写法是在 `@Transactional` 标注的 Service 方法内部，直接调用 `rabbitTemplate.convertAndSend()` 发送消息通知下游消费者。

#### (2) 实际测试暴露的问题（推翻初始方案）
在高并发压测和偶发网络延迟场景下，出现了**下游消费者处理异常**：
1. **并发脏读/数据未找到**：MQ 消息发送与网络传输极快（几毫秒内抵达），下游消费者收到消息后立即去 MySQL 查询最新数据，但此时上游的数据库事务**尚处于提交阶段（Commit 中未完成）**，导致下游查询到的是旧数据或直接报错“数据不存在”；
2. **事务回滚引发的幽灵消息**：当上游 Service 在发完 MQ 之后的代码中抛出异常导致本地事务回滚时，MQ 消息却已经不可逆地发到了 Broker，下游消费到了本已回滚作废的脏数据。

#### (3) 调整与优化落地
全面推翻在事务体内直接发消息的做法，引入 **Spring 事务同步管理器（`TransactionSynchronizationManager`）** 进行重构：
```java
// 仅在本地事务 100% 成功 Commit 之后才触发 MQ 投递
if (TransactionSynchronizationManager.isActualTransactionActive()) {
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            rabbitTemplate.convertAndSend(exchange, routingKey, msg);
        }
    });
} else {
    rabbitTemplate.convertAndSend(exchange, routingKey, msg);
}
```
通过将消息投递绑定在 `afterCommit` 钩子中，彻底解决了事务与消息的生命周期倒挂问题；配合消费端的业务唯一键幂等校验，系统数据一致性达到了 100%。
