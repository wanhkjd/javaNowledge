# 高并发下单/支付链路：四阶段架构要点

> 来源：B站视频 BV1Jae16UEuE ｜ 主讲：java架构师百里

**核心问题**：从用户点击下单到数据库扣减库存成功，在高并发下每个环节的风险与对策。按请求流转分为四个阶段。

---

## 一、接入层（NGINX / 网关）

**风险**：流量洪峰打垮后端；下游服务故障拖垮上游。

- **限流**：令牌桶 / 漏桶算法。例如每秒放行 1000 个请求，超出的直接返回 `429`。
- **熔断**：错误率 / 超时率超过阈值自动跳闸，走降级逻辑。三态流转：

  | 状态 | 含义 | 转换 |
  |---|---|---|
  | 关闭 Closed | 正常放行 | 超阈值 → 开启 |
  | 开启 Open | 跳闸，直接降级 | 隔一段时间 → 半开 |
  | 半开 Half-Open | 放几个请求探路 | 通了→关闭 / 不通→继续开启 |

## 二、业务层

**风险**：超卖、重复下单。

- **防超卖**
  - 读多写少：乐观锁，更新时加库存 > 0 的条件。
    ```sql
    UPDATE stock SET count = count - 1 WHERE product_id = #{id} AND count > 0;
    ```
  - 写冲突高：Redis `DECR` 在缓存扣减（抗并发强），再异步同步数据库。
- **防重复下单（幂等）**
  - 兜底：订单号建唯一索引，重复插入直接报错。
  - 通用：分布式锁 + 状态机。先用订单号抢 Redis 锁，再查状态，若已「支付中 / 支付成功」则直接返回。

## 三、中间件（MQ）

**目的**：削峰填谷，避免庞大流量直接打到脆弱的数据库。

- 流程：请求封装成消息入 MQ → 前端立即返回「处理中」→ 消费者按数据库能力拉取消息、扣减落库。
- 三个追问点：
  - **消息丢失**：生产者确认机制 + MQ 持久化 + 消费者手动 ACK。
  - **重复消费**：消费者做幂等处理。
  - **消息积压**：扩容消费者实例；或转移到新 topic 用更多机器消化。

## 四、存储层

**风险**：单表过亿后读写骤慢；分表后自增主键冲突。

- **分库分表**：解决单表瓶颈。
- **全局唯一 ID —— 雪花算法（64 位）**：1 符号位 + 41 时间戳 + 10 机器 id + 12 序列号。
- **时钟回拨处理**：记录上次生成时间戳并对比；回拨时间短 → 线程等待或用预留序列号缓冲；回拨时间长 → 抛异常并切换备用机器 id。

---

## 关键考点速记

| 考点 | 答案 |
|---|---|
| 幂等性 | 唯一索引 + 分布式锁 + 状态机 |
| 缓存与数据库不一致 | Redis 扣减 + 异步同步数据库 |
| 下游故障 | 熔断降级（关闭 / 开启 / 半开三态） |
| 乐观锁 vs 悲观锁 | 读多写少用乐观锁；写冲突高走 Redis 扣减 |
| 分布式 ID | 雪花算法 + 时钟回拨兜底 |
