# 【大厂面试】Function Calling、MCP、A2A 到底有什么区别与联系？

> 来源：B站视频 BV19sa36qE6d ｜ 主讲：AI探索喵

---

## 一、一句话直觉：三个形象的比喻

| 概念 | 比喻 | 作用 |
|------|------|------|
| **Function Calling** | 模型的"手" | 模型自己调不了 API，只能输出文字。FC 让它表达出"我想调哪个函数、参数是什么"这个**意图**。 |
| **MCP** | 工具连接的"USB-C" | 以前 agent 每对接一个工具都要单独写适配代码；MCP 把连接方式**标准化**了。 |
| **A2A** | agent 之间的"协作语言" | 当你有多个专业 agent（客服、订单、物流），它们之间如何分派任务、汇报结果——A2A 定义了这套规则。 |

**最关键的认知：这三者根本不在同一个层次上，是一层一层往上搭的。**

- Function Calling —— 模型**内部能力**
- MCP —— 解决 **agent ↔ 工具** 的连接
- A2A —— 解决 **agent ↔ agent** 的协作

---

## 二、Function Calling：让模型"能动手"

**常见误区**：以为 Function Calling 是模型自己去执行函数。**完全不是。**

模型只做一件事：输出一段**结构化 JSON**，告诉你"我想调这个函数，参数是这些"。真正的执行由**你自己的 runtime** 完成。

**完整流程：**

1. 用户提问（例如"今天天气如何"）
2. 模型输出一个**函数调用意图**（函数名 + 参数的 JSON）
3. **你的代码**拿着这个意图去真正调用天气 API
4. 把 API 返回结果塞回给模型
5. 模型基于结果生成最终回复

**关键点：Function Calling 是模型能力，不是协议。**

- OpenAI 有 OpenAI 的格式，Anthropic 有 Anthropic 的格式，**互相不通**。
- 如果直接硬编码某一家的格式，以后想换模型就特别麻烦。
- 👉 这正是需要 MCP 的原因。

---

## 三、MCP：让 agent"有工具可用"

**全称**：Model Context Protocol，由 Anthropic 率先提出，后捐赠给基金会托管，现为**开放标准**。

**架构（Client-Server 模式，非常简单）：**

- 左边 **MCP Client** = 你的 agent
- 右边 **MCP Server** = 各种工具和数据源
- 中间跑 **MCP 协议**

**MCP Server 暴露三种能力：**

| 能力 | 作用 | 类比 / 举例 |
|------|------|------------|
| **Resources** | 提供数据 | 相当于 GET 接口：读取文件、查数据库 |
| **Tools** | 执行操作 | 发邮件、创建工单 |
| **Prompts** | 复用模板 | 预置可复用的提示词模板 |

**核心价值：解耦。**

- 以前：N 个模型接 M 个工具 = **N × M** 套适配代码。
- 有了 MCP：模型侧、工具侧各对接一次，**N + M** 搞定。

**重要更新（面试加分项）：** MCP 最新版本做了**无状态化重构**，变成纯 HTTP 协议，可以部署在 API Gateway 后面做负载均衡、水平扩展——这是它走向**企业级**的关键一步。

---

## 四、A2A：让 agent"有队友可协作"

**全称**：Agent-to-Agent Protocol，由 Google 推出。

**目标**：让**不同框架**做出来的 agent 能互相通信、互相协作。

**通信模型与前两者完全不同——核心单元逐级变大：**

| 概念 | 通信单元 |
|------|---------|
| Function Calling | 一次**调用** |
| MCP | 一次**工具请求** |
| A2A | 一个**任务（Task）** |

**典型流程（举例：做一份市场分析）：**

1. 协调 agent 先去查其他 agent 的 **Agent Card**（能力"名片"：我能干什么、怎么跟我交互）
2. 发现"分析 agent"擅长此事，就发一个 **Task** 过去
3. 分析 agent 收到后**异步执行**，过程中通过**事件流**持续汇报状态（正在处理 / 完成 / 失败）

**特点**：A2A 不关心你内部用什么框架、什么模型，只管**外部通信规则**——可以理解成 **agent 世界的 HTTP**。

---

## 五、串起来：三层能力栈

三者是**递进关系（不是替代关系）**的三层栈：

```
┌──────────────────────────────────────────────┐
│  A2A —— agent 协作层                           │  多个 agent 互相发现、委派任务、跟踪进度
├──────────────────────────────────────────────┤
│  MCP —— 工具连接层                             │  agent 统一接入数据库 / API / 文件系统
├──────────────────────────────────────────────┤
│  Function Calling —— 推理执行层                 │  模型如何表达"调用意图"
└──────────────────────────────────────────────┘
```

真正复杂的 agent 系统，三层都会用到：**底层做推理，中间接工具，上层做编排。**

## 七、怎么选型？

**一条实用的判断标准（边界）：**

- 面对**被动**的资源（数据库、API、文件系统）→ 用 **MCP**
- 面对有**自主推理能力的 agent** → 用 **A2A**

边界一清楚，选型就不会乱。

**按项目复杂度渐进选择：**

| 场景                             | 方案                          |
| ------------------------------ | --------------------------- |
| 简单：一个模型 + 两三个固定工具              | 直接 **Function Calling** 就够了 |
| 工具 / 数据源越来越多，多个应用都要复用          | 上 **MCP** 做接入层标准化           |
| 多角色分工协作（客服 / 订单 / 物流各司其职，互相委派） | 引入 **A2A**                  |

## 八、它们可以共存：一个生产级架构

```
                编排 Agent
                   │  (A2A 分派任务)
        ┌──────────┼──────────┐
        ▼          ▼          ▼
    客服 Agent   订单 Agent   物流 Agent      ← 专业 agent
        │          │          │
        │   (MCP 对接外部系统)
        ▼          ▼          ▼
      CRM        ERP        数据库
```

- 最上面的**编排 agent** 通过 **A2A** 把任务分派给各专业 agent
- 每个专业 agent 再通过 **MCP** 对接 CRM / ERP / 数据库
- 每一层**内部的模型推理**，靠的都是 **Function Calling**

**一个好记的类比：**

- **A2A** 管 agent 之间的"**外交**"
- **MCP** 管每个 agent 的"**内政**"
- **Function Calling** 是最底层的"**基本功**"

分层清晰了，架构就不会乱。

## 九、总结

| 层 | 一句话 |
|----|--------|
| **Function Calling** | 让模型**能动手** |
| **MCP** | 让 agent **有工具可用** |
| **A2A** | 让 agent **有队友可协作** |

三者构成从**推理 → 工具 → 协作**的**三层能力栈**，是**互补关系，不是竞争关系**。

面试时把 **「比喻 + 层次 + 对比表」** 讲清楚，面试官就知道你是真的理解了。
