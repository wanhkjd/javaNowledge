## 一、MVCC 是什么

- **全称**：Multi-Version Concurrency Control，多版本并发控制。
- **本质**：事务隔离级别的一种**无锁实现方式**，用于提升事务的并发性能。
- **定位**：它是部分事务隔离级别的**底层实现机制**——但并非所有隔离级别都用 MVCC（只有「读已提交」和「可重复读」用到）。

> 要讲清 MVCC，先要理解事务的隔离级别。

---

## 二、事务隔离级别与并发问题

多个事务并发读写**同一数据**时，会产生一系列线程不安全问题；隔离级别就是用来解决这些问题的。

### 2.1 三类并发问题

| 问题 | 说明 | 典型场景 |
|------|------|----------|
| 脏读 | 读到了**其他事务未提交**的数据 | 事务A 把余额 1000→800（未提交），事务B 读到 800；随后 A 回滚，B 读到的就是脏数据 |
| 不可重复读 | 同一事务内**前后两次查询同一行**结果不一致 | A 查到余额 1200；B 改成 800 并提交；A 再查变成 800（针对**某行**，由 UPDATE 引起） |
| 幻读 | 同一事务内**前后两次统计整表**结果不一致 | A 汇总 = 3000；B 插入一条 1000 的记录；A 再汇总结果变了（针对**整张表**，由 INSERT/DELETE 引起） |

> **不可重复读 vs 幻读**：两者都是「查两次结果不同」，区别在于——幻读针对**整张表**（行数变化），不可重复读针对**具体某行的值变化**。

### 2.2 四种隔离级别

| 隔离级别 | 能解决 | 遗留问题 | 实现方式 |
|----------|--------|----------|----------|
| 读未提交 Read Uncommitted | — | 脏读、不可重复读、幻读 | 直接读写数据源，**不加锁、不用 MVCC** |
| 读已提交 Read Committed | 脏读 | 不可重复读、幻读 | **MVCC**（每次查询都创建 Read View） |
| 可重复读 Repeatable Read | 脏读、不可重复读 | 幻读 | **MVCC**（事务内只创建一次 Read View） |
| 串行化 Serializable | 脏读、不可重复读、幻读 | 并发性能最低 | **表锁**（读表时加锁，其他事务增删改需阻塞等待） |

### 2.3 默认隔离级别

- **MySQL**：可重复读（Repeatable Read）
- **Oracle**：读已提交（Read Committed）

实际开发中无需每次手动设置，数据库已提供默认级别。查询 MySQL 当前隔离级别：

```sql
SELECT @@transaction_isolation;   -- MySQL 8.0+
-- 旧版本（< 8.0）：SELECT @@tx_isolation;
```

## 三、MVCC 实现原理（以「读已提交」为例）

### 3.1 为什么不用行锁

「读已提交」要保证查询时读到的是**已提交**的数据。若用**行锁**实现：事务A 修改数据时加锁，查询就必须**阻塞等待** A 完成，退化成**串行执行**，并发性能差——可行但不是最优。所以 MySQL 改用 **MVCC**。

### 3.2 三个关键点

**① 隐藏列**：每张表除业务列外，还维护 3 个看不到的隐藏列。

| 隐藏列 | 作用 |
|--------|------|
| 事务ID（DB_TRX_ID） | 记录**最近修改该行的事务 id**（如插入时写入当前事务 id） |
| 回滚指针（roll_pointer） | 指向该行**上一版本（老数据）**在 undo log 中的位置，用于回滚、串联版本链 |
| DB_ROW_ID | 不重要；当表**无主键**时自动生成的隐藏行号 |

**② undo log（回滚日志）**：存储数据的**历史版本**。每次 UPDATE/DELETE 把老版本存入 undo log，通过回滚指针串成一条**版本链**；既方便回滚，也供 MVCC 读取历史版本。并发事务的各版本都保存在此。

**③ Read View（读视图/快照）**：查询时创建的一致性视图，决定**到版本链中读取哪个版本**。含 4 个关键信息：

| 字段 | 含义 |
|------|------|
| 当前事务 id | 发起本次查询的事务 id |
| 活跃事务列表 | 当前所有**未提交**的并发事务 id（升序排列） |
| 最小事务 id | 活跃事务中的最小 id |
| 最大事务 id | 下一个**尚未分配/未开始**的事务 id |

### 3.3 版本可见性判断（四步）

取版本链中某版本的事务ID（trx_id），依次判断：

1. **trx_id == 当前事务id？** → 本事务自己改的 → **可读**
2. **trx_id < 最小事务id？** → 事务开始前就已提交 → **可读**
3. **trx_id > 最大事务id？** → 事务开始后才产生 → **不可读**，沿回滚指针找更老版本
4. **最小 ≤ trx_id ≤ 最大？** → 落在活跃（未提交）事务区间 →「读已提交」下**不可读**

> 四条都不满足时，沿**回滚指针**取版本链的下一条（更老）数据，重复以上判断，直到命中。

### 3.4 完整示例

两个并发事务：事务A（id=10）、事务B（id=20），假设下一个未开始事务 id=21。

1. **事务A 先 UPDATE**：余额 1000 变为老版本，新值 800 为最新版本，回滚指针指向老版本（1000）。
2. **事务B 执行查询**，创建 Read View：当前=20，活跃={10,20}，最小=10，最大=21。
3. 对最新版本（trx_id=10）走判断：
   - `10 == 20`？否
   - `10 < 10`？否
   - `10 > 21`？否
   - `10 ∈ [10,21]`？是 → 属未提交事务 → 不可读
4. 沿回滚指针取老版本（1000，trx_id 为事务开始前已提交的更小值）：
   - 命中**判断 2**（trx_id < 最小事务id）→ 已提交数据 → **读取 1000** ✅

**结论**：事务B 读到的是**已提交的 1000**，而非 A 未提交的 800——脏读被规避。

### 3.5 本质

MVCC = **undo log 多版本** + **Read View 做版本可见性比较（类 CAS）**，是一种**乐观锁**思想的体现。相比行锁/悲观锁的阻塞串行，大幅提升并发性能。

## 四、各隔离级别与 MVCC 的关系

| 隔离级别 | 是否用 MVCC | 实现要点 |
|----------|:-----------:|----------|
| 读未提交 | ❌ | 直接读数据源，会读到未提交数据（脏读） |
| 读已提交 | ✅ | **每次查询**都新建 Read View，故每次可能读到不同的已提交版本 |
| 可重复读 | ✅ | 事务内**只在第一次查询**创建 Read View 并复用 → 多次查询结果一致 |
| 串行化 | ❌ | 表锁，锁粒度最大、并发最低，非必要不用 |

**读已提交 vs 可重复读的核心差异**：Read View 的创建时机——前者**每次查询都建**，后者**整个事务只建一次**。

---

## 五、总结

- **MVCC** = 多版本并发控制，是「读已提交」「可重复读」两级别的无锁底层实现。
- 三大基石：**隐藏列**（事务ID + 回滚指针）、**undo log**（版本链）、**Read View**（快照 + 四步可见性判断）。
- 通过对历史版本做可见性比较来**避免加锁**，本质是**乐观锁**，兼顾一致性与并发性能。
- 「读未提交」直接读源数据、「串行化」用表锁，二者都**不走 MVCC**。
