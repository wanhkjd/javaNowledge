## 一、背景：Redis 的正常缓存流程

Redis 的主要作用是给数据库做「挡箭牌」，减轻数据库压力。一个标准的「缓存读」流程如下（以物流系统按发货单号查物流信息为例）：

```java
public LogisticsInfo getByOrderNo(String orderNo) {
    // 1. 先查缓存
    LogisticsInfo info = redis.get(orderNo);
    if (info != null) {
        return info;                       // 命中缓存，直接返回
    }
    // 2. 缓存未命中，查数据库
    info = db.query(orderNo);
    if (info != null) {
        redis.set(orderNo, info, expireTime);   // 回写缓存 + 设置过期时间
    }
    return info;                           // 数据库也没有，则返回 null / 抛异常
}
```

逻辑上没问题，但在**高并发**场景下会暴露出击穿、雪崩、穿透三个问题。

## 二、缓存击穿（Cache Breakdown）

### 定义
**某一个热点 key 突然失效**，瞬间的大并发请求直接「击穿」Redis 打到数据库。

- 典型场景：某商品之前冷门（设了过期时间），突然变成爆款（如疫情期间的口罩、消毒水），而这个 key 恰好在高并发时刻过期。
- 危害：① 大并发直接压垮数据库；② 大量线程查到数据后**重复回写** Redis，造成没必要的性能浪费（其实存一次就够）。

### 解决方案 1：热点 key 永不过期
- 不能把所有 key 都设永不过期（Redis 存储不够）。
- 做法：可预料的热门商品设**永不过期**，冷门商品设**定时过期**。
- 对突发爆款：写个算法，当访问量**激增到某阈值**时，动态把该 key 改为永不过期。

### 解决方案 2：加锁排队（双重检查锁 Double-Checked Locking）
key 失效时加**同步锁**，只放一个线程进去查库并回写 Redis，其余线程阻塞排队；第一个线程回填缓存后释放锁，后续线程进来**再查一次 Redis 即可命中**。

```java
public LogisticsInfo getByOrderNo(String orderNo) {
    // 第一次检查：90%+ 请求在此命中缓存直接返回，不进锁
    LogisticsInfo info = redis.get(orderNo);
    if (info != null) {
        return info;
    }
    // 缓存失效，加同步锁，只放一个线程进入
    synchronized (LOCK) {
        // 第二次检查：排队线程进来时，缓存可能已被第一个线程回填
        info = redis.get(orderNo);
        if (info != null) {
            return info;
        }
        // 真正查库并回写
        info = db.query(orderNo);
        redis.set(orderNo, info, expireTime);
        return info;
    }
}
```

**三个常见疑问：**

| 疑问              | 解答                                                                                   |
| --------------- | ------------------------------------------------------------------------------------ |
| 为什么要查两遍 Redis？  | 这就是**双重检查锁**：第一次在锁外（绝大多数命中请求无需进锁），第二次在锁内（排队线程进来时缓存往往已回填，避免重复查库）。                     |
| 为什么用同步锁而不用分布式锁？ | 分布式锁更「完美」但更复杂。应用集群假设 10 台，用进程内同步锁最多也只有 **10 个线程**击穿到数据库，DB 完全扛得住。**大道至简，不要为了技术而技术。** |
| 加锁会不会拖慢性能？      | 不会。90%+ 请求在**第一次检查**就命中缓存直接返回，只有 key 恰好失效时才会走到锁的分支。                                  |

## 三、缓存雪崩（Cache Avalanche）

### 定义
与「击穿」（单个热点 key 失效）不同，雪崩是**大量 key 在同一时间集中过期**（或 Redis 宕机），导致海量请求同时打到数据库 → 数据库被压垮 → 整个应用不可用 → 系统雪崩。

### 两大原因与解决方案

| 原因 | 解决方案 |
|------|----------|
| 缓存**集中过期** | 在击穿方案的基础上，给过期时间加一个**随机值**，打散过期时刻，避免集中失效。 |
| 缓存服务器**宕机** | 提前做高可用部署：Redis **集群 + 哨兵模式**（挂一台另一台顶上）。 |
| 服务器**断电**等机房级故障 | 提前做**灾备 / 多机房**，一个机房挂掉立即切换到另一个。 |

## 四、缓存穿透（Cache Penetration）

### 定义
请求的数据 **Redis 没有、数据库也没有**，请求穿过 Redis 直达 DB 且始终查不到。

- 偶发正常；但**大量**请求都命中「两边都没有」的数据，很可能是**恶意攻击**：攻击者伪造大量不存在的 id（负数、超大数值等）疯狂请求，拖垮系统。后果严重。

### 解决方案

| 方案 | 说明 | 局限 |
|------|------|------|
| **参数校验** | 过滤负数、非法参数等明显无效请求 | 无法完全杜绝（如「多大算大」、恰好不存在的合法 id） |
| **缓存空对象** | 查库后**无论有没有数据都回写 Redis**（含空值），并**务必设过期时间**（数据以后可能被新增） | 简单最有效；可配随机过期时间，**同时防雪崩 + 防穿透** |
| **布隆过滤器** | 一种比 List / Set / Map 更高效、更省空间的数据结构，用于快速判断某 id 是否存在 | 需额外理解其原理 |

**布隆过滤器的两种用法：**
- **黑名单**：把 DB 中**不存在**的 id 放入布隆过滤器；请求先查过滤器，命中则直接返回空。
- **白名单**：把 DB 中**存在**的 id 放入布隆过滤器；请求时过滤器**有**才执行后续操作，**没有**直接返回。

## 五、三者对比与记忆口诀

把 **Redis 比作防弹衣、MySQL 比作身体**：

| 问题 | 一句话 | 本质 | 核心解决方案 |
|------|--------|------|--------------|
| 击穿 | 防弹衣被穿透，身体没事 | **单个**热点 key 失效，打到 DB（DB 扛得住） | 永不过期 / 双重检查锁 |
| 雪崩 | 直接被打死，整个系统瘫痪 | **大量** key 集中过期 或 Redis 宕机 | 随机过期时间 / 集群哨兵 / 灾备 |
| 穿透 | 防弹衣和身体都被击穿 | 请求的数据 Redis 和 DB **都没有**（常为恶意攻击） | 参数校验 / 缓存空对象 / 布隆过滤器 |
