# Java 多线程面试题

> 主题：线程基础、线程状态、锁机制、JMM、CAS、AQS、线程池、并发工具类。

## 1. 线程和进程的区别？

- **进程**：正在运行的程序实例，是系统进行资源分配的基本单位。
- **线程**：进程中的执行单元，是 CPU 调度的基本单位。一个进程中可以包含多个线程。
- **内存空间**：不同进程拥有独立的内存空间；同一进程中的多个线程共享该进程的内存空间。
- **切换成本**：线程更轻量，线程上下文切换成本通常低于进程上下文切换。

> 上下文切换：CPU 从执行一个线程/进程切换到另一个线程/进程时，需要保存和恢复执行现场。

---

## 2. 并发和并行有什么区别？

- **并发（Concurrency）**：同一时间段内处理多个任务。多个线程轮流使用一个或多个 CPU，看起来像同时执行。
- **并行（Parallelism）**：同一时刻真正同时执行多个任务。比如多核 CPU 上多个线程分别运行在不同核心上。

简单理解：

- 并发强调“同时应对多件事”；
- 并行强调“同时执行多件事”。

---

## 3. 创建线程的方式有哪些？

Java 中常见的创建线程方式有四种：

1. 继承 `Thread` 类；
2. 实现 `Runnable` 接口；
3. 实现 `Callable` 接口，配合 `Future` / `FutureTask` 获取返回值；
4. 使用线程池创建线程。

实际项目中更推荐使用**线程池**，可以统一管理线程资源，避免频繁创建和销毁线程。

---

## 4. Runnable 和 Callable 有什么区别？

| 对比项 | Runnable | Callable |
| --- | --- | --- |
| 方法 | `run()` | `call()` |
| 返回值 | 无返回值 | 有返回值，支持泛型 |
| 异常 | 不能直接抛出受检异常，只能内部处理 | 可以抛出异常 |
| 获取结果 | 不支持 | 可配合 `Future` / `FutureTask` 获取异步结果 |

补充：

- `FutureTask.get()` 可以获取 `Callable` 的执行结果；
- 如果任务还没有执行完成，调用 `get()` 会阻塞当前线程。

---

## 5. 线程的 run() 和 start() 有什么区别？

- `start()`：用于启动线程。调用后线程进入就绪状态，等待 CPU 调度，最终由 JVM 调用该线程的 `run()` 方法。一个线程对象的 `start()` 只能调用一次。
- `run()`：只是普通方法调用，里面封装了线程要执行的业务逻辑。直接调用 `run()` 不会开启新线程，而是在当前线程中执行。

---

## 6. 线程有哪些状态？状态之间如何变化？

![[线程状态变化.png|598]]

Java 中 `Thread.State` 定义了 6 种线程状态：

1. **NEW（新建）**：线程对象已创建，但还没有调用 `start()`。
2. **RUNNABLE（可运行）**：调用 `start()` 后进入该状态，等待 CPU 调度或正在运行。
3. **BLOCKED（阻塞）**：线程等待获取 monitor 锁。
4. **WAITING（等待）**：线程进入无限期等待，需要被其他线程唤醒。
5. **TIMED_WAITING（有时限等待）**：线程进入限时等待，超时后自动恢复。
6. **TERMINATED（终止）**：线程执行结束。

常见状态变化：

- 创建线程对象后，线程处于 **NEW** 状态；调用 `start()` 后进入 **RUNNABLE** 状态。
- `run()` 执行完毕后，线程进入 **TERMINATED** 状态。
- 获取锁失败时，线程从 **RUNNABLE** 进入 **BLOCKED**；获得锁后恢复为 **RUNNABLE**。
- 调用 `wait()` 后线程进入 **WAITING**，并释放锁；被 `notify()` / `notifyAll()` 唤醒后重新竞争锁。
- 调用 `sleep(long)`、`join(long)`、`wait(long)` 后进入 **TIMED_WAITING**，时间到后恢复为 **RUNNABLE**。

## 7. 如何保证 T1、T2、T3 三个线程按顺序执行？

可以使用 `join()` 方法，让一个线程等待另一个线程执行完成后再继续执行。

```java
public class JoinTest {
    public static void main(String[] args) {
        Thread t1 = new Thread(() -> System.out.println("t1"));

        Thread t2 = new Thread(() -> {
            try {
                t1.join(); // 等待 t1 执行完成
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            System.out.println("t2");
        });

        Thread t3 = new Thread(() -> {
            try {
                t2.join(); // 等待 t2 执行完成
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            System.out.println("t3");
        });

        t1.start();
        t2.start();
        t3.start();
    }
}
```

也可以使用 `CountDownLatch`、`Semaphore`、单线程线程池等方式实现顺序控制。

## 8. notify() 和 notifyAll() 有什么区别？

- `notify()`：随机唤醒一个在该对象上等待的线程。
- `notifyAll()`：唤醒所有在该对象上等待的线程。

注意：被唤醒的线程不会立即执行，而是需要重新竞争对象锁，拿到锁之后才会继续执行。

---

## 9. wait() 和 sleep() 有什么区别？

### 共同点

- 都可以让当前线程暂停执行；
- 都可以响应中断；
- `wait(long)` 和 `sleep(long)` 到时间后都可以自动恢复。

### 不同点

| 对比项 | wait() | sleep() |
| --- | --- | --- |
| 所属类 | `Object` | `Thread` |
| 是否需要锁 | 必须先获取对象锁 | 不要求持有锁 |
| 是否释放锁 | 会释放对象锁 | 不会释放锁 |
| 唤醒方式 | `notify()` / `notifyAll()` / 超时 / 中断 | 超时 / 中断 |
| 使用场景 | 线程间通信 | 暂停当前线程一段时间 |

重点：`wait()` 会释放锁，`sleep()` 不会释放锁。

---

## 10. 如何停止一个正在运行的线程？

常见方式有三种：

1. **使用退出标志位**：在线程循环中判断标志位，主动结束 `run()` 方法。
2. **使用 `stop()` 强制停止**：不推荐，方法已废弃，可能导致数据不一致。
3. **使用 `interrupt()` 中断线程**：推荐方式。

`interrupt()` 的表现：

- 如果线程处于 `sleep()`、`wait()`、`join()` 等阻塞状态，会抛出 `InterruptedException`；
- 如果线程正在正常运行，需要在线程内部通过 `isInterrupted()` 判断中断状态并主动退出。

## 11. synchronized 的底层原理是什么？

`synchronized` 是 Java 提供的内置锁，采用互斥方式保证同一时刻最多只有一个线程持有对象锁。

底层核心是 **Monitor**：

- 每个 Java 对象都可以关联一个 Monitor；
- Monitor 是 JVM 层面的对象；
- 线程获取锁，本质上是竞争对象关联的 Monitor。

Monitor 主要包含三个重要部分：

- **owner**：当前持有锁的线程；
- **entryList**：等待获取锁的阻塞线程队列；
- **waitSet**：调用 `wait()` 后进入等待状态的线程集合。

`synchronized` 支持锁升级：

1. 偏向锁；
2. 轻量级锁；
3. 重量级锁。

锁一旦发生激烈竞争，会逐步升级，最终可能变为重量级锁。

## 12. 谈谈你对 JMM（Java 内存模型）的理解

JMM（Java Memory Model）定义了 Java 程序中共享变量的访问规则，以及线程之间如何通过内存进行通信。

核心点：

- 所有共享变量存储在**主内存**中；
- 每个线程都有自己的**工作内存**；
- 线程对共享变量的读写，通常发生在自己的工作内存中；
- 不同线程之间不能直接访问对方的工作内存，变量值的传递必须通过主内存完成。

JMM 主要解决三类并发问题：

- **原子性**：一个或多个操作要么全部执行，要么都不执行；
- **可见性**：一个线程修改共享变量后，其他线程能够及时看到；
- **有序性**：程序执行顺序符合预期，避免指令重排序带来的问题。

## 13. CAS 是什么？基本流程是什么？

CAS 全称是 **Compare And Swap（比较并交换）**，是一种乐观锁思想，用于在无锁场景下保证共享变量操作的原子性。

CAS 包含三个值：

- **V**：内存中的实际值；
- **E**：期望值；
- **N**：要更新的新值。

执行流程：

1. 比较内存值 `V` 是否等于期望值 `E`；
2. 如果相等，说明没有其他线程修改过，更新为新值 `N`；
3. 如果不相等，说明数据已经被其他线程修改，更新失败，通常会重试。

常见使用场景：

- `AtomicInteger`、`AtomicLong` 等原子类；
- AQS；
- 并发容器中的部分操作。

CAS 底层通常依赖 `Unsafe` 类和 CPU 原子指令实现。

## 14. 谈谈你对 volatile 的理解

`volatile` 是 Java 中的关键字，可以修饰成员变量或静态成员变量。

主要作用：

1. **保证可见性**：一个线程修改了 `volatile` 变量后，其他线程能立即看到最新值。
2. **禁止指令重排序**：通过内存屏障保证特定操作前后的执行顺序。

注意：

- `volatile` 不能保证复合操作的原子性，例如 `i++`；
- 如果需要保证原子性，可以使用锁或原子类。

---

## 15. 什么是 AQS？

AQS 全称是 `AbstractQueuedSynchronizer`，是 JDK 提供的一个用于构建锁和同步器的基础框架。

核心组成：

- `state`：表示同步状态，比如锁是否被占用、重入次数等；
- CAS：用于安全修改 `state`；
- FIFO 双向等待队列：用于管理获取同步状态失败的线程。

队列中常见指针：

- `head`：指向等待队列头节点；
- `tail`：指向等待队列尾节点。

典型实现：

- `ReentrantLock`；
- `Semaphore`；
- `CountDownLatch`；
- `ReentrantReadWriteLock`。

---

## 16. AQS 是公平锁还是非公平锁？

AQS 本身只是同步器框架，既可以实现公平锁，也可以实现非公平锁。

- **公平锁**：新线程进入等待队列排队，优先让队列中等待时间最长的线程获取锁。
- **非公平锁**：新线程可以和队列中的线程一起竞争锁，可能出现插队。

`ReentrantLock` 默认是**非公平锁**，也可以通过构造方法指定为公平锁：

```java
new ReentrantLock(true);  // 公平锁
new ReentrantLock(false); // 非公平锁，默认
```

一般来说，非公平锁吞吐量更高，公平锁可以减少线程饥饿。

---

## 17. ReentrantLock 的实现原理是什么？

`ReentrantLock` 是 JUC 包下的可重入锁，底层主要基于 **AQS + CAS** 实现。

特点：

- 支持可重入：同一个线程多次获取同一把锁不会阻塞，只会增加重入次数；
- 支持公平锁和非公平锁；
- 支持可中断获取锁；
- 支持超时获取锁；
- 需要手动调用 `unlock()` 释放锁。

基本流程：

1. 调用 `lock()` 时，尝试通过 CAS 修改 AQS 的 `state`；
2. 如果修改成功，表示获取锁成功；
3. 如果失败，线程进入 AQS 等待队列；
4. 调用 `unlock()` 时减少 `state`；
5. 当 `state` 变为 0 时释放锁，并唤醒等待队列中的线程。

## 18. synchronized 和 Lock 有什么区别？

| 对比项 | synchronized | Lock |
| --- | --- | --- |
| 类型 | Java 关键字 | JUC 接口 |
| 实现层面 | JVM 层面 | Java API 层面 |
| 释放锁 | 自动释放 | 需要手动 `unlock()` |
| 可中断 | 不支持等待锁时中断 | 支持 `lockInterruptibly()` |
| 超时获取 | 不支持 | 支持 `tryLock(timeout)` |
| 公平锁 | 不支持指定公平性 | 支持公平锁/非公平锁 |
| 条件变量 | 单一等待队列 | 可创建多个 `Condition` |

总结：

- 简单同步优先使用 `synchronized`；
- 需要可中断、超时、公平锁、多条件队列等高级功能时，使用 `Lock`。

## 19. 死锁产生的条件是什么？

死锁产生需要同时满足四个条件：

1. **互斥条件**：资源同一时刻只能被一个线程占用；
2. **持有并等待**：线程已经持有一个资源，同时还在等待其他资源；
3. **不可剥夺**：线程已持有的资源不能被其他线程强制剥夺，只能主动释放；
4. **循环等待**：多个线程之间形成资源等待环路。

破坏其中任意一个条件，都可以避免死锁。

## 21. ConcurrentHashMap 的底层原理是什么？

### JDK 1.7

- 底层结构：`Segment` 数组 + `HashEntry` 数组 + 链表；
- 加锁方式：分段锁，每个 `Segment` 继承 `ReentrantLock`；
- 并发度由 `Segment` 数量决定。

### JDK 1.8

- 底层结构：数组 + 链表 / 红黑树；
- 加锁方式：
  - 插入空桶时使用 CAS；
  - 桶中已有元素时，使用 `synchronized` 锁住桶的头节点。

JDK 1.8 相比 JDK 1.7 锁粒度更细，并发性能更好。

## 22. 导致并发程序出现问题的根本原因是什么？

并发问题主要来自底层计算机系统的三个特性：

1. **多核 CPU 并行执行**：多个线程可能同时修改共享数据，引发原子性问题；
2. **CPU 缓存与主内存分离**：线程可能看不到其他线程的最新修改，引发可见性问题；
3. **编译器和处理器指令优化**：代码实际执行顺序可能与编写顺序不同，引发有序性问题。

Java 中的解决方式：

- 锁和 CAS：保证原子性；
- `volatile` 和锁：保证可见性；
- `volatile`、锁、`final`：保证有序性。

## 23. 线程池的核心参数有哪些？执行原理是什么？

线程池核心参数主要来自 `ThreadPoolExecutor` 的构造方法。

![[线程池核心参数.png]]

核心参数：

- `corePoolSize`：核心线程数；
- `maximumPoolSize`：最大线程数；
- `keepAliveTime`：非核心线程空闲存活时间；
- `unit`：时间单位；
- `workQueue`：任务队列；
- `threadFactory`：线程工厂，可自定义线程名称、是否守护线程等；
- `handler`：拒绝策略。

线程池工作流程：

![[线程池工作流程.png|415]]

1. 任务提交后，如果运行线程数小于 `corePoolSize`，创建核心线程执行任务；
2. 如果核心线程已满，任务进入 `workQueue`；
3. 如果队列满了，并且线程数小于 `maximumPoolSize`，创建非核心线程执行任务；
4. 如果线程数达到 `maximumPoolSize` 且队列也满了，执行拒绝策略。

常见拒绝策略：

1. `AbortPolicy`：直接抛出异常，默认策略；
2. `CallerRunsPolicy`：由提交任务的线程执行任务；
3. `DiscardOldestPolicy`：丢弃队列中最旧的任务，再尝试提交当前任务；
4. `DiscardPolicy`：直接丢弃任务，不抛异常。

## 24. 线程池中常见的阻塞队列有哪些？

常见阻塞队列：

- `ArrayBlockingQueue`；
- `LinkedBlockingQueue`；
- `SynchronousQueue`；
- `PriorityBlockingQueue`；
- `DelayQueue`。

### ArrayBlockingQueue 和 LinkedBlockingQueue 的区别

| 对比项 | ArrayBlockingQueue | LinkedBlockingQueue |
| --- | --- | --- |
| 数据结构 | 数组 | 链表 |
| 是否有界 | 必须指定容量，有界 | 默认近似无界，也可指定容量 |
| 锁机制 | 通常使用一把锁 | 读写分离，两把锁 |
| 使用特点 | 内存占用稳定 | 吞吐量通常更高，但要注意容量 |

实际使用线程池时，建议使用**有界队列**，避免任务堆积导致 OOM。

## 25. 如何确定核心线程数？

常见经验公式：

- **CPU 密集型任务**：`CPU 核数 + 1`
- **IO 密集型任务**：`CPU 核数 * 2` 或 `CPU 核数 * 2 + 1`
- **高并发、长耗时业务**：不能只靠调大线程池解决，需要结合缓存、异步化、限流、拆分服务、扩容等整体架构优化。

更准确的估算公式：

```text
线程数 = CPU 核数 * (1 + 等待时间 / 计算时间)
```

## 26. 线程池有哪些常见种类？

JDK 通过 `Executors` 提供了几种常见线程池创建方式：

1. `newCachedThreadPool()`：可缓存线程池，线程数可动态增长；
2. `newFixedThreadPool()`：固定大小线程池；
3. `newScheduledThreadPool()`：支持定时和周期任务；
4. `newSingleThreadExecutor()`：单线程线程池，保证任务按顺序执行。

不过实际开发中不建议直接使用 `Executors` 创建线程池，而是推荐显式使用 `ThreadPoolExecutor`。

---

## 27. 为什么不建议使用 Executors 创建线程池？

主要原因是：`Executors` 封装的部分线程池存在资源耗尽风险。

例如：

- `newFixedThreadPool()` 和 `newSingleThreadExecutor()` 使用的队列容量接近 `Integer.MAX_VALUE`，可能导致大量任务堆积，最终 OOM；
- `newCachedThreadPool()` 最大线程数接近 `Integer.MAX_VALUE`，可能创建过多线程，耗尽系统资源。

因此更推荐手动使用 `ThreadPoolExecutor`，明确指定：

- 核心线程数；
- 最大线程数；
- 队列类型和容量；
- 线程工厂；
- 拒绝策略。

## 28. CountDownLatch 的使用场景有哪些？

`CountDownLatch` 用于让一个或多个线程等待其他线程执行完成。

常见场景：

1. **批量数据导入**
   - 例如将大量数据同步到 ES；
   - 可以把数据拆分成多个批次，由线程池并发处理；
   - 主线程通过 `CountDownLatch` 等待所有批次完成。

2. **聚合多个远程服务结果**
   - 例如订单页需要同时查询订单信息、商品详情、物流信息；
   - 多个查询可以并发执行；
   - 最后等待所有结果返回后统一组装响应。

3. **异步任务统计结果**
   - 多个子任务并发执行；
   - 主线程等待所有子任务完成后汇总。

常与线程池、`Future` / `CompletableFuture` 配合使用。

## 29. 如何控制某个方法允许并发访问的线程数量？

可以使用 `Semaphore`（信号量）。

核心方法：

- `acquire()`：获取一个许可。如果没有可用许可，线程会阻塞等待；
- `release()`：释放一个许可。

示例：

```java
private final Semaphore semaphore = new Semaphore(10);

public void handle() {
    try {
        semaphore.acquire();
        // 执行业务逻辑
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        semaphore.release();
    }
}
```

上面代码表示同一时刻最多允许 10 个线程执行 `handle()` 方法。

## 30. 谈谈你对 ThreadLocal 的理解

`ThreadLocal` 用于为每个线程提供独立的变量副本，主要作用：

1. **线程隔离**：每个线程使用自己的资源对象，避免线程安全问题；
2. **线程内共享**：同一线程内的多个方法可以共享上下文数据。

常见使用场景：

- 保存用户上下文；
- 保存请求链路信息；
- 数据库连接或事务上下文；
- 日期格式化工具等非线程安全对象。

### ThreadLocal 底层原理

每个 `Thread` 内部都有一个 `ThreadLocalMap`：

- 调用 `set()` 时，以当前 `ThreadLocal` 对象作为 key，以设置的对象作为 value，存入当前线程的 `ThreadLocalMap`；
- 调用 `get()` 时，以当前 `ThreadLocal` 对象作为 key，从当前线程的 `ThreadLocalMap` 中取值；
- 调用 `remove()` 时，移除当前线程中对应的 key-value。

### ThreadLocal 为什么可能导致内存泄漏？

`ThreadLocalMap` 中的 key 是弱引用，value 是强引用。

如果 `ThreadLocal` 对象被 GC 回收，key 会变成 `null`，但 value 仍然被当前线程强引用着。如果线程长期存活，例如线程池中的线程，就可能导致 value 无法及时释放，造成内存泄漏。

最佳实践：

```java
try {
    threadLocal.set(value);
    // 使用 ThreadLocal
} finally {
    threadLocal.remove();
}
```

使用完一定要调用 `remove()`。
